# マージの前に、最新の main と組み合わせた状態で CI が通っていることを、ルールセットの必須のチェックで求める

## 背景と課題

#102（設定の置き場所の変更）が 11:24 にマージされ、11分後に #106 がマージされた。#106 の CI は #102 より前の main で動いて通っていたので、古い置き場所に設定を書くテストがそのまま入り、main の Test のワークフローが失敗した（#108）。ルールセットには、マージの前に CI が通ることを求める規則が無く（deletion・non_fast_forward・pull_request だけ）、main が先に進んでいても、古い CI の結果のままマージできた。

ただし、Lint・Test のワークフローは `paths-ignore` でドキュメントだけの PR では動かないので、そのまま必須のチェックにすると、チェックが「待ち」のまま残ってマージできなくなる。

## 判断の決め手

* main が先に進んでいる PR は、最新の main と組み合わせて CI が通るまでマージできないこと
* ドキュメントだけの PR も、これまでどおりマージできること
* repo-setup で作るルールセットでも使え、CI の無いリポジトリでマージできなくならないこと

## 検討した案

* ルールセットの必須のチェックと「最新の main の取り込み」（strict）を求める
* マージキューを使う

## 判断の結果

選んだ案：「ルールセットの必須のチェックと strict を求める」。理由は、個人のアカウントのリポジトリでも使えるため（マージキューは、個人のリポジトリでは使えない見込みだった。#112 の時点では未確認）。

* Lint・Test の `paths-ignore` をやめ、いつも動かす。最初の `changes` ジョブがドキュメントだけの変更かを判定し、そのときだけ lint・test を飛ばす。
* 最後に必ず動く門番のジョブ（`lint-result`・`test-result`）を足し、これを必須にする。飛ばしたときも成功にし、本体が失敗・取り消しなら失敗にする。test は matrix で、飛ばしたジョブのチェック名が展開されず「待ち」になるため、門番のジョブにまとめた。
* repo-setup（`setup-repo.sh`・`setup-all.sh`）に `--required-check <名前>` を足す。指定した一覧で必須のチェックを置き換え、最新の base_branch の取り込みも求める。チェックの名前はチームの CI で決まり、CI が無いと「待ち」のまま残るので、既定では入れない。

### 結果として起きること

* 良い点：古い main で通った CI の結果のままマージして、main が壊れることを防げる。
* 悪い点：strict では、main が進むたびに、PR へ main を取り込み直して CI を待つ必要がある。
* 悪い点：プラグインは既定で必須のチェックを入れないので、設定しないまま使うと、CI が通らなくてもマージできる。

### 確認

`tests/docs-only.bats` で、ドキュメントだけの変更かの判定を確かめる。`tests/setup-repo.bats` で、`--required-check` で必須のチェックと strict が設定されることを確かめる。
