# PR の確認と対応は、分けずに1つのスキル gh-pr-check にまとめる

## 背景と課題

「PR を確認して」と頼んでも、pr-respond は起動しなかった。description の例が「指摘に対応して」など対応を頼む言い方だけで、状態を尋ねる言い方が無かったためである（#254）。#254 は、確かめるだけの pr-check を足して pr-respond と分ける案だった。しかし、確認も対応も同じ PR の状態（CI・レビュー・指摘）を見る流れである。また、返信するつもりが無いのに「respond」が起動するのは、使う人に分かりにくい。確認と対応を、どう構成するか。

## 判断の決め手

* 「PR を確認して」と「指摘に対応して」のどちらでも、迷わず起動すること
* 同じ状態の読み取りと一覧を、2つのスキルに複製しないこと
* 返信が必須ではないことが、名前から分かること
* 破壊的変更の大きさ（既存の利用者に直させるもの）が小さいこと

## 検討した案

* 確認だけの pr-check を足し、pr-respond と分ける（#254 の案）
* pr-respond の description だけを広げて、名前は変えない
* 確認から対応までを1つのスキルにまとめ、名前を gh-pr-check に改める

## 判断の結果

選んだ案：「確認から対応までを1つのスキルにまとめ、gh-pr-check に改める」。理由は、状態を見て、対応が要れば直すところまでが1つの流れで、2つに分けると一覧を作る手順が重なり、pr-check から pr-respond への受け渡しも要るから。名前は、`gh pr checks` / `gh pr view` に対応させ、返信が必須ではないことも表す。

* スキル `pr-respond` を `gh-pr-check` に改める。手順は「状態を見せる → 指摘・質問・CI の失敗があれば分類して、直すものを選んでもらう → 直す・承認・push・返信」。対応が要らなければ、状態だけを見せて何も変えずに終える。
* 担当の skill の設定キー `pr_respond.handlers` を `pr_check.handlers` に改める。
* 旧名と旧キーの別名は残さない。`/dev-workflow:pr-respond` は呼べなくなり、利用者は config.json のキーを直す。旧キーが残っていれば、doctor が警告する。移行のしかたは README に書く。

### 結果として起きること

* 良い点：「PR を確認して」「CI は通った？」「指摘に対応して」のどれでも、同じスキルが起動する。
* 良い点：状態の読み取りと一覧の手順が1か所にまとまる。
* 悪い点：破壊的変更になる。旧キーのままだと、担当の skill への委譲が効かない（doctor の警告で気づける）。
* 悪い点：確認だけを頼んだときも、同じスキルの長い手順を読み込む。

## 他の案の利点と欠点

### 確認だけの pr-check を足し、pr-respond と分ける（#254 の案）

* 良い点：スキルを足すだけで、既存の呼び方と設定がそのまま動く（破壊的変更ではない）。
* 悪い点：状態の読み取りと一覧が2つのスキルにまたがり、pr-check から pr-respond への受け渡しの手順が要る。
* 悪い点：「respond」の名前が残り、返信が必須でないことが名前から分からない。

### pr-respond の description だけを広げて、名前は変えない

* 良い点：変更が小さく、破壊的変更にならない。
* 悪い点：確認だけのときに「respond」が起動する分かりにくさが残る。
