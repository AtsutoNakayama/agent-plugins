# スキルは自動で呼べるようにし、確認を取るのは AI の文章を GitHub に残すときと、スクリプトが守っていない取り消しにくい操作の前だけにする

## 背景と課題

最初は、外部に影響するスキルに `disable-model-invocation: true` を付け、明示的に呼んだときだけ動くようにしていた。依頼するだけで使えるよう、#23（2026-09-27）で全スキルからこれを外し、代わりに、外部に影響する操作（GitHub への書き込み、push）と取り消しにくい操作（ワークツリーやブランチの削除）の前には、必ず AskUserQuestion で確認を取ることにした。

その後、次の問題が出た。

* 「#N に着手して」「マージしたので片付けて」と伝えた後に、task-start・task-finish がもう一度確認を取るのが煩わしい。どちらも依頼の一言で結果が決まる。task-start の割り当てと列の移動は簡単に戻せる。task-finish で作業が失われるときは、`cleanup.sh` が何も消さずに止まるので、確認はそれ以上を防いでいない。
* 確認の選択肢の説明に「--dry-run を外して実行する」のような内部の手順が書かれ、ユーザーに意味が伝わらなかった。

どの操作で確認を取り、確認では何を見せるか。

## 判断の決め手

* 依頼するだけでスキルを使えること
* AI が決めた内容や、取り消しにくい操作は、使用者が見てから行われること
* 確認を挟んでも防げるものが無い操作で、手間を増やさないこと

## 検討した案

* 外部に影響する操作と取り消しにくい操作の前には、必ず確認を取る（#23 で決めた形）
* 確認を取るのは、AI が決めた内容を GitHub に残すときと、スクリプトが安全を確かめていない取り消しにくい操作の前だけにする

## 判断の結果

選んだ案：「確認を取るのは、AI が決めた内容を GitHub に残すときと、スクリプトが安全を確かめていない取り消しにくい操作の前だけにする」。理由は、依頼の一言で結果が決まり、戻せる操作や、失うものが無いことをスクリプトが確かめる操作では、確認を挟んでも防げるものが無く、手間が増えるだけだから。

* どのスキルも、依頼の内容から自動で呼ばれてよい（`disable-model-invocation` は付けない。#23 から変えていない）。
* 次の操作の前には、何が起きるか（下書きや dry-run の結果）を見せてから、AskUserQuestion で確認を取る。
  * AI が決めた内容（Issue や PR の文章、Story Point の見積もり）を GitHub に残す操作
  * 取り消しにくく、スクリプトが安全を確かめていない操作（push、リポジトリの設定の変更など）
* 依頼の一言で結果が決まり、戻せる操作（割り当て、列の移動）や、失うものが無いことをスクリプトが確かめる操作（マージ済みのワークツリーとブランチの削除）は、確認せずに進めて結果を伝える。
* 確認の選択肢の説明には、選ぶと実際に何が起きるか（作るもの・削除するもの・GitHub に書き込むもの）を使用者の言葉で書き、フラグやスクリプト名などの内部の手順は書かない。

### 結果として起きること

* 良い点：着手と後片付けが、依頼の一言で最後まで進む。
* 良い点：確認の選択肢を読めば、何を承認するのかが分かる。
* 悪い点：確認の画面で止められていたものが、黙って消えるおそれがある。そのため `cleanup.sh` は、git が無視するファイル（`.env` など）があれば一覧を出して何も消さずに止まり（消してよいときだけ `--remove-ignored` で続ける）、`status.showUntrackedFiles=no` の設定でも未コミットのファイルを見落とさないようにした。

### 確認

`tests/skills.bats` で、どの SKILL.md にも `disable-model-invocation` が無いこと、task-start・task-finish が実行の確認を取らないこと、確認を残すスキルに選択肢の説明の書き方が書かれていることを確かめる。
