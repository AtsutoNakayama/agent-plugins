# PR を無人で直すのは、CI の失敗・許可した投稿者の指摘・main とのコンフリクトだけにし、CI が全部通ってマージできる状態（CLEAN）になったら見回りを終える

## 背景と課題

PR を定期的に見回し、CI の失敗・レビューの指摘・コンフリクトを無人で直す仕組みを足したい。#269（自動で作った PR の指摘に CI で対応）は、許可した投稿者・回数の上限・保留の列で止まる、までを決めているが、定期の見回り・CI の失敗・コンフリクト・見回りを終える条件は決めていない。

今の pr-respond は、push と返信を承認してから行い、スレッドは resolved にしない（レビューした人に任せる）。無人では、この承認を指示役（実行を動かすセッション）の判断に置き換える（[ADR 000267](000267-opt-in-auto-mode.md) の延長）。

どこまでを自動で直し、どこから人に任せるか。いつ見回りを終えるか。何をきっかけに起動するか。スレッドをどうするか。どんな条件で無人で push してよいか。

## 判断の決め手

* 人の判断なしに main に入らないこと（マージは人が行う。ADR 000267）
* 決めきれないときは、推し量らずに止まり、人に引き継ぐこと
* 直す対象が無い回で、プランの使用量を消費しないこと
* 暴走（同じ失敗の繰り返し・強制 push・同時実行による競合）で、PR やブランチを壊さないこと
* レビューした人の判断（resolved にするか）を、AI が奪わないこと
* 後続の Issue（判定スクリプト・コンフリクトの自動修正・見回りのワークフロー）が、この ADR だけを見て進められること

## 検討した案

直す対象

* 人が見る前提の今の pr-respond のまま、無人では直さない
* 指摘・CI の失敗・コンフリクトのすべてを、投稿者を問わず直す
* CI の失敗・許可した投稿者の指摘・main とのコンフリクトに絞って直し、ほかは直さずに止まる

見回りを終える条件

* 1回直したら終える
* 指摘のスレッドがすべて resolved になったら終える
* CI が全部通り、マージできる状態（CLEAN）になったら終える（CodeRabbit の最初のレビューが付くまで待つ）

起動のしかた

* 定期（cron）で毎回、Claude を動かす
* イベント駆動（`check_suite`・`pull_request_review` などの GitHub のイベント）だけで起動する
* 定期の見回りは、スクリプトだけで「直す対象があるか」を判定し、あるときだけ Claude を動かす

resolve の方針

* 直した指摘は、自分で `resolveReviewThread` を呼んで resolved にする
* 返信までにし、resolved にするのは、人のレビュアーはその人に、CodeRabbit は CodeRabbit に任せる

無人の push

* 制限を置かず、通るまで直して push する
* 強制 push の禁止・PR ごとの回数の上限・同じ PR の直列化を置く

## 判断の結果

選んだ案：直す対象は「CI の失敗・許可した投稿者の指摘・main とのコンフリクトに絞る」、終える条件は「CI が全部通り、CLEAN になったら終える」、起動は「定期の見回りで、スクリプトが対象の有無を判定し、あるときだけ Claude を動かす」、resolve は「返信までにして自分では resolved にしない」、push は「強制 push の禁止・回数の上限・直列化を置く」。

### 直す対象と止まる条件

* 直すのは次の3つだけ。
  * CI の失敗（必須のチェックの失敗。ログを読んで直す）
  * 許可した投稿者のレビューの指摘（行ごとのスレッドと、diff の外の指摘のレビュー本文・PR コメント）。許可した投稿者は、#269 で決めた設定に従う（人のレビュアーと CodeRabbit を、設定で個別に許可する）
  * main とのコンフリクト（`/dev-workflow:branch-update` の手順。直し方の確認は指示役が答える）
* 直さないもの：許可していない投稿者の指摘と質問、フォークからの PR、人が作った PR（対象は自動で作った PR のみ）、マージ自体（人が行う。`allow_ai_merge` にかかわらず）、強制 push が要る直し方、範囲外の変更。許可していない投稿者の分は、無視する（コメントも止まる理由もつけない）。
* 次のときは、それ以上進めず、理由を Issue にコメントして保留の列（`status.hold`。[ADR 000195](000195-hold-status-column.md)）に移して止まる（ADR 000267 と同じ止まり方）。
  * 指摘が、要件の変更・設計の判断・範囲外の作業を求めていて、直してよいか決められない
  * 同じ失敗（CI のチェックまたは同じ指摘）が、直しても `repair.max_fix_attempts` 回続く
  * コンフリクトが、両立のさせ方を決められない（どちらの意図を残すか判断できない）
  * PR ごとの push の回数の上限に達した
  * 直してもテスト・lint がローカルで通らない
* 止まる条件に当たらない「何も直すものが無い」回は、止まらずに何もせず終わる（コメントも列の移動もしない）。

### 見回りを終える条件

* 終えるのは、**必須のチェックがすべて成功し、PR がマージできる状態（`mergeStateStatus` が CLEAN）になり、未対応の許可した投稿者の指摘が無い**とき。
* CodeRabbit の最初のレビューが付く前に終えない。CodeRabbit を許可した投稿者にしているリポジトリでは、CodeRabbit のレビューまたはそのレート制限のコメントが付くまで終えない（待つ）。ただし、PR を作ってから `repair.review_wait_minutes`（既定 60）経っても付かないときは、待たずに終える（CONTRIBUTING.md の Claude によるレビューの見回りと同じ時間。CodeRabbit の障害で、見回りが際限なく続かないため）。
* 終えたら、それ以降の見回りは対象にしない。人が後から push したり指摘を足したりして、状態が CLEAN でなくなれば、また対象になる。
* CLEAN でない理由が、人のレビューの承認待ち・resolved でないスレッドだけのとき（許可していない投稿者の分など、自分では直せない）は、止まらずに終える。

### 起動のしかた

* 定期の見回り（GitHub Actions の `schedule`）を使う。毎回、まず Claude を使わないスクリプトで、対象の PR（自動で作った・開いている・直す対象がある・止まっていない）を判定し、**対象があるときだけ** Claude を動かす。対象が無い回は、スクリプトだけで終わり、プランの使用量を消費しない。
* イベント駆動だけにしない。`GITHUB_TOKEN` が起こしたイベントでは後続のワークフローが起動しないことと、CodeRabbit のレビューが遅れて付く・レート制限で付かないなど、「何も起きない」ことを待つ必要があることと、イベントを取りこぼしたときに誰も気づけないことが理由。イベントの起動は、遅延を短くしたいときに後から足してよい（判定スクリプトは同じものを使う）。
* 判定スクリプト（後続の Issue）の出力は JSON で、PR ごとに、直す対象の種類（`ci`・`review`・`conflict`）・終える条件を満たすか・止まる条件に当たるかを返す。

### 返信と resolve

* 人のレビュアーの指摘は、直したコミットを添えて返信するまでにし、スレッドは resolved にしない（レビューした人が確かめて resolved にする。今の pr-respond と同じ）。
* CodeRabbit の指摘は、CONTRIBUTING.md の手順どおり、直したコミットを添えて `@coderabbitai` 付きで返信し、CodeRabbit が現在のコードを読んで resolved にする。`@coderabbitai resolve` は使わない。
* どの場合も、自分では GraphQL の `resolveReviewThread` を呼ばない。直さない指摘には、理由を返信する。
* 無人で返信する文章は、定型の枠（直したコミット・直した内容の要約）に収め、push と返信の承認は指示役が答える。

### 無人で push する条件

* 強制 push（`--force`・`--force-with-lease` を含む）をしない。push は fast-forward だけで、リモートが先に進んでいたら取り込んでから push する。コンフリクトが取り込みで起きたら、上の止まる条件に従う。
* PR ごとに、無人の push の回数の上限（`repair.max_pushes_per_pr`、既定 5）を置く。上限は PR ごとに数える（実行をまたぐ。数え方は、push のコミットのトレーラー等、後続の Issue で決める）。上限に達したら、止まる。
* 同じ PR の実行は直列にする（GitHub Actions の `concurrency` を PR の番号で分け、`cancel-in-progress: false`）。直している最中に、次の見回りが同じ PR を触らないため。ほかの PR とは並行してよい。
* push は、自動で作った PR のブランチにだけ行う。main へは push しない。

### 結果として起きること

* 良い点：CI の失敗・指摘・コンフリクトで止まっていた自動の PR が、人の手なしでマージできる状態まで進む。マージは人が行う。
* 良い点：対象が無い回は、スクリプトだけで終わり、使用量を消費しない。
* 良い点：レビューした人の resolved の判断を奪わない。
* 良い点：強制 push の禁止・回数の上限・直列化で、暴走しても被害が1つの PR に収まる。
* 悪い点：定期の見回りなので、失敗や指摘が付いてから直るまで、最大で見回りの間隔だけ遅れる。
* 悪い点：人のレビュアーのスレッドは返信だけで残るので、人が resolved にするまで、PR はキューに入れられない。
* 悪い点：CodeRabbit を待つ間は終えないので、障害時は `repair.review_wait_minutes` 分だけ見回りが続く。
* 悪い点：`repair.*` の設定が増える。

### 確認

後続の Issue で、次を確かめる。判定スクリプトの bats で、対象の判定（直す対象の種類・CLEAN の判定・CodeRabbit を待つ・待つ時間の超過・許可していない投稿者・止まる条件・上限）を、偽の `gh` で確かめる。ワークフローは actionlint で検査し、`concurrency` が PR ごとで `cancel-in-progress: false` であること、強制 push を使っていないこと、判定が対象なしのとき Claude を動かさないことを確かめる。`tests/skills.bats` で、無人で直す場合の SKILL.md に、resolveReviewThread を呼ばないことが書かれていることを確かめる。

## 各案の長所と短所

### 人が見る前提の今の pr-respond のまま、無人では直さない

* 良い点：仕組みを足さずに済み、AI の push と返信は必ず人が承認する。
* 悪い点：Issue から自動で作った PR が、CI の失敗や指摘で止まったまま、人が来るのを待つ。

### すべてを、投稿者を問わず直す

* 良い点：人が何もしなくてよい範囲が最大になる。
* 悪い点：許可していない投稿者の文章が、そのまま Claude への指示になりうる（指示の混入）。
* 悪い点：要件や設計の判断を求める指摘まで、AI が決めてしまう。

### CI の失敗・許可した投稿者の指摘・コンフリクトに絞って直す

* 良い点：直す範囲が決まっていて、範囲外は止まって人に引き継ぐので、被害が小さい。
* 悪い点：許可の設定と止まる条件を、決めて保つ手間がある。

### 1回直したら終える／スレッドがすべて resolved になったら終える

* 悪い点：1回では、直した結果の CI やレビューを確かめられない。
* 悪い点：人のレビュアーのスレッドは自分では resolved にしないので、人が resolved にするまで終わらない。

### CLEAN になったら終える

* 良い点：マージできる状態という、GitHub が示す1つの値で決められ、CI の結果まで含む。
* 悪い点：CodeRabbit のレビューは CLEAN と無関係に遅れて付くので、待つ決まりを別に要る。

### 定期（毎回 Claude を動かす）

* 良い点：実装が単純で、取りこぼしが無い。
* 悪い点：対象が無い回でも使用量を消費する。

### イベント駆動だけ

* 良い点：遅延が短く、対象があるときだけ動く。
* 悪い点：`GITHUB_TOKEN` が起こしたイベントで後続が起動しないため、起動しない場合がある。
* 悪い点：レビューが遅れる・付かない状況のような、待つ判断ができず、取りこぼしに気づけない。

### 定期の見回りで、スクリプトが対象を判定し、あるときだけ Claude を動かす

* 良い点：取りこぼしが無く、対象が無い回は使用量を消費しない。
* 悪い点：直るまでの遅れが、見回りの間隔になる。

### 直した指摘を自分で resolved にする／返信までにする

* 悪い点（自分で resolved）：レビューした人が確かめる前にスレッドが閉じ、直っていない指摘が見えなくなる。
* 良い点（返信まで）：レビューした人（CodeRabbit なら CodeRabbit）が確かめて閉じるので、判断が奪われない。
* 悪い点（返信まで）：人が resolved にするまで、PR がキューに入れられない。

### 制限なしで push する／強制 push の禁止・回数の上限・直列化を置く

* 悪い点（制限なし）：直せない失敗を繰り返して、使用量を消費し続け、ブランチを荒らす。
* 良い点（制限あり）：暴走しても止まり、人に引き継ぐ。
* 悪い点（制限あり）：上限が低いと、直せたはずの PR でも止まる。
