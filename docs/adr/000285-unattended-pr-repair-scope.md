# PR を無人で直すのは、CI の失敗・許可した投稿者の指摘・main とのコンフリクトだけにし、必須のチェックが全部通り、自分で直せない理由を除いてマージを妨げるものが無くなったら見回りを終える

## 背景と課題

PR を定期的に見回し、CI の失敗・レビューの指摘・コンフリクトを無人で直す仕組みを足したい。#269（自動で作った PR の指摘に CI で対応）は、許可した投稿者・回数の上限・保留の列で止まる、までを決めているが、定期の見回り・CI の失敗・コンフリクト・見回りを終える条件は決めていない。

今の pr-respond は、push と返信を承認してから行い、スレッドは resolved にしない（レビューした人に任せる）。無人では、この承認を指示役（実行を動かすセッション）の判断に置き換える（[ADR 000267](000267-opt-in-auto-mode.md) の延長）。

どこまでを自動で直し、どこから人に任せるか。いつ見回りを終えるか。何をきっかけに起動するか。スレッドをどうするか。どんな条件で無人で push してよいか。

## 判断の決め手

* 人の判断なしに main に入らないこと（マージは人が行う。ADR 000267）
* 決めきれないときは、推し量らずに止まり、人に引き継ぐこと
* 直す対象が無い回で、プランの使用量を消費しないこと
* 暴走（同じ失敗の繰り返し・強制 push・同時実行による競合）で、PR やブランチを壊さないこと
* レビューした人の判断（resolved にするか）を、AI が奪わないこと
* 後続の Issue（判定スクリプト・コンフリクトの自動修正・見回りのワークフロー）が、この ADR だけを見て進められること

## 検討した案

直す対象

* 人が見る前提の今の pr-respond のまま、無人では直さない
* 指摘・CI の失敗・コンフリクトのすべてを、投稿者を問わず直す
* CI の失敗・許可した投稿者の指摘・main とのコンフリクトに絞って直し、ほかは直さずに止まる

見回りを終える条件

* 1回直したら終える
* 指摘のスレッドがすべて resolved になったら終える
* 必須のチェックが全部通り、自分で直せない理由を除いてマージを妨げるものが無くなったら終える（レビューの到着を待つ投稿者のレビューが付くまで待つ）

起動のしかた

* 定期（cron）で毎回、Claude を動かす
* イベント駆動（`check_suite`・`pull_request_review` などの GitHub のイベント）だけで起動する
* 定期の見回りは、スクリプトだけで「直す対象があるか」を判定し、あるときだけ Claude を動かす

resolve の方針

* 直した指摘は、自分で `resolveReviewThread` を呼んで resolved にする
* 返信までにし、resolved にするのは、人のレビュアーはその人に、CodeRabbit は CodeRabbit に任せる

無人の push

* 制限を置かず、通るまで直して push する
* 強制 push の禁止・PR ごとの回数の上限・同じ PR の直列化を置く

## 判断の結果

選んだ案：直す対象は「CI の失敗・許可した投稿者の指摘・main とのコンフリクトに絞る」、終える条件は「必須チェックが全部成功し、自分で直せない理由を除いて、マージを妨げるものが無くなったら終える」、起動は「定期の見回りで、スクリプトが対象の有無を判定し、あるときだけ Claude を動かす」、resolve は「返信までにして自分では resolved にしない」、push は「強制 push の禁止・回数の上限・直列化を置く」。

### 前提と設定

* #269 の ADR は、この ADR を書いた時点ではまだ無い。そのため、見回りが使う設定の名前と「自動で作った PR」の見分け方を、この ADR で仮に決める。#269 の ADR が違う名前や見分け方を決めたら、#269 の側に合わせ、新しい ADR で直す（この ADR は書き換えない）。
* 設定は `repair.*` にまとめる（既定は `plugins/dev-workflow/defaults/workflow.json`）。

| 設定 | 既定 | 意味 |
| --- | --- | --- |
| `repair.enabled` | false | 見回りを使うか。false なら対象にしない |
| `repair.allowed_authors` | [] | 指摘を直してよい投稿者（GitHub のログイン名。人のレビュアーも CodeRabbit のようなボットも、ここに並べる） |
| `repair.wait_for_reviewers` | [] | 到着を待つレビューの投稿者（下の「見回りを終える条件」）。特定のボットの名前は、プラグインの既定に入れない |
| `repair.review_wait_minutes` | 60 | 待つ時間の上限（分） |
| `repair.max_fix_attempts` | 3 | 同じ失敗を直す回数の上限 |
| `repair.max_pushes_per_pr` | 5 | 1つの PR に、無人で push する回数の上限（再開でリセット） |
| `repair.bot_logins` | [] | 自動で作った PR の作成者として認める、task-auto の GitHub App のログイン名 |
| `repair.reply_logins` | [] | 無人の返信（`repair-reply`）の投稿者として認める、見回りを動かす GitHub App のログイン名 |

* このリポジトリでは、`.claude/dev-workflow/config.json` で `repair.wait_for_reviewers` に CodeRabbit（`coderabbitai[bot]`）を設定する。CodeRabbit 固有の運用は、CONTRIBUTING.md の側が正本で、プラグインの文には名前を出さない。
* 「自動で作った PR」は、次の3つをすべて満たす PR とする。(1) 作成者が task-auto の GitHub App のログイン（`repair.bot_logins`）のどれかである。(2) head がこのリポジトリのブランチである（フォークでない）。(3) 本文に task-auto が入れるマーカー `<!-- dev-workflow:auto -->` がある（補助。task-auto が `pr-create` で本文に足す。後続の Issue で足す）。作成者と head は人が偽れないが、本文は書き換えられるため、作成者と head を必須にする。ブランチ名や draft かどうかでは見分けない。満たさない PR は、対象にしない。

### 直す対象と止まる条件

* 直すのは次の3つだけ。
  * CI の失敗（必須のチェックの失敗。ログを読んで直す）
  * 許可した投稿者（`repair.allowed_authors`）のレビューの指摘（行ごとのスレッドと、diff の外の指摘のレビュー本文・PR コメント）
  * main とのコンフリクト（`/dev-workflow:branch-update` の手順。直し方の確認は指示役が答える）
* 直さないもの：許可していない投稿者の指摘と質問、フォークからの PR、自動で作った PR ではないもの、マージ自体（人が行う。`allow_ai_merge` にかかわらず）、強制 push が要る直し方、範囲外の変更。許可していない投稿者の分は、無視する（コメントも止まる理由も付けない）。
* 次のときは、それ以上進めず、理由を Issue にコメントして保留の列（`status.hold`。[ADR 000195](000195-hold-status-column.md)）に移して止まる（ADR 000267 と同じ止まり方）。
  * 指摘が、要件の変更・設計の判断・範囲外の作業を求めていて、直してよいか決められない
  * 同じ失敗が、直しても `repair.max_fix_attempts` 回続く（下の「同じ失敗」）
  * コンフリクトが、両立のさせ方を決められない（どちらの意図を残すか判断できない）
  * PR ごとの push の回数の上限に達した
  * 処理に時間がかかりすぎた（下の「無人で push する条件」の上限）
  * 直すのに `.github/workflows/` か `.claude/` の変更が要る
* 止まる条件に当たらない「何も直すものが無い」回は、止まらずに何もせず終わる（コメントも列の移動もしない）。
* `repair.max_fix_attempts`（既定 3）は、`auto.max_fix_attempts`（既定 3）と同じ値にそろえるが、別の設定にする。`auto.*` は task-auto が1回の実行の中で直す回数で、`repair.*` は見回りが実行をまたいで直す回数であり、数える単位が違うため。
* 「同じ失敗」は、次が一致するものとする。CI の失敗は、チェックの名前と、失敗のログの先頭のエラー行（タイムスタンプとパスを除いて正規化して比べる）。レビューの指摘は、スレッド（または diff の外の指摘のコメント）の ID。ローカルでテストや lint が通らないときも、同じ上限に数える（失敗のテストの名前と、先頭のエラー行で一致を見る）。
* インフラ起因らしい失敗（再実行で通る失敗。ランナーの障害・ネットワークの失敗・タイムアウトなど）は、直さずに、そのチェックを1回だけ再実行する。再実行でも通らなければ、同じ失敗として数える。

### 状態の持ち方（対象にしない条件と再開）

見回りの状態は、次の2つだけで持つ。ほかに状態のファイルやラベルは足さない。

* **止まった**：PR が閉じる Issue（本文の `Closes #N`）が、保留の列にある。保留の列は Issue 単位、見回りは PR 単位なので、止まりの判断は PR が閉じる Issue の列で行う。task-auto が止めた Issue の PR も、同じ規則で対象にしない。PR の `Closes #N` が1つに決まらない（無い・複数）ときは、その PR は対象にせず（無人では直さない）、見回りのログに残すだけにする。
* **終えた**：PR に、見回りが付けた PR コメントのマーカー `<!-- dev-workflow:repair-done sha=<head の sha> at=<時刻> -->` がある。マーカーが複数あれば最新のものを見て、無ければ未終了として扱う。「マーカーの sha が今の head と同じで、かつ、マーカーの時刻より後に許可した投稿者の新しいコメントが無い」間だけ、対象にしない。ただし、sha が同じで新しい指摘が無くても、必須のチェックが失敗している、またはコンフリクトしている（`mergeStateStatus` が DIRTY など）ときは、マーカーを無視して対象に戻す。

再開の起点は、PR の最新の `repair-done` マーカー、人の push（実行ログのコメントに対応しない、無人でないコミットの push）、許可した投稿者の最新の指摘（コメント）のうち、時刻が最も新しいものにそろえる。実行ログのコメントの件数は、この起点より後のものだけを数える。push の回数のリセットは、人の push、または許可した投稿者の新しい指摘があったときだけにする。保留の列の移動ではリセットしない。

止まるときは、Issue のコメントに、理由の種類（`push-limit`・`same-failure`・`other`）をマーカー `<!-- dev-workflow:repair-stopped reason=<種類> -->` 付きで残す。人が保留の列から戻しても、同じ理由が残っている間（上限に達したまま、新しい人の push も新しい指摘も無い）は、再び止まる。人が直して push するか、許可した投稿者が新しい指摘を付ければ、リセットして再開する。

### 見回りを終える条件

終える条件は、次の1つの規則で決める。

> **必須のチェックがすべて成功し、許可した投稿者の未対応の指摘が無く、マージを妨げているものが、自分で直せない理由だけである。**

判定スクリプトは、次の3つを見て決める。

* 必須のチェックの状態。必須のチェックの集合は、PR の base ブランチに適用されるルールセットと従来のブランチ保護設定の、必須のステータスチェックから取る（`statusCheckRollup` の値だけでは、必須かどうか分からないため）。その各チェックが `statusCheckRollup` に存在して成功しているときだけ、成功とみなす。失敗・実行中・`statusCheckRollup` に無い（欠落）チェックが1つでもあれば、終えない。必須のチェックの集合を取れなかったときも終えない（止まらず、次の見回りでもう一度判定する）
* 許可した投稿者の未対応の指摘（下の「対応済み」）の有無
* `mergeStateStatus` が CLEAN なら、これで終える。CLEAN 以外（BLOCKED など）は、理由が「自分で直せないものだけ」のときに限って終える。自分で直せない理由は、次のとおりで、スクリプトは次の値で見分ける。
  * `reviewDecision` が `REVIEW_REQUIRED`（人の承認待ち）。ただし、`repair.wait_for_reviewers` のレビューを待っている間（レビューが届かず、待つ時間も過ぎていない間）はこの理由を適用せず、終えない
  * 未 resolved のスレッドが残っていて、そのスレッドの投稿者がすべて許可した投稿者でない、または許可した投稿者の分が「対応済み」である（resolved にするのは、レビューした人または CodeRabbit）
  * 上の2つ以外の理由（必須のチェックの失敗・コンフリクト・許可した投稿者の未対応の指摘）が1つでもあれば、終えず、直す対象になる

見回りを終えることは、マージできることを意味しない。人のレビュアーの行ごとのスレッドは、返信までで resolved にしない（自分では resolved にしない）ので、終えたあとも、人が resolved にするまで PR はマージキューに入れられない（CONTRIBUTING.md のマージの条件）。判定スクリプトの出力では、「見回りを終える条件を満たすか」と「マージできるか（`mergeStateStatus` が CLEAN か）」を別の値にする。

**対応済み**：許可した投稿者の**各コメント**（行ごとのスレッドの1つ1つのコメント、diff の外の指摘のレビュー本文、PR コメント）ごとに決める。そのコメントより後に、無人の実行の返信（マーカー `<!-- dev-workflow:repair-reply -->` 付きで、投稿者が `repair.reply_logins` のどれかであるもの。マーカーだけでは対応済みにしない。直したコミットを添えたもの、または直さない理由）があれば、対応済みとする。コミットの有無は問わない。同じスレッドに後から付いた許可した投稿者のコメントは、新しい未対応として数える。返信は、対象のコメントに結び付ける。返信のマーカーに対象のコメントの ID を入れ（`<!-- dev-workflow:repair-reply to=<コメントの ID> -->`）、スクリプトは、返信の `to` が、そのコメントの ID と一致する返信だけを、そのコメントの対応済みにする（別の指摘への返信は、時刻が後でも、ほかのコメントを対応済みにしない）。スクリプトが見るのは、コメントの投稿者と ID と時刻、返信の投稿者とマーカー（`to` を含む）と時刻だけである。

**確認だけのコメント**：許可したボットの、直ったことの確認や情報だけで、直す要求を含まないコメントは、未対応に数えない。判定の基準は、そのコメントが付いたスレッドが resolved であること、または `repair.wait_for_reviewers` の投稿者のコメントのうち定型の確認の文（後続の Issue で定型を決める）であること、のどちらかとする。ループを防ぐため、無人の実行は、ボットの確認コメントに返信しない。

**待つもの**：`repair.wait_for_reviewers` の投稿者のレビューは、最初のレビューだけでなく、無人の push の後の増分のレビューも待つ。待つ基準の時刻は、PR の作成時刻（最初のレビュー）と、無人の push の時刻（増分のレビュー）である。「到着」は、基準の時刻より後で、今の head に対するレビューが付くこととする。レート制限を知らせるコメントは到着に数えない。その場合は、Claude のレビューの見回り（CONTRIBUTING.md）がレビューを付けるか、待つ時間が過ぎるまで待つ。基準の時刻から `repair.review_wait_minutes` 経っても到着しないときは、待たずに終える（レビューの障害などで、見回りが際限なく続かないため）。

### 起動のしかた

* 定期の見回り（GitHub Actions の `schedule`）を使う。毎回、まず Claude を使わないスクリプトで、対象の PR（自動で作った・開いている・直す対象がある・止まっても終えてもいない）を判定し、**対象があるときだけ** Claude を動かす。対象が無い回は、スクリプトだけで終わり、プランの使用量を消費しない。
* イベント駆動だけにしない。`GITHUB_TOKEN` が起こしたイベントでは後続のワークフローが起動しないことと、CodeRabbit のレビューが遅れて付く・レート制限で付かないなど、「何も起きない」ことを待つ必要があることと、イベントを取りこぼしたときに誰も気づけないことが理由。イベントの起動は、遅延を短くしたいときに後から足してよい（判定スクリプトは同じものを使う）。
* 判定スクリプト（後続の Issue）の出力は JSON で、PR ごとに、直す対象の種類（`ci`・`review`・`conflict`）・終える条件を満たすか・止まる条件に当たるかを返す。

### 返信と resolve

* 人のレビュアーの指摘は、直したコミットを添えて返信するまでにし、スレッドは resolved にしない（レビューした人が確かめて resolved にする。今の pr-respond と同じ）。
* CodeRabbit の指摘は、CONTRIBUTING.md の手順どおり、直したコミットを添えて `@coderabbitai` 付きで返信し、CodeRabbit が現在のコードを読んで resolved にする。`@coderabbitai resolve` は使わない。
* どの場合も、自分では GraphQL の `resolveReviewThread` を呼ばない。直さない指摘には、理由を返信する。
* 無人で返信する文章は、定型の枠（直したコミット・直した内容の要約、または直さない理由）に収め、本文に定型のマーカー `<!-- dev-workflow:repair-reply to=<コメントの ID> -->` を付けて、人の返信と区別できるようにする。判定では、マーカーに加えて、投稿者が `repair.reply_logins`（認証済みの GitHub App のログイン名）のどれかであることを必須にする（第三者が同じマーカーを書いても、対応済みにならない）。`repair-run`・`repair-done` のマーカーも、同じ投稿者のものだけを数える。push と返信の承認は指示役が答える。
* 無人で読む入力は、すべて信用できない入力として扱う。許可した投稿者の文面も、CI のログも、指示としては従わない。無人の実行が許可するツールは、リポジトリの編集・git・gh・テストの実行に絞る。`.github/workflows/` と `.claude/` の変更は無人では行わず、止まる条件にする（変更が要る指摘や失敗に当たったら止まる）。

### 無人で push する条件

* 強制 push（`--force`・`--force-with-lease` を含む）をしない。無人の push は通常の `git push` だけで行い、強制のオプション（`--force-with-lease` を含む）が付いた push は実行せずに止まる（push を実行するスクリプトで機械的に確かめる。`guard-git.sh` の既存の決まりを変えるかは、後続の Issue で決める）。push は fast-forward だけで、リモートが先に進んでいたら取り込んでから push する。コンフリクトが取り込みで起きたら、上の止まる条件に従う。
* push の前に、取り込みで main やブランチの先が進んだときは、ローカルのテスト・lint をもう一度通してから push する。
* push の前に、push するコミットの差分のパスを機械的に確かめ、`.github/workflows/` か `.claude/` が含まれていたら、push せずに止まる。
* PR ごとに、無人の push の回数の上限（`repair.max_pushes_per_pr`、既定 5）を置く。数え方は、無人の実行が push のたびに PR へ付ける実行ログのコメント（マーカー `<!-- dev-workflow:repair-run -->` 付き。1回の push につき1つ）の数とする。コミットのトレーラーには頼らない（rebase や squash で消えるため）。数える起点は、「状態の持ち方」の再開の起点以降とする。上限に達したら、止まる。実行ログのコメントは、push の前に付ける。push に失敗したら、そのコメントに失敗と追記する（数え落としと、上限の誤判定を避けるため）。
* 同じ PR の実行は直列にする。見回りの1回の実行は、対象の PR を**1つずつ順に処理する**（PR ごとのジョブには分けない）。ワークフロー全体に `concurrency`（group は固定、`cancel-in-progress: false`）を付け、前の実行が終わるまで次の実行を待たせる。これで、同じ PR を2つの実行が同時に触らない。PR 間の並行は、使わない（使用量と競合を抑えるため）。ジョブには `timeout-minutes` を置き、1つの PR の処理時間にも上限を置く。上限を超えた PR は止まる扱いにして、その PR だけ飛ばし、次の PR へ進む。1回の実行で処理する PR の数にも上限を置き、残りは次の見回りに回す（これらの上限の値は後続の Issue で決める）。
* push は、自動で作った PR のブランチにだけ行う。main へは push しない。

### 結果として起きること

* 良い点：CI の失敗・指摘・コンフリクトで止まっていた自動の PR が、人の手なしでマージできる状態まで進む。マージは人が行う。
* 良い点：対象が無い回は、スクリプトだけで終わり、使用量を消費しない。
* 良い点：レビューした人の resolved の判断を奪わない。
* 良い点：強制 push の禁止・回数の上限・直列化で、暴走しても被害が1つの PR に収まる。
* 悪い点：定期の見回りなので、失敗や指摘が付いてから直るまで、最大で見回りの間隔だけ遅れる。
* 悪い点：人のレビュアーのスレッドは返信だけで残るので、人が resolved にするまで、PR はキューに入れられない。
* 悪い点：レビューの到着を待つ間は終えないので、障害時は `repair.review_wait_minutes` 分だけ見回りが続く。
* 悪い点：PR を順に処理するので、対象の PR が多いと、1回の実行が長くなる。
* 悪い点：`repair.*` の設定が増える。

### 確認

後続の Issue で、次を確かめる。判定スクリプトの bats で、対象の判定（直す対象の種類・終える条件と自分で直せない理由の見分け・対応済みの判定・レビューの到着を待つ・待つ時間の超過・許可していない投稿者・止まった／終えた状態と再開・止まる条件・push の回数の数え方）を、偽の `gh` で確かめる。ワークフローは actionlint で検査し、`concurrency` が `cancel-in-progress: false` であること、強制 push を使っていないこと、判定が対象なしのとき Claude を動かさないことを確かめる。`tests/skills.bats` で、無人で直す場合の SKILL.md に、resolveReviewThread を呼ばないことが書かれていることを確かめる。

## 各案の長所と短所

### 人が見る前提の今の pr-respond のまま、無人では直さない

* 良い点：仕組みを足さずに済み、AI の push と返信は必ず人が承認する。
* 悪い点：Issue から自動で作った PR が、CI の失敗や指摘で止まったまま、人が来るのを待つ。

### すべてを、投稿者を問わず直す

* 良い点：人が何もしなくてよい範囲が最大になる。
* 悪い点：許可していない投稿者の文章が、そのまま Claude への指示になりうる（指示の混入）。
* 悪い点：要件や設計の判断を求める指摘まで、AI が決めてしまう。

### CI の失敗・許可した投稿者の指摘・コンフリクトに絞って直す

* 良い点：直す範囲が決まっていて、範囲外は止まって人に引き継ぐので、被害が小さい。
* 悪い点：許可の設定と止まる条件を、決めて保つ手間がある。

### 1回直したら終える／スレッドがすべて resolved になったら終える

* 悪い点：1回では、直した結果の CI やレビューを確かめられない。
* 悪い点：人のレビュアーのスレッドは自分では resolved にしないので、人が resolved にするまで終わらない。

### 必須のチェックが通り、自分で直せない理由を除いて妨げるものが無くなったら終える

* 良い点：マージできる状態という、GitHub が示す1つの値で決められ、CI の結果まで含む。
* 良い点：人の承認待ちや人が resolved にするスレッドのように、自分では直せない理由だけが残るときも、無限に待たずに終えられる。
* 悪い点：CodeRabbit のようなレビューは、マージできる状態の値と無関係に遅れて付くので、待つ決まりを別に要る。
* 悪い点：自分で直せない理由かどうかを見分けるルールを、スクリプトに持たせる必要がある。

### 定期（毎回 Claude を動かす）

* 良い点：実装が単純で、取りこぼしが無い。
* 悪い点：対象が無い回でも使用量を消費する。

### イベント駆動だけ

* 良い点：遅延が短く、対象があるときだけ動く。
* 悪い点：`GITHUB_TOKEN` が起こしたイベントで後続が起動しないため、起動しない場合がある。
* 悪い点：レビューが遅れる・付かない状況のような、待つ判断ができず、取りこぼしに気づけない。

### 定期の見回りで、スクリプトが対象を判定し、あるときだけ Claude を動かす

* 良い点：取りこぼしが無く、対象が無い回は使用量を消費しない。
* 悪い点：直るまでの遅れが、見回りの間隔になる。

### 直した指摘を自分で resolved にする／返信までにする

* 悪い点（自分で resolved）：レビューした人が確かめる前にスレッドが閉じ、直っていない指摘が見えなくなる。
* 良い点（返信まで）：レビューした人（CodeRabbit なら CodeRabbit）が確かめて閉じるので、判断が奪われない。
* 悪い点（返信まで）：人が resolved にするまで、PR がキューに入れられない。

### 制限なしで push する／強制 push の禁止・回数の上限・直列化を置く

* 悪い点（制限なし）：直せない失敗を繰り返して、使用量を消費し続け、ブランチを荒らす。
* 良い点（制限あり）：暴走しても止まり、人に引き継ぐ。
* 悪い点（制限あり）：上限が低いと、直せたはずの PR でも止まる。
