# branch-update は、衝突を直す前に、両立できると判断した衝突も含めて直し方の方針の確認を取る

## 背景と課題

branch-update は、衝突したとき、両側の意図を両立できると AI が判断した衝突を、ユーザーに確かめずに直して、取り込みのコミットまで作っていた。聞くのは、どちらを採るか AI が判断できない衝突だけだった。ユーザーが直し方を見られるのは push の前の確認だけで、そのときには直したコミットが既にできていて、直し方を選び直すには取り込みをやり直すことになる。#236（#219 の PR）で main を2回取り込んだときも、README・設計書・tests/common.bats の衝突を、方針を確かめずに直して進めた。

[000064](000064-confirmation-policy.md) は、確認を取るのを、AI が決めた内容を GitHub に残す操作と、スクリプトが安全を確かめていない取り消しにくい操作の前だけにしている。衝突を直すのは手元の作業で、push の前の確認もあるので、この線引きでは確認は要らないことになる。両立できるかを AI に任せたままでよいか。

## 判断の決め手

* 両側のどちらかの変更の意図を、ユーザーが知らないうちに落とさないこと
* 直し方を、直したコミットができる前に選び直せること
* 確認の手間を、衝突したときだけにとどめること

## 検討した案

* 今のまま、判断できない衝突だけを聞き、直し方は push の前の確認で見せる
* 衝突したら、直す前に、両立できると判断した衝突も含めて、衝突ごとの方針の確認を取る

## 判断の結果

選んだ案：「衝突したら、直す前に、両立できると判断した衝突も含めて、衝突ごとの方針の確認を取る」。理由は、両立できるかは AI の解釈で、解釈を誤ると片側の意図が黙って落ち、それが push の前の確認で見つかっても、直し方を選び直すには取り込みをやり直すことになるから。衝突は取り込みのたびに起きるものではないので、確認が増えるのは衝突したときだけで済む。

* 衝突したら、まだファイルを直さずに、衝突ごとに、ファイル、両側の変更の要点、どう直すかを AskUserQuestion で見せる。内容は質問の文と選択肢の preview にも入れる（設計書 §8）。
* 選択肢は「この方針で直す」「直し方を変える」「取り込みをやめる（merge を取り消して、取り込む前の状態に戻す）」にする。AI が判断できない衝突は、その衝突ごとに別の質問にして、同じ確認で聞く。
* 直している途中で方針のとおりに直せないと分かったら、もう一度確認を取る。確認の後に、テストの失敗などで直し方を変えたら、push の前の確認で、何をなぜ変えたかを分けて示す。
* 000064 の線引きを、branch-update の衝突の直し方についてだけ変える（[000162](000162-start-without-worktree.md) の task-start・task-finish の例外と同じ扱い）。衝突が無ければ、今までどおり push の前の確認だけを取る。

### 結果として起きること

* 良い点：直し方を、直したコミットができる前に選び直せる。両立できるという AI の判断の誤りに、直す前に気づける。
* 悪い点：衝突したときに、確認が1回（判断できない衝突が多く、1回の確認に収まらなければ、それ以上）増える。

### 確認

`tests/skills.bats` で、branch-update の手順2が、両立できると判断した衝突も含めて直す前に方針の確認を取ること、選択肢が3つあること、確認が直してコミットするより前にあること、確認の後に変えた直し方を push の前の確認で示すことを確かめる。
