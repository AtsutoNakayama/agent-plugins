# レビューの指摘に原因を添え、反映した後に再レビューし、繰り返す指摘は根本の原因から直す

## 背景と課題

review スキルは、選んだ指摘を反映してコミットしたところで終わっていた。反映した変更をもう一度レビューする手順や、何周まで回すかの決まりは無かった。#108 では、反映の後に `/code-review` をもう一度動かして新しい指摘が見つかった。

また #108 では、Lint の検査に指摘が出るたびに、その場所だけを直し続けた（除外の仕方、終了コードの扱い）。根本を見直すと、検査そのものが要らないという結論になった。最初の指摘の時点で「なぜ起きたか」を考えていれば、そこで気づけた可能性がある。

## 判断の決め手

* 反映の後に出る新しい指摘を、PR の前に見つけること
* 同じ種類の指摘を、その場所ごとに直し続けないこと
* すべての指摘で深く調べて、レビューが重くならないこと
* 直しては新しい指摘が出る往復が、止まらなくならないこと

## 検討した案

* 原因を調べる深さ
  * すべての指摘で深く調べる
  * 2段階にする：最初の周から毎回、原因を1行添えて局所か構造かを分け、深く調べるのは繰り返す指摘だけにする
* 周回の終わらせ方
  * 指摘が無くなるまで自動で回す
  * 上限（`review.max_rounds`）の周でも指摘が出たら、続けるかをユーザーに選んでもらう

## 判断の結果

選んだ案：「2段階にする」と「上限の周でも指摘が出たら、続けるかをユーザーに選んでもらう」。理由は、すべての指摘で深く調べると重くなるからと、自動で回し続けると、直しては新しい指摘が出る往復が止まらなくなるから。

* 一覧の各指摘に、最初の周から毎回「なぜ起きたか」を1行添え、その場所だけの誤り（局所）か、設計や前提の誤り（構造）かを分ける。構造の指摘には、その場所を直す案と並べて、根本を直す案（その仕組み自体が要らないかも含めて）を出す。サブエージェントは増やさない。
* 反映でコードの振る舞いが変わったら（言い換えやコメントだけなら不要）、反映したコミットの差分を、`/code-review` と当てはまる独自の観点で再レビューする。新しい指摘が無ければ終える。
* 周回の上限は `review.max_rounds`（既定 3。最初のレビューを含む）。上限の周でも指摘が出たら、「もう1周レビューする」「ここで終える」を選んでもらう。続けるなら1周ごとに同じように聞くので、4周目以降も回せる。
* 前の周と同じ場所や同じ種類の問題が、周を合わせて2回以上出たら、「繰り返し」と印を付ける。反映の前に、これまでの修正が表面的でなかったかを確かめ、根本の原因とそれを直す案を必ず示す。

### 結果として起きること

* 良い点：反映の後に入った誤りを、PR の前に見つけられる。
* 良い点：繰り返す指摘を、その場所だけの修正で済ませずに、根本から見直せる。
* `review.max_rounds` の誤りは、`review-perspectives.sh --auto` がレビューの前に検査して止める（スキルの文章ではなくスクリプトに置いたのは、反映の後ではなくレビューの前に誤りに気づけ、テストもできるため）。

### 確認

`tests/review-perspectives.bats` で `review.max_rounds` の検査を、`tests/config.bats` で既定値を確かめる。スキルの手順（原因の1行・再レビュー・繰り返しの印）は bats では確かめられないので、実際にスキルを動かして確かめる。
