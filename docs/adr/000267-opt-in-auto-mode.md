# 設定で有効にしたリポジトリでだけ、task-auto が今のスキルの確認に代わりに答え、Issue から draft の PR まで自動で進める

## 背景と課題

今のスキルは、AI が決めた内容を GitHub に残す前と、スクリプトが安全を確かめていない取り消しにくい操作の前に、AskUserQuestion で確認を取る（[ADR 000064](000064-confirmation-policy.md)）。そのほか、ワークツリーを作るか・反映するレビューの指摘・上限の周で続けるかなども、ユーザーが選ぶ。Issue を指定したら、ユーザーの承認や入力なしで PR まで進める機能を、任意で使えるようにしたい（#266）。確認を取る範囲を、どこで・どう変えるか。

## 判断の決め手

* 有効にしていないリポジトリでは、今のスキルの振る舞い（確認を取る）が変わらないこと
* 確認の線引き（ADR 000064）と、各スキルの手順を、二重に持たないこと
* AI が決めたことを、人が後から確かめられること。決めきれないときは、推し量らずに止まること
* 自動で作ったものが、人の判断なしに main に入らないこと

## 検討した案

* 確認を取る今の形のまま、自動では進めない
* 設定で、各スキルの確認そのものを止める（どのスキルも、設定を読んで確認を飛ばす）
* 設定で有効にしたときだけ、別のスキル task-auto が、今のスキルの手順をたどりながら、各スキルの確認に代わりに答える

## 判断の結果

選んだ案：「設定で有効にしたときだけ、別のスキル task-auto が、今のスキルの手順をたどりながら、各スキルの確認に代わりに答える」。理由は、今のスキルを変えずに済み（有効にしていないリポジトリでも、有効にしたリポジトリで task-auto を使わないときも、振る舞いが変わらない）、代わりに答える決まりを task-auto の1か所にまとめられるから。

* ADR 000064 は書き換えない。ADR 000064 の線引きは、今のスキルの線引きとして残し、task-auto はその例外として、有効にしたリポジトリでだけ、確認を指示役（task-auto を動かすセッション）の判断に置き換える。
* 有効にするのは設定 `auto.enabled`（既定 false）。false なら、task-auto は何もせずに止まり、今のスキルで代わりに進めることもしない。
* 保留の列（`status.hold`。[ADR 000195](000195-hold-status-column.md)）が無いリポジトリでは、始めずに止まる。止まったときに、理由を Issue にコメントして保留の列に移すことで、人に引き継ぐため。ADR 000195 では「スキルが自動でこの列へ移すことは無い」としていたが、task-auto が止まるときだけは、この列へ移す。
* 代わりに答える内容は、task-auto の SKILL.md の表（「確認の代わりに決めること」）に、スキルと手順ごとに書く。表に無い確認に当たったら止まる。
* 止まる条件（breaking ラベル・type ラベルが1つでない・「やること」や「完了条件」が無い・Issue があいまい・テストや lint が `auto.max_fix_attempts` 回直しても通らない・レビューが `review.max_rounds` の周でも指摘を出す・差分に ADR にすべき判断がある）に当たったら、それ以上進めない。スクリプトで決められるもの（ラベル・節の有無・設定）は `auto-check.sh` が決め、AI の判断は SKILL.md に書く。
* PR は必ず draft で出し（`pr-create.sh --draft`）、マージはしない（`allow_ai_merge` にかかわらず）。代わりに決めたことは、PR の本文の「自動で決めたこと」の節に書く。
* 範囲外のレビューの指摘と前からある不具合は、開いている Issue で重複を確かめてから起票する。起票の数は、1回の実行で `auto.max_new_issues`（既定 3）までにする。Story Point は空欄にする（見積もりは人が確定する）。

### 結果として起きること

* 良い点：有効にしたリポジトリでは、Issue の番号を指定するだけで、ユーザーの入力なしに draft の PR まで進む。
* 良い点：有効にしていないリポジトリと、今のスキルの振る舞いは変わらない。
* 良い点：決めたことが PR の本文か Issue のコメントに残るので、人がレビューのときに確かめられる。
* 悪い点：有効にすると、AI が書いた PR の本文・Issue のコメント・起票した Issue が、人が見る前に GitHub に残る（PR は draft で、マージは人が行う）。
* 悪い点：今のスキルに確認を足したり変えたりしたときは、task-auto の表も合わせて直す必要がある（直さなければ、表に無い確認として止まる側に倒れる）。

### 確認

`tests/auto-check.bats`・`tests/auto-hold.bats` で、進めるか・止まるかの判定と、止まるときのコメントと列の移動を確かめる。`tests/skills.bats` で、task-auto の SKILL.md に、action ごとの扱い・止まる条件・確認の代わりに決めることの表・draft で出すことが書かれていることを確かめる。eval のケース（`task-auto-disabled-does-nothing`・`task-auto-stops-on-breaking`）で、無効なら何もしないことと、止まる条件で Issue にコメントして保留の列に移すことを確かめる。

## 各案の長所と短所

### 確認を取る今の形のまま、自動では進めない

* 良い点：仕組みを足さずに済み、AI の文章は必ず人が見てから GitHub に残る。
* 悪い点：Issue を任せて待つ使い方ができない。

### 設定で、各スキルの確認そのものを止める

* 良い点：スキルを増やさずに済む。
* 悪い点：どのスキルにも「設定が有効なら確認を飛ばす」分岐が入り、確認の線引きと代わりの決め方が、スキルごとに散らばる。
* 悪い点：有効にしたリポジトリでは、人が手でスキルを使うときも確認が無くなる。

### 設定で有効にしたときだけ、別のスキル task-auto が、各スキルの確認に代わりに答える

* 良い点：今のスキルを変えずに済み、代わりに答える決まりが1か所にまとまる。
* 良い点：有効にしたリポジトリでも、人が手でスキルを使うときは、今までどおり確認を取る。
* 悪い点：今のスキルの確認が変わったときに、task-auto の表がずれうる。
