# task-auto は、レビューの上限の周の後も PR まで進め、PR を draft にせずレビューできる状態で出す

## 背景と課題

[ADR 000267](000267-opt-in-auto-mode.md) では、task-auto は、レビューが `review.max_rounds` の周でも範囲内の指摘を出したときは、反映してコミットしてから止まり、PR は必ず draft で出すとしていた。#178 を task-auto で進めたとき、上限の周でも範囲内の指摘（テストの抜け・テスト用の偽物・文書の細かい食い違い）が出て、反映してコミットした後に止まり、PR が作られなかった。反映は済み、テストとチェックも通っていたので、止めずに PR を出して、人や PR のレビューに任せたほうがよかった。

また、PR の自動レビューのツールの多くは、既定では draft の PR をレビューしない。このリポジトリでも、PR の自動レビューも、上限のときの Claude の代わりのレビュー（`.github/workflows/claude-review.yml` の見回りは draft を外す）も、draft の PR では動かない。自動で作った PR が、人が ready にするまでレビューされない（#280）。上限の周の後の扱いと、PR を出す状態を、どう決めるか。

## 判断の決め手

* 自動で作った PR が、人が操作しなくても自動のレビューを受けられること
* 反映済みでテストとチェックが通る作業を、止めて人に戻さないこと
* レビューされていない変更が、人に見える形で残ること
* 自動で作ったものが、人の判断なしに main に入らないこと

## 検討した案

* 今のまま（上限の周で止まり、PR は draft で出す）
* 上限の周の後も PR まで進めるが、PR は draft で出す
* 上限の周の後も PR まで進め、PR を draft にせず、レビューできる状態で出す

## 判断の結果

選んだ案：「上限の周の後も PR まで進め、PR を draft にせず、レビューできる状態で出す」。理由は、反映済みでテストとチェックが通る作業を止めずに済み、PR の自動レビューが人の操作なしに動き、上限の周の反映のようにレビューされていない部分は、PR の本文で人に伝えられるから。マージは今のとおり人が行うので、人の判断なしに main に入ることはない。

* レビューが `review.max_rounds` の周でも範囲内の指摘を出したときは、もう1周せずに、指摘を反映してコミットし、テストとチェックが通れば、止まらずに PR の作成へ進む。テストやチェックが通らなければ、他の場面と同じく `auto.max_fix_attempts` まで直させ、通らなければ止まる。
* 最後の反映はレビューされていないので、反映したコミットと指摘を、PR の本文の「自動で決めたこと」に「上限の周の反映（未レビュー）」として書く。無ければ「なし」と書く。
* PR は draft にせず、レビューできる状態（オープン）で出す（`pr-create.sh` に `--draft` を付けない）。`pr-create.sh` の `--draft` は、使う人のために残す。
* マージは人が行う（`allow_ai_merge` にかかわらず）。この点は ADR 000267 のまま変えない。
* ADR 000267 は書き換えない。ADR 000267 の「レビューが上限の周でも指摘を出すと止まる」と「PR は必ず draft で出す」は、この ADR が置き換える。それ以外の判断は、そのまま残る。

### 結果として起きること

* 良い点：上限の周の指摘を反映した作業も、PR まで進み、人や PR のレビューに任せられる。
* 良い点：自動で作った PR が、人が ready にしなくても、PR の自動レビューを受ける。
* 悪い点：最後の反映は、レビューされないまま PR に載る（本文に書き、PR のレビューで見てもらう）。
* 悪い点：draft でないので、人が見る前に、PR の通知やレビューが走る。マージは人が行う。

### 確認

`tests/skills.bats` で、task-auto の SKILL.md が、`--draft` を付けないこと、上限の周の後に止まらず PR へ進むこと、「上限の周の反映（未レビュー）」を本文に書くことを確かめる。eval のケース（`task-auto-stops-on-breaking`・`task-auto-disabled-does-nothing`）は、PR まで進める依頼で、止まる条件と無効のときの振る舞いを確かめる。

## 各案の長所と短所

### 今のまま

* 良い点：レビューされていない反映が、PR に載らない。
* 悪い点：反映済みでテストが通る作業が止まり、人が続きを進める必要がある。draft の PR は、人が ready にするまでレビューされない。

### 上限の周の後も PR まで進めるが、PR は draft で出す

* 良い点：人が ready にするまでレビューやマージに進まない。
* 悪い点：PR の自動レビューが動かず、人が ready にするまでレビューされない。

### 上限の周の後も PR まで進め、PR を draft にせず、レビューできる状態で出す

* 良い点：PR の自動レビューが人の操作なしに動き、最後の反映もレビューされうる。
* 悪い点：レビューされていない反映が、通常の PR に載る。
