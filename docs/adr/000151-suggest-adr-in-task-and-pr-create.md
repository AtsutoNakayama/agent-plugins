# 設計上の判断をしたときに、task-create と pr-create が ADR の作成を確認の中で提案し、断った記録は Issue の「やること」に取り消し線で残す

## 背景と課題

#107 で ADR を作れるようにしたが（adr-create）、作るのは依頼されたときだけで、判断をしたタイミングでは提案しなかった。判断をしても ADR が残らず、「なぜ」が失われる。

判断をしたときに ADR の作成を提案するなら、どこで提案するか、何を判断の基準にするか、断ったことをどう覚えて同じ判断で何度も促さないようにするか、提案そのものをどう止めるか。

## 判断の決め手

* 起票の時点で分かる判断も、実装の中で生まれた判断も拾えること
* 同じ判断で何度も促さないこと（断ったら、その Issue では再び聞かない。別の会話で PR を作るときも）
* 確認の回数を増やさないこと（[000064](000064-confirmation-policy.md)）
* 判断の基準を1か所にし、テンプレートの選び方と食い違わないこと
* 提案を止められること

## 検討した案

提案する契機：

* task-create と pr-create
* task-create・pr-create と、review の観点（ADR が要るのに無いことを指摘する）
* pr-create だけ

断った記録：

* Issue の「やること」に、取り消し線の項目として残す
* 会話の中だけで覚える
* Issue にラベル（`no-adr` など）を付ける

提案の止め方：

* 設定 `adr.suggest` を足す
* 止める手段は作らない（毎回断る）

## 判断の結果

選んだ案：「task-create と pr-create」「やることに取り消し線で残す」「設定 `adr.suggest` を足す」。理由は、起票の時点の判断と実装の中の判断を、それぞれ確認の質問の中で1回ずつ拾え、断った記録が Issue に残るので会話をまたいでも同じ判断で促さず、既にある決まり（取り消し線の項目は取りやめた項目）をそのまま使えるから。

* 基準は adr-create の SKILL.md の「ADR にすべき判断」の節を正本にする。他の案と比べて選んだ判断・破壊的変更・元に戻しにくい判断は ADR にし（`full`）、どれにも当たらず記録しておけば足りる判断は、ユーザーが残すと決めたときだけ ADR にする（`minimal`）。task-create・pr-create は基準を写さず、この節を読んで判断する。
* task-create は、Issue に判断が含まれれば、「やること」に `- [ ] <判断>を ADR に残す` を足した下書きを、起票の確認の中で見せる。断れば、その項目を取り消し線にして起票する。
* pr-create は、差分に判断があり、その Issue の ADR（`adr-list.sh --issue`。front matter の `issue` で探す）も、Issue のチェックリストの ADR の項目も無ければ、PR の確認の中で「ADR を作ってから PR を作る」を選べるようにする。断れば（そのまま PR を作れば）、`pr-create.sh --add-task` が、最初のチェックリストの項目がある節（ふつうは「やること」）に取り消し線の項目を足す。
* ADR の項目は、Issue のチェックリスト（「やること」に限らない）の項目のうち、文に「ADR に残す」を含むもの（ADR を話題にしているだけの項目は含めない）。ADR の項目があれば（取り消し線の有無を問わない）、その Issue では提案しない。取り消し線もチェックも無い ADR の項目が残っていて ADR がまだ無ければ、提案ではなく、そのことを伝える。
* 提案するかは、これらの状態の組み合わせで決まるので、`adr-list.sh --issue` が Issue の本文も読んで `proposal` に出す。AI が判断するのは、ADR の項目が無いとき（`judge`）に、差分に判断があるかだけにする。
* 設定 `adr.suggest`（既定 true）を false にすると、提案しない。

### 結果として起きること

* 良い点：判断を含む Issue と PR で、ADR を残すかを必ず一度考える。確認の回数は増えない。
* 良い点：断った記録が Issue に見える形で残り、後から読む人にも、ADR を残さないと決めたことが分かる。
* 悪い点：断った Issue の「やること」に、取り消し線の項目が1行増える。
* 悪い点：判断を含むかは AI が差分と Issue から判断するので、見落としも、要らない提案も起こりうる。迷うときは提案し（断れるので）、繰り返し要らない提案が出るリポジトリでは `adr.suggest` で止める。
* 悪い点：PR を出す前の review では ADR の不足を指摘しないので、PR を作るときに初めて提案される。

### 確認

`tests/adr-list.bats`（front matter の `issue` で探す、`adr.suggest` の既定と検査）、`tests/pr-create.bats`（`--add-task` の位置・字下げ・改行、同じ項目を重ねない）、`tests/skills.bats`（基準の正本が adr-create にあり、task-create・pr-create がそれを読んで、確認の質問の中で提案する）で確かめる。

## 各案の長所と短所

### task-create と pr-create

* 良い点：起票の時点で分かる判断は「やること」に載り、作業に含まれる。実装の中で生まれた判断は PR を作るときに拾える。
* 良い点：どちらも既にある確認の質問の中で聞ける。
* 悪い点：起票の時点で提案を受けた判断を、PR で改めて確かめることはしない（「やること」の項目に任せる）。

### task-create・pr-create と、review の観点

* 良い点：PR を出す前のレビューで、ADR の不足に気づける。
* 悪い点：pr-create と同じことを2回聞くことになる。レビューは何周も回し、「もう一度レビューして」でも動くので、断っても観点が同じ指摘を出し続ける（観点は Issue の断った記録を読まない）。

### pr-create だけ

* 良い点：判断が差分で具体的になってから聞ける。
* 悪い点：起票の時点で分かっている判断が「やること」に載らず、ADR が作業の範囲として見えない。

### 断った記録を、やることに取り消し線で残す

* 良い点：取り消し線の項目は、pr-create が取りやめた項目として扱う決まりが既にあり、チェックも付けない。
* 良い点：会話をまたいでも、別の人が PR を作っても、同じ判断で促さない。
* 悪い点：PR を作るときに断ったら、Issue の本文を書き換える（pr-create の確認の中で、何を足すかを見せてから行う）。

### 断った記録を、会話の中だけで覚える

* 良い点：Issue に何も書かない。
* 悪い点：別の会話で PR を作るときに、また聞く。

### 断った記録を、Issue のラベルで残す

* 良い点：一覧で絞り込める。
* 悪い点：ラベルの定義（`labels.json`）を変え、既にあるリポジトリでは `setup-labels.sh` で足し直す手間がかかる。判断ごとではなく Issue ごとにしか表せない。

### 設定 `adr.suggest` を足す

* 良い点：ADR を使わないリポジトリや、提案が要らない人が止められる。層で上書きできるので、自分だけ止めることもできる。
* 悪い点：設定が1つ増える。

### 止める手段は作らない

* 良い点：設定が増えない。
* 悪い点：ADR を使わないリポジトリでも、判断のたびに断る手間がかかる。
