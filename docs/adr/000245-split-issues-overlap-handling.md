# 分けた Issue が既にある Issue と重なるときは、重なった Issue だけを対象にし、問いは分け方を見せる確認の中で1回にまとめる

## 背景と課題

task-create は、下書きの前に依頼全体と開いている Issue を照らして重複と親の候補を探すが、分けた Issue（分け方の案と、Story Point 21/34 の分割）は照らさなかった。依頼全体とは重ならなくても、分けた一部が既にある Issue と重なることがある。

#169 のレビューでは、分けた Issue ごとに同じ決まりで照らす案を試し、次の継ぎ目が出て外した。

* 重なりの質問で「既にある Issue で進める」を選ぶと、その Issue だけでなく全体が止まる
* 分けた Issue の親の候補が、案の親子の木とぶつかる（Issue の親は1つだけ）
* 分けた Issue ごとに質問すると、問いが多くなる

分けた Issue を照らすとき、重なった Issue の扱い、親の候補と案の木のぶつかり、問いの出し方をどう決めるか。

## 判断の決め手

* 重なった Issue があっても、残りの分けた Issue の起票を止めないこと
* Issue の親は1つだけなので、案の親子の木を壊さないこと
* 確認の質問を増やさないこと（設計書 §8）

## 検討した案

* 重なった分けた Issue だけを対象にし、問いは分け方を見せる確認の中で1回にまとめる
* 分けた Issue ごとに、依頼全体と同じ決まりで質問する（#169 で試して外した案）
* 分けた Issue は照らさず、重なりは起票の後に人が気づくのに任せる

## 判断の結果

選んだ案：「重なった分けた Issue だけを対象にし、問いは分け方を見せる確認の中で1回にまとめる」。理由は、決め手の3つをすべて満たす唯一の案だから。

決めたことは次のとおり。

* 照らす時点：分け方の案は手順2、Story Point 21/34 の分割は手順3で分割を提案するとき（手順2の時点では分割案が無いため）。どちらも、手順2で読んだ開いている Issue の一覧を使い、読み直さない
* 扱いは3つ：「外す」（起票せず、既にある Issue を使う）、「重ならない部分だけにする」、「そのまま起票する」。どれを選んでも、重なっていない分けた Issue の起票は止めない
* 外した Issue に依存する子は、依存先を既にある Issue に付け替えて確認で伝える
* 親：分けた Issue の親は案の親子の木で決め、既にある Issue を親の候補として足さない。例外として、木の一番上の親を外したときは、重なる既にある Issue を親にする（その Issue がサブ Issue を持つ・既に別の親を持つ・深さの上限を超えるときは、子を親なしで起票して確認で伝える）。木の途中の親を外したときは、子の親を外した親のさらに上の親にする
* 問い：分け方を見せる確認（21/34 の分割では分割の案を見せる確認）の中で1回にまとめ、「この内容で起票する」の代わりに3択を並べて選択肢を4つ以内に収める（21/34 の分割では、「分割する」を3つの扱いごとの3択に置き換え、「このまま設定する」と合わせて4つにする）。Issue ごとに扱いを変えたいときは「その他」で受ける

### 結果として起きること

* 良い点：分けた Issue の一部が重なっても、全体は止まらず、問いも1回で済む
* 悪い点：Issue ごとに扱いを変えるには「その他」で答える必要があり、確認が1回で終わらないことがある
* 悪い点：親にできるかの判断が SKILL.md の文章にあり、スクリプトでは確かめていない（#326 で扱う）

### 確認

`tests/skills.bats` が、SKILL.md の手順2・3に、照らす時点・3つの扱い・親の扱い・問いを1回にまとめることが書かれているかを確かめる。
