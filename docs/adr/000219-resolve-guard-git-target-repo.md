# guard-git は、操作の対象のリポジトリを確かめて求め、導入したかの判定と設定の読み込みに同じ対象を使う

## 背景と課題

フック guard-git は、導入したリポジトリ（[ADR 000219](000219-limit-scope-to-set-up-repos.md)）でだけ、base_branch の上のコミットや強制 push を止める。そのためには、コマンドが操作するリポジトリを知る必要がある。git は、`cd`・`git -C` のほかに、`--git-dir`・`--work-tree` のオプションや、`GIT_DIR`・`GIT_WORK_TREE`・`GIT_COMMON_DIR` の環境変数でも操作の対象を変えられ、`.git` の中や bare リポジトリでも動く。また、サブモジュールや `--separate-git-dir` で作ったリポジトリは、git のディレクトリが作業ツリーの直下の `.git` ではない。対象を誤ると、導入したリポジトリの守りが外れるか、導入していないリポジトリまで止めるか、別のリポジトリの base_branch で判断する。#219 のローカルのレビューでは、対象の求め方への同じ種類の指摘が5回続き、下の案を順に試した。

## 判断の決め手

* 導入したリポジトリは、どの書き方で指しても守ること
* 導入していないリポジトリは、どの書き方で指しても止めないこと（#219 の方針）
* 導入したかの判定と、設定（base_branch・branch.pattern）を読むリポジトリが同じであること
* 対象が分からないときは、止める側に倒すこと

## 検討した案

* 対象のリポジトリ（`--git-common-dir`）を求め、ルートの候補を、その場所で git が同じリポジトリを見つけるかで確かめる。確かめられなければ、HEAD にコミットされたチームの設定で判断する
* `git rev-parse --show-toplevel` をルートとする
* リポジトリ（`--git-common-dir`）の親をルートとする
* オプションや環境変数があるときは、ルートが分からないものとして、導入したかを問わず調べる

## 判断の結果

選んだ案：「ルートの候補を確かめ、確かめられなければ HEAD にコミットされたチームの設定で判断する」。理由は、決め手をすべて満たすのはこの案だけだったため。

* コマンドごとに1回、コマンドと同じディレクトリ・オプション・環境変数で `git rev-parse --git-common-dir` を実行して、対象のリポジトリを求める（git は1回だけ起動する）。オプションと環境変数の値の先頭の `~`・`$HOME` は、シェルが展開する前の文字列を見ているので、自分で展開する。
* オプションも環境変数も無ければ、`--show-toplevel` がそのままルート。あれば、ルートの候補（`--show-toplevel` の値と、リポジトリのメインのワークツリー）を、その場所で git が同じリポジトリを見つけるかで確かめる。メインのワークツリーは、リポジトリの親か core.worktree（サブモジュール）を、同じように確かめて求める（`lib/common.sh` の `dw_repo_main_root`。task-start・cleanup が使う `dw_main_root` も同じ確かめ方にした）。
* ルートが分かれば、そこ（かメインのワークツリー）にチームの設定があるかで導入したかを判定し、設定もそこから読む。
* ルートが分からない（bare リポジトリや、外から git のディレクトリだけで指した `--separate-git-dir` のリポジトリなど）ときは、HEAD にチームの設定がコミットされているかで判定し、base_branch もそこから読む（チームの設定が決めていなければ、ユーザーの層の値。導入したリポジトリにはユーザーの層も効くため）。ワークツリー（`git worktree add`）の git のディレクトリを指したときも、同じリポジトリの別のワークツリーと見分けられないので、ルートが分からないものとする。ブランチ名は、どの規約で確かめるか分からないので確かめない（警告だけなので、止める側に倒さない）。
* git がリポジトリを見つけられないとき（ディレクトリが分からない `cd -` の後など）だけ、導入したものとみなし、ユーザーの層の設定（無ければプラグインの既定）で調べる。今のディレクトリのリポジトリの設定は、対象と違うことがあるので読まない。

### 結果として起きること

* 良い点：オプション・環境変数・`.git` の中・サブモジュールでも、導入したかと base_branch を、操作の対象のリポジトリで判断できる。
* 良い点：関係のない bare のミラーで `git push --mirror` をしても止めず、導入したリポジトリのミラーは守る。
* 悪い点：git の操作のたびに、フックが git を数回多く実行する。
* 悪い点：ルートが分からず、HEAD のブランチがチームの設定をコミットする前に作ったものだと、導入したリポジトリでも導入していないとみなす。
* 良い点：bare リポジトリ＋ワークツリーの配置（`<ルート>/.bare` と、それを指す `<ルート>/.git` のファイル）でも、task-start・cleanup の `dw_main_root` は `<ルート>` を返す。
* 悪い点：`--separate-git-dir` のリポジトリのワークツリーからは、メインのワークツリーが分からない。そのワークツリーにチームの設定が無ければ導入していないとみなし、task-start・cleanup は「メインのワークツリーが分かりません」で止まる（推測した別の場所でワークツリーを作り・消すより安全なため）。
* コマンドの文字列を簡易に解析するだけなのは変わらず、`sh -c` や git の別名、展開前の `$HOME` などを通すと見逃す。最後の守りは GitHub のルールセット。

### 確認

`tests/guard-git.bats` で、配置ごと（普通のリポジトリ・`.git` の中・`--git-dir`・`GIT_DIR`・`GIT_WORK_TREE`・`--separate-git-dir`・サブモジュールとそのワークツリー・bare のミラー）に、導入したかの判定と base_branch・ブランチ名の規約を確かめる。`tests/common.bats` で、`dw_main_root`・`dw_repo_main_root` を確かめる。

## 各案の長所と短所

### ルートの候補を確かめ、確かめられなければ HEAD にコミットされたチームの設定で判断する

* 良い点：オプション・環境変数・`.git` の中・サブモジュールでも、同じ対象を求められる。
* 良い点：導入していないリポジトリを止めず、導入したリポジトリの守りも外さない。
* 悪い点：処理が多く、git の呼び出しが増える。

### `git rev-parse --show-toplevel` をルートとする

* 良い点：オプションも環境変数も無いときは正しく、速い。
* 悪い点：`--git-dir`・`GIT_DIR` だけを付けると、今のディレクトリを返す。導入していないディレクトリから、導入したリポジトリを指すと守りが外れる。

### リポジトリ（`--git-common-dir`）の親をルートとする

* 良い点：`--git-dir`・`GIT_DIR`・`.git` の中でも、普通のリポジトリなら正しい。
* 悪い点：サブモジュール（`<上のリポジトリ>/.git/modules/<名前>`）や `--separate-git-dir` のリポジトリでは、別の場所になる。導入したサブモジュールで、`GIT_WORK_TREE` を付けたコミットを止められなかった。

### オプションや環境変数があるときは、導入したかを問わず調べる

* 良い点：守りは外れない。
* 悪い点：導入していないリポジトリまで止める（#219 の方針に反する）。
* 悪い点：base_branch を読むリポジトリが決まらない。今のディレクトリの設定（とユーザーの層）で調べると、別のリポジトリの base_branch で判断し、base_branch が develop のリポジトリの守りが外れた。
