# 今は着手できない Issue を、任意の役割 hold の列（保留の列）に置いて、task-next の候補から外す

## 背景と課題

Todo には、今は着手できない Issue も並び、task-next の候補になる。外の条件を待つものが当たる（例：#160 は CodeRabbit の試用期間が終わるまで着手できない）。本文の「依存」は Issue の番号しか読めないので、Issue でない条件では待ちにできない。利用者が Project に列を足し、task-status で移せば候補から外せる。ただ、この使い方は仕組みとして案内されておらず、移した後に Todo に戻し忘れやすい。今は着手できない Issue を、どう候補から外すか。

## 判断の決め手

* Issue でない条件（期間・外の出来事）を待つ Issue も、候補から外せること
* 外した Issue を、条件がそろったときに Todo に戻し忘れないこと
* 使わないリポジトリでは、動きが変わらないこと

## 検討した案

* 本文の「依存」に書いて待ちにする
* 利用者が足した列へ task-status で移す（今の仕組みのまま）
* 設定に任意の役割 hold を足し、その列（保留の列）を task-next が読む

## 判断の結果

選んだ案：「設定に任意の役割 hold を足し、その列（保留の列）を task-next が読む」。Issue でない条件も扱え、task-next が保留の Issue を毎回伝えるので戻し忘れにくく、既定（null）では動きが変わらないから。

* `status.hold` は既定 null。repo-setup で作るかを聞き、作るなら列名を `.claude/dev-workflow/config.json` に書いて、Status 列に足す（`setup-project.sh --hold-column`）。
* スキルが自動でこの列へ移すことは無い。移すのも Todo に戻すのも、利用者が task-status で行う。
* task-next（`next-tasks.sh`）は、この列の Issue を候補に入れず、件数と番号を伝え、条件がそろったものを Todo に戻すよう案内する。
* Iteration（別の Issue）とは独立に使える形にする。列は「今は着手できない」という状態、Iteration は「いつやるか」という計画で、軸が違うため。
* ほかの役割の列と同じ名前にはできない。同じだと、保留の Issue が Todo や着手中にも数えられる。

### 結果として起きること

* 良い点：Issue でない条件を待つ Issue を候補から外せ、外したことが task-next のたびに見える。
* 良い点：設定しないリポジトリでは、今までどおりに動く。
* 悪い点：列に移すのも戻すのも手で行うので、条件がそろったかは人が判断する。
* 悪い点：役割の名前 `hold` が列名より先に解釈されるので、hold を設定していないリポジトリで、利用者が足した `Hold` の列へ `hold`（小文字）と指定しても移らない。列のとおりの大文字・小文字で指定する。

### 確認

`tests/setup-project.bats` で、保留の列を Todo の後ろに足すこと・`--hold-column` で設定に書くこと・ほかの役割と同じ名前なら止まることを確かめる。`tests/next-tasks.bats` で、保留の列の Issue が候補に入らず `hold` に出ること・設定しなければ動きが変わらないことを確かめる。

## 各案の長所と短所

### 本文の「依存」に書いて待ちにする

* 良い点：仕組みを足さずに済む。
* 悪い点：「依存」は Issue の番号しか読めないので、Issue でない条件では待ちにできない。

### 利用者が足した列へ task-status で移す（今の仕組みのまま）

* 良い点：仕組みを足さずに済み、今でも候補から外せる。
* 悪い点：仕組みとして案内されておらず、task-next にも出ないので、移した後に Todo に戻し忘れやすい。

### 設定に任意の役割 hold を足し、その列（保留の列）を task-next が読む

* 良い点：Issue でない条件も扱え、task-next が保留の Issue を伝えるので戻し忘れにくい。
* 良い点：既定 null なので、使わないリポジトリでは動きが変わらない。
* 悪い点：設定の役割と、setup・task-next・task-status の対応が増える。
