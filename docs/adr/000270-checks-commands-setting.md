# テストとチェックのコマンドは、設定 checks.commands → リポジトリからの推測 → ユーザーに聞いて保存、の順で決める

## 背景と課題

branch-update（手順3）と pr-respond は、実行するテストとチェックを「リポジトリの規約（CONTRIBUTING.md など）」から読み取り、review は「関係するテストや lint」と書くだけで、何を実行するかを決めていなかった。このため、何を実行するかが、人向けの自由な文書の書き方と Claude の読み取りでぶれた。CONTRIBUTING.md が無いリポジトリでは、package.json・Makefile・CI などの手がかりがあっても使わず、毎回ユーザーに聞き、答えも残らなかった。プラグインは、CONTRIBUTING.md が無いリポジトリでも単体で使える必要がある（#270）。テストとチェックのコマンドを、どう決めるか。

## 判断の決め手

* CONTRIBUTING.md が無いリポジトリでも、プラグイン単体で実行するコマンドを決められること
* 3つのスキルで、決め方が同じであること（スキルごとに文章を書き分けて、ずれないこと）
* 一度ユーザーに聞いたら、次からは聞かないこと
* 設定を書いていないリポジトリで、今の振る舞い（規約を読む）が急に変わらないこと

## 検討した案

* 今のまま、スキルが CONTRIBUTING.md などの規約を読み取る
* 設定 `checks.commands` だけで決め、無ければ必ずユーザーに聞く
* 設定 `checks.commands` → リポジトリからの推測 → ユーザーに聞いて保存、の順で決める

## 判断の結果

選んだ案：「設定 `checks.commands` → リポジトリからの推測 → ユーザーに聞いて保存、の順で決める」。理由は、設定があれば決め方がぶれず、設定が無くても package.json などの手がかりで候補が出て、聞いた答えを保存すれば次からは聞かずに済むから。

* 設定 `checks.commands` は、コマンドの配列（既定 null）。配列なら、その順に実行する。空の配列は「実行するものが無い」と決めてあること。null は、まだ決めていないこと。
* 推測の手がかりは `checks-commands.sh` が JSON で出す（CONTRIBUTING.md のパス・package.json の scripts・Makefile のターゲット・CI の設定ファイル・Cargo.toml や go.mod などのファイル）。手がかりから実行するコマンドを組み立てるのは AI が行う（リポジトリごとに書き方が違い、スクリプトで決めきれないため）。設定を書いたリポジトリでは、手がかりを調べない。
* 推測できなければ、ユーザーに聞き、保存するかも聞く。保存は `checks-commands.sh --save --scope <local・team>` で行う。自分だけなら `config.local.json`、チームで共有するなら `config.json`。
* branch-update（手順3）・pr-respond（手順5）・review（手順6）は、この決め方で実行するコマンドを決める。

### 結果として起きること

* 良い点：`checks.commands` を書いたリポジトリでは、3つのスキルが同じコマンドを実行する。
* 良い点：CONTRIBUTING.md が無くても、実行するコマンドの候補が出る。
* 良い点：聞いた答えが設定に残り、次からは聞かれない。
* 悪い点：設定を書かなければ、推測は毎回 AI が行うので、ぶれる余地が残る（設定に書けば解消する）。
* 悪い点：`checks.commands` の内容と CONTRIBUTING.md の文章が二重になりうる（このリポジトリのように、CONTRIBUTING.md を正本にしたいときは、設定にそのコマンドを書いて合わせる）。

### 確認

`tests/checks-commands.bats` で、設定の読み取り（層の優先・不正な値で止まる）、手がかりの出力、保存（team・local・`--none`）、引数の誤りを確かめる。`tests/skills.bats` で、3つの SKILL.md が `checks-commands.sh`・`checks.commands`・`--save` に触れていることを確かめる。

## 各案の長所と短所

### 今のまま、スキルが CONTRIBUTING.md などの規約を読み取る

* 良い点：仕組みを足さずに済む。
* 悪い点：規約の書き方と読み取りでぶれる。
* 悪い点：規約が無いリポジトリでは、手がかりがあっても使わず、毎回聞く。

### 設定 `checks.commands` だけで決め、無ければ必ずユーザーに聞く

* 良い点：決め方が単純で、ぶれない。
* 悪い点：設定を書くまで、毎回聞かれる。package.json などの手がかりがあっても使わない。

### 設定 → 推測 → 聞いて保存

* 良い点：上の2案の悪い点を避けられる。
* 悪い点：決め方の段階が増える。
