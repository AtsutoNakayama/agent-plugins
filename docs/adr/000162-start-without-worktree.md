# リポジトリを変えないタスクはワークツリーを作らずに着手し、PR の代わりに task-finish が確認を取って Issue を閉じる

## 背景と課題

#153（過去の設計判断を洗い出す作業）では、ファイルを1つも変えないのに、task-start がブランチとワークツリーを作り、終わってから `cleanup.sh --abandon` で捨てた。調査・洗い出し・Issue の整理のように、リポジトリを変えないタスクには、ワークツリーもブランチも PR も要らない。

ワークツリーを作らずに着手するなら、作るかどうかをどう決め、PR の無いタスクをどう終えるか。これまでの決まりでは、[000064](000064-confirmation-policy.md) が task-start・task-finish は実行の確認を取らないことを、[000065](000065-issue-cancel-outcomes.md) が task-finish は Issue を閉じないこと（完了は PR のマージで閉じる）を決めていた。PR の無いタスクでは、どちらもそのままでは成り立たない。

## 判断の決め手

* ファイルを変えないタスクで、作って捨てるだけのワークツリーとブランチを作らないこと
* ファイルを変えるタスクを、base_branch の上で作業させないこと（作るかの判断を誤らないこと）
* 別の Issue の作業や、まだ終わっていない作業を、片付けや Issue を閉じる操作で失わないこと
* PR の無いタスクも、スキルで終えられること

## 検討した案

作るかの決め方：

* type ラベルで決める
* Issue の本文から AI が判断し、ユーザーが選ぶ

終えるときの作業のブランチの探し方：

* 名前と、Issue に紐付く PR の両方から探して片付ける
* 名前だけで広めに探して片付ける
* 確かなブランチ（branch.pattern に合い、番号が一致する）だけを片付け、名前が似ているブランチと PR のブランチは候補として見せて聞く

PR の無いタスクの終え方：

* task-finish は閉じ方を案内するだけにする（000065 のまま）
* task-finish が確認を取って completed で閉じる

## 判断の結果

選んだ案：「本文から AI が判断してユーザーが選ぶ」「確かなブランチだけを片付け、候補は見せて聞く」「task-finish が確認を取って completed で閉じる」。理由は、作るかどうかは type ラベルでは分からず、作業のブランチかどうかも名前の付け方しだいで外れるので、自動で決めてよいのは確かな場合だけにし、ほかは人が決めるのが、作業を失わずにすむ唯一の形だから。

* task-start は、Issue の本文（やること・完了条件・変更するファイル・領域）から判断し、「ワークツリーを作って着手する」「作らずに着手する」を、判断と理由を添えて提案し、ユーザーが選ぶ。依頼の文章で既に決まっていれば聞かない。000064 の「task-start は確認を取らない」を、この選択についてだけ変える（割り当てと列の移動は、今までどおり確認しない）。
* 作らないときは `task-start.sh --no-worktree` で、割り当てと列の移動だけを行う。Issue に既にブランチがあれば止まる。後からファイルを変えることになったら、`--slug` を付けて実行し直せばワークツリーを作れる。
* 本文の「変更するファイル・領域」の「- なし」を「ファイルを変えない」と決める。task-next は、どれとも重ならないものとして扱う（着手中でも警告しない）。
* 終えるときは（task-finish・task-cancel）、作業のブランチを `issue-branches.sh` で2つの段階に分けて探す。片付けや取りやめの対象にするのは、`branch.pattern` に合い番号が一致する確かなブランチ（先頭に 0 が付いた古い名前も含む）だけで、作業がすべてマージ済み（先端がマージ済みの PR に含まれる。`cleanup.sh` と同じ基準）のものは取りやめず、`--no-worktree` の着手も止めない。task-finish は、確かなブランチがすべてマージ済みで Issue が開いていれば、片付けた後に閉じるかを聞く。名前が似ているだけのブランチと、Issue を閉じる PR のブランチは候補として見せて聞くだけにし、自動では片付けない。
* task-finish は、ブランチが見つからなければ、Issue を閉じる PR が開いていれば閉じず、開いている子のある親の Issue も閉じない。そうでなければ、名前で探して無かったことを見せて、「完了として閉じる」「別の名前のブランチで作業した」「やめる」から選んでもらい、閉じると選ばれたら completed で閉じる。000065 の「task-finish は Issue を閉じない」を、PR の無いタスクについてだけ変える（PR のある作業は、今までどおり PR のマージで閉じる）。
* task-cancel は、ブランチが無ければ Issue を閉じるだけにする（000065 のとおり）。

### 結果として起きること

* 良い点：ファイルを変えないタスクで、作って捨てるだけのワークツリーとブランチができない。
* 良い点：別の Issue のブランチ（`Closes #17, #18` の PR のブランチや、リリース用の PR のブランチなど）を、片付けの対象にしない。
* 悪い点：着手するときと、PR の無いタスクを閉じるときに、確認がそれぞれ1回増える（000064 が避けていた手間）。作るかの判断を誤ると base_branch の上でファイルを変えるおそれがあり、決めつけて閉じると終わっていない作業の Issue を閉じるおそれがあるので、ここは人が決める。
* 悪い点：名前に `/<番号>-` を含まないブランチで作業したタスクは、名前では見つからない。task-finish は閉じる前に聞くので止められるが、task-cancel は Issue だけを閉じる。そのため、task-cancel の確認に、Issue を閉じる開いている PR を出し、閉じるかはユーザーに任せる。

### 確認

`tests/task-start.bats`（`--no-worktree`、既にブランチがあるとき）、`tests/issue-branches.bats`（確かなブランチと候補を分ける、関係の無いブランチや別の Issue のブランチを確かなブランチにしない、PR の番号では止まる）、`tests/next-tasks.bats`（「なし」の Issue）、`tests/skills.bats`（task-start がワークツリーを作るかを聞く、task-finish がブランチの見つからないときに閉じるかを聞く）で確かめる。

## 各案の長所と短所

### type ラベルで決める

* 良い点：着手のときに確認が要らない。
* 悪い点：docs の type でもファイルを変えるし、調査は type に現れないので、決められない。

### Issue の本文から AI が判断し、ユーザーが選ぶ

* 良い点：本文の項目を根拠に提案でき、判断が外れても人が直せる。
* 悪い点：着手のたびに確認が1回増える。

### 名前と、Issue に紐付く PR の両方から探して片付ける

* 良い点：規約に合わない名前のブランチも、PR があれば見つかる。
* 悪い点：`Closes #17, #18` の PR やリリース用の PR のブランチなど、別の Issue のブランチまで拾い、task-cancel が別の Issue の作業を消しうる。PR の状態（閉じた・マージ済み・フォーク）や件数の上限などの場合分けも増える。

### 名前だけで広めに探して片付ける

* 良い点：PR の場合分けが要らない。規約に合わない名前のブランチも見つかる。
* 悪い点：`backup/2024-01-15`（#2024）や `release/1-0-x`（#1）のように、名前が似ているだけの関係の無いブランチまで拾い、task-cancel が消しうる。名前に番号を含まないブランチは見つからない。

### 確かなブランチだけを片付け、名前が似ているブランチと PR のブランチは候補として見せて聞く

* 良い点：自動で片付けるのは確かなブランチだけなので、関係の無いブランチや別の Issue のブランチを消さない。候補を見せるので、規約に合わない名前のブランチも見落とさない。
* 悪い点：規約に合わない名前のブランチで作業したタスクは、片付けるたびに候補から選ぶ手間がかかる。

### task-finish は閉じ方を案内するだけにする

* 良い点：000065 の決まりのまま。task-finish が Issue を閉じる経路が増えない。
* 悪い点：PR の無いタスクを終えるのに、もう一度「閉じて」と頼む手間がかかる。

### task-finish が確認を取って completed で閉じる

* 良い点：PR の無いタスクも、task-finish の1回で終えられる。
* 悪い点：000065 の決まりに、PR の無いタスクについての例外ができる。

## 補足

* 出典：Issue #162（https://github.com/nakayama-labs/agent-plugins/issues/162）、Issue #153（https://github.com/nakayama-labs/agent-plugins/issues/153）、設計書 §4「リポジトリを変えないタスクには、ワークツリーを作らない」、§8
* 000064・000065 は置き換えない。どちらも、PR のある作業については今までどおりで、この ADR は、PR の無いタスクについてだけ例外を決める。
* 作業のブランチの探し方は、ローカルのレビューで2回変えた。最初は名前と PR の両方から探したが、別の Issue のブランチを拾って task-cancel が作業を消しうることが分かり、名前だけで広めに探す形にした。次に、名前が似ているだけの関係の無いブランチも拾うことが分かり、確かなブランチと候補の2つの段階に分けた。PR は、Issue を閉じる PR が開いていれば閉じない、という守りと、候補にだけ使う。
