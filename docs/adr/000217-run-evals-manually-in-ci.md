# スキルの振る舞いの eval は、CI では手で起動したときだけ動かし、必須のチェックにしない

## 背景と課題

スキルの振る舞いを `claude plugin eval` で Claude に実行させて確かめるケース（`plugins/dev-workflow/evals/`）を足した（#217）。手元では `tests/eval/run.sh` で動かせる。これを CI でいつ動かすか、マージやリリースを止める必須のチェックにするかを決める必要があった。

eval は bats と違い、1回の実行ごとに本物のモデルを何度も呼ぶ（ケースの数 × 実行回数 × プラグインあり・なしの2つ）。シークレット `CLAUDE_CODE_OAUTH_TOKEN` のプランの使用量を消費し、結果も毎回少し揺れる。

## 判断の決め手

* プランの使用量：変更のたびに自動で動かすと、使用量を消費し続ける
* 結果の揺れ：モデルの振る舞いは毎回少し違う。必須のチェックにすると、プラグインに問題が無くても、揺れでマージやリリースが止まることがある
* マージキューの仕組み：キューが待つのは必須のチェックだけ（[ADR 000112](000112-require-ci-on-latest-main.md)）。必須でない eval をキュー（`merge_group`）で動かしても、落ちたときにマージを止められず、結果を見るだけになる
* 必要なときに CI でも動かせること：手元の環境（bubblewrap・socat などのサンドボックスの準備）が無くても確かめられるようにしたい

## 検討した案

* Actions の画面から手で起動したときだけ動かす（`workflow_dispatch`。必須にしない）。手元でも実行できる
* スキルや共有のファイル（`scripts/`・`hooks/`・`defaults/`）を変えた PR の push で、変わったスキルのケースだけを自動で動かす（必須にしない）
* リリース PR をマージキューに入れたときだけ、前回のリリースから変わったスキルのケースを動かし、必須のチェックにする（`eval-result` を足し、ほかの PR では飛ばして成功にする）
* CI では動かさず、手元だけにする

## 判断の結果

選んだ案：「Actions の画面から手で起動したときだけ動かす」。理由は、使用量を消費するのが動かしたいときだけで済み、揺れでマージやリリースを止めることもなく、手元の準備が無くても CI で確かめられるから。必要になれば、後から自動で動かす形に足せる。

### 結果として起きること

* 良い点：PR や push で使用量を消費しない。eval の揺れで、マージキューやリリースが止まらない
* 良い点：手元にサンドボックスの準備が無くても、CI で同じ手順（`tests/eval/run.sh`）で確かめられる。結果のレポートは artifact に残る
* 悪い点：自動では動かないので、スキルを変えた PR で eval を動かすかは、変更した人に任される（CONTRIBUTING.md の「スキルの振る舞いを eval で確かめる」で、確認を取る場面などを変えたときは関係するケースを手元で動かすよう書いた）
* 悪い点：スキルの振る舞いが崩れても、マージやリリースは止まらない

### 確認

* `.github/workflows/eval.yml` の起動の条件が `workflow_dispatch` だけで、`pull_request`・`push`・`merge_group` が無いこと
* main のルールセットの必須のチェックに、eval のジョブが入っていないこと

## 各案の長所と短所

### Actions の画面から手で起動したときだけ動かす

* 良い点：使用量を消費するのは、動かしたいときだけ
* 良い点：揺れでマージやリリースが止まらない
* 良い点：手元の準備が無くても CI で動かせる
* 悪い点：動かし忘れると、振る舞いの崩れに気付かない

### スキルや共有のファイルを変えた PR の push で、変わったスキルのケースだけを自動で動かす

* 良い点：スキルを変えた PR では、動かし忘れが無い
* 良い点：変わったスキルのケースだけなので、全部を動かすより使用量が少ない
* 悪い点：PR に push するたびに使用量を消費する
* 悪い点：変わったファイルからタグを決めるスクリプトと、そのテストが要る
* どちらでもない点：必須にしないので、落ちてもマージは止まらない

### リリース PR をマージキューに入れたときだけ動かし、必須のチェックにする

* 良い点：振る舞いが崩れたままリリースすることを防げる
* 良い点：動かすのはリリースのときだけなので、使用量が少ない
* 悪い点：揺れで点が下がっただけで、リリースが止まることがある
* 悪い点：必須のチェックを足すので、ルールセットの変更と、ほかの PR で飛ばして成功にする仕組みが要る
* 悪い点：キューの一時的なブランチの先頭のコミットのメッセージなどで、リリース PR かを判定する必要がある

### CI では動かさず、手元だけにする

* 良い点：ワークフローを足さないので、仕組みが最も小さい
* 悪い点：手元にサンドボックスの準備（Linux なら bubblewrap・socat）が要り、無い環境では確かめられない

## 補足

判断したときの方針は「一旦は手で起動するのと、手元だけにしたい。必要であれば CI に足す」だった。スキルを変えた PR で動かし忘れることが問題になったら、変わったスキルのケースだけを自動で動かす案（必須にしない）に足すことを検討する。
