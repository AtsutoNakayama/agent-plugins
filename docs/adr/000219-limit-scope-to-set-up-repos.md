# プラグインが効く範囲を、チームの設定があるリポジトリ（導入したリポジトリ）に限る

## 背景と課題

プラグインが動く範囲は、初期設定をしたかではなく、Claude Code でプラグインを有効にした範囲で決まる。ユーザー単位でインストールすると、フック（guard-git・task-flow・pr-link）は初期設定していないリポジトリでも動き、`~/.claude/dev-workflow/` に置いたユーザーの層（設定・文章のガイド・レビューの観点・タスクの進め方の追記）もそこで効く。たとえば、ユーザーの層に `base_branch: "develop"` と書くと、初期設定していないリポジトリでも develop の上のコミットを止める。#131 では、レビューに使うモデル（`review.model`）だけを、リポジトリの層（`config.json`・`config.local.json`）からだけ読むようにして避けたが、ほかの設定とフックには同じ問題が残っていた。

## 判断の決め手

* インストールの範囲（ユーザー単位・プロジェクト単位）に関わらず、同じ結果になること
* 複数のリポジトリで使う人が、個人の設定を1か所（ユーザーの層）に書けること
* 個人の設定だけで、チームのリポジトリの振る舞いが変わらないこと
* 破壊的変更になる範囲が小さいこと

## 検討した案

* プラグインの側で、導入したリポジトリ（チームの設定 `.claude/dev-workflow/config.json` があるリポジトリ）かを判定し、導入していなければフックもユーザーの層も効かせない
* 今のまま、プラグインを有効にした範囲すべてで効かせる（範囲は、インストールの単位で選んでもらう）
* ユーザーの層をやめ、設定はリポジトリの層だけにする
* `.claude/dev-workflow/` のディレクトリや、個人の上書き（`config.local.json`）があれば導入したとみなす

## 判断の結果

選んだ案：「プラグインの側で、導入したリポジトリかを判定する」。理由は、インストールの範囲に関わらず同じ結果になり、ユーザーの層も残せるため。

* 導入したリポジトリは、チームの設定 `.claude/dev-workflow/config.json` があるリポジトリとする（`lib/common.sh` の `dw_is_set_up`）。初期設定（repo-setup）が作るファイルで、中身は空でもよい。ワークツリーに無くても、メインのワークツリーにあれば導入したとみなす（初期設定をまだコミットしていないときや、初期設定より前に作ったブランチのワークツリーで、守りが外れないようにするため）。
* ホームをリポジトリにしているとき（dotfiles を `~/.git` で管理するときなど）は、`~/.claude/dev-workflow/config.json` がユーザーの層の設定と同じファイルになるので、チームの設定とはみなさない（ユーザーの層の設定があるだけで、ホームの下がすべて導入したことにならないようにするため）。
* 導入していないリポジトリ（リポジトリの外を含む）では、フックは何もせず、ユーザーの層を読まない。導入したリポジトリでは、今までどおりユーザーの層も効く。
* `review.model` も、ほかの設定と同じく層を合わせた値を使うように戻す。#131 で避けたかったのはほかのリポジトリへの影響で、ユーザーの層が導入したリポジトリにだけ効くようになったため。`setup-models.sh` が書くのは、今までどおりリポジトリの層だけにする。
* guard-git がどのリポジトリを判定の対象にするかは、[ADR 000219（guard-git の対象のリポジトリ）](000219-resolve-guard-git-target-repo.md) で決めた。

### 結果として起きること

* 良い点：ユーザー単位でインストールしても、導入していないリポジトリの git の操作やセッションに影響しない。
* 良い点：ユーザーの層に書いた設定は、導入したリポジトリのすべてに効き、それ以外には効かない。
* 悪い点：破壊的変更。初期設定をせずに使っていたリポジトリでは、フックとユーザーの層が効かなくなる。引き続き使うには、repo-setup で初期設定するか、`.claude/dev-workflow/config.json` を `{}` で作ってコミットする。そのため `doctor.sh` は、導入していないリポジトリで、このことを警告して repo-setup を案内する。
* 悪い点：初期設定（repo-setup）は、`.claude/dev-workflow/config.json` を作るまでは導入していないリポジトリで動くので、それまでの手順ではユーザーの層の設定を読まない。

### 確認

`tests/guard-git.bats`・`tests/task-flow.bats`・`tests/pr-link.bats` で、導入していないリポジトリではフックが何もしないことを確かめる。`tests/config.bats`・`tests/review-perspectives.bats`・`tests/review-perspective-add.bats` で、導入していないリポジトリとホームのリポジトリではユーザーの層を読まないことを確かめる。`tests/common.bats` で、導入したかの判定（メインのワークツリー・サブモジュール・ホームのリポジトリ）を確かめる。`tests/doctor.bats` で、導入していないリポジトリで警告することを確かめる。

## 各案の長所と短所

### プラグインの側で、導入したリポジトリかを判定する

* 良い点：インストールの範囲に関わらず、同じ結果になる。
* 良い点：ユーザーの層を残せる。
* 悪い点：判定のために、スクリプトとフックが、そのたびにチームの設定のファイルを探す。

### 今のまま、プラグインを有効にした範囲すべてで効かせる

* 良い点：変更が要らない。
* 悪い点：ユーザー単位でインストールすると、初期設定していないリポジトリでも main の上のコミットを止めたり、タスクの進め方を渡したりする。

### ユーザーの層をやめ、設定はリポジトリの層だけにする

* 良い点：ユーザーの層の設定が、ほかのリポジトリに効くことは無くなる。
* 悪い点：複数のリポジトリで使う人が、個人の設定をリポジトリごとに書く必要がある。
* 悪い点：フックが初期設定していないリポジトリで動くことは変わらない。

### `.claude/dev-workflow/` のディレクトリや `config.local.json` があれば導入したとみなす

* 良い点：チームの設定をコミットしなくても、手元だけで導入できる。
* 悪い点：個人の設定だけで、チームのリポジトリの振る舞いが変わる。

## 補足

* 出典：Issue #219（https://github.com/nakayama-labs/agent-plugins/issues/219）、設計書 §1「効く範囲」
* `review.model` をリポジトリの層からだけ読むようにしたのは #131（https://github.com/nakayama-labs/agent-plugins/issues/131）。この ADR で、ほかの設定とそろえた。
