# 最新の main の取り込み

main が進んだ PR は、最新の main を取り込んで CI が通り直るまでマージできない（ルールセットの「最新の main の取り込み」。設計書 §9）。ただし、マージキューを使うリポジトリでは、キューが最新の main と組み合わせて確かめるので、取り込むのは main とコンフリクトしたときだけでよい。このスキルは、作業用のブランチに `origin/<base_branch>` を merge して、テストとチェックを通し、push して CI の結果まで見る。取り込み先は設定の `base_branch`。

強制 push は使えない（フックで禁止）ので、rebase はせず merge で取り込む。

スクリプト（JSON を出力する）:

- `${CLAUDE_PLUGIN_ROOT}/scripts/branch-status.sh`：origin から `base_branch` を取得し、ブランチの遅れ（`behind`）・先行（`ahead`）、取り込むと衝突するか（`conflicts`。手元で確かめる）、追跡しているファイルの未コミットの変更（`dirty`。未追跡のファイルは除く）、origin のブランチとのずれ（`unpushed`・`unpulled`）、push 済みのブランチの遅れ（`pushed_behind`）と衝突（`pushed_conflicts`）、開いている PR のマージ状態（`pr.merge_state`）とマージキューの状態（`pr.merge_queue`）、push で origin に入るコミット（`push_commits`。取り込む前に控えた sha を渡すと、main の取り込み・pull の取り込み・自分のコミットに分ける）を調べ、次にすること（`plan`）を出す。何も変更しない（`--help` で使い方）
- `${CLAUDE_PLUGIN_ROOT}/scripts/branch-plan.sh`：`branch-status.sh` の出力から、次にすること（`plan` の `action`・`reason`・`queue`・`fallback`）を決める。`branch-status.sh` が中で使うので、直接は呼ばない。判断の表は `--help` にある

## 手順

### 1. 次にすることを調べる

取り込むのは今のブランチ（HEAD）なので、取り込む作業用のブランチのワークツリーの中で `branch-status.sh` を実行する（調べるのは今のブランチだけ。別のブランチに取り込むときは、そのブランチのワークツリーに移ってから行う）。

次にすることは、出力の `plan.action` だけで決める。取り込むか・push するか・止めるかは、`branch-plan.sh` が出力の値から判断の表で決めていて、組み合わせはテストで確かめてある。ここで出力の値を組み合わせて決め直さない。

- `merge`：取り込む。下の「取り込む前の確認」をしてから、手順2へ進む
- `push`：手元では取り込み済みで、まだ push していない（前に取り込んで直したが、push を断った・拒否された）。GitHub は push 済みの古いコミットを見ている。下の「取り込む前の確認」をしてから、手順2を飛ばして手順3へ進む（手順4・6は、「`push` として進めたとき」の扱いに従う。`none`・`recheck` で `plan.fallback` の `push` が選ばれて進めたときも同じ）
- `none`：取り込まずに終える。`plan.reason` ごとの文（下の表）を伝え、`plan.queue` があれば、キューの案内（下の表）を添える。`pr.merge_state` が `BLOCKED` なら、チェックの失敗や承認待ちでマージできないことも伝える。ただし、ユーザーが最新の main を求めている（CI の失敗を直すのに、main に入った変更が要るなど）ときは、`plan.fallback` に従う。null なら、最新の main はもう取り込んであると伝える。`merge`・`push` なら、AskUserQuestion で「取り込む」「取り込まずに終える」を選んでもらい（`push` は、手元で取り込み済みの分を push すること）、「取り込む」なら、その action と同じように進める。`plan.queue` が `queued`（キューに並んでいる）なら、push するとキューから外れるので、選択肢の説明に、キューの何番目（`pr.merge_queue.position`）から外れるかを書く
- `recheck`：GitHub が PR の衝突をまだ調べていて（`pr.merge_state` が `UNKNOWN`。main が進んだ直後によくなる）、手元でも確かめられなかった。数秒待って `branch-status.sh` を実行し直す。何回か実行し直しても `recheck` のままなら、AskUserQuestion で、`plan.fallback` をするか（`merge` なら取り込むか、`push` なら手元で取り込み済みの分を push するか）を選んでもらい、するならその action と同じように進める
- `ask_base`：GitHub は遅れや衝突があると言うが、手元では設定の `base_branch` を取り込み済み。調べている間に `base_branch` が進んだか、PR のマージ先が設定の `base_branch` と違う。もう一度 `branch-status.sh` を実行し、それでも `ask_base` なら、「PR のマージ先と設定の `base_branch` が違う可能性がある」ことを伝えて、どちらに取り込むかユーザーに聞く

`none` のときに伝える文（`plan.reason`）:

| `plan.reason` | 伝えること |
| --- | --- |
| `up_to_date` | すでに最新です |
| `no_conflict` | マージキューが最新の main と組み合わせて確かめるので、main と衝突していない今は、取り込みは要りません |
| `merged_not_pushed` | 手元では main を取り込み済みですが、main とは衝突していないので、push も要りません（push すると、キューに並んでいる PR は外れます。手元の取り込みは、次に push するときに一緒に入ります） |

キューの案内（`plan.queue`）。キューの状態からは、先に並んだ PR がマージされたかも、外れた後に push したかも分からないので、どれに当たるかを決めつけずに伝える:

| `plan.queue` | 伝えること |
| --- | --- |
| `conflict` | キューの中で先に並んだ PR と衝突していて、まもなくキューから外れます（GitHub の PR の画面では CLEAN に見えます）。先に並んだ PR はまだ main に入っていないので、今の main を取り込んでも直りません。その PR がマージされるのを待ち、その後に main と衝突したら、もう一度このスキルで取り込みます |
| `queued` | キューの `pr.merge_queue.position` 番目に並んでいるので、そのまま待ちます |
| `removed` | `pr.merge_queue.removed.reason`（衝突なら `merge_conflict`）でキューから外れたままです。次の3つを並べて伝える。①先に並んだ PR と衝突して、その PR がまだキューにあるなら、そのマージを待つ。マージされた後に main と衝突したら、もう一度このスキルで取り込む。②その PR がマージされたかキューから外れていて、こちらの衝突も直して push してあるなら、すぐにもう一度キューに入れる。③衝突以外の理由（CI の失敗など）なら、それに対応して push してから（対応済みならそのまま）、もう一度キューに入れる |
| `not_queued` | キューに入っていません。CI が通ったら、キューに入れてください（PR の「Merge when ready」か `gh pr merge <PR番号>`。入れるのは人です） |

取り込む前の確認（`merge`・`push` のとき）:

- `dirty` が true なら（未追跡のファイルは数えない）、merge の前にコミットするか、ユーザーに片付けてもらう（取り込みの結果と混ざらないようにする）
- `unpulled` が 1 以上なら、origin のブランチに手元に無いコミットがあり、push が拒否される。取り込む前に、そのコミットを取り込むか（`git pull --no-rebase`）ユーザーに確かめる。取り込むなら、pull の前の sha を控えるかは、下の「控える sha」に従う。取り込んで衝突したら、下の「衝突の直し方の確認」に従って直す

控える sha（`merge` として進めるときだけ。`push` として進めるときは、手順4で分けないので控えない）:

- 控えるのは、手順2より前（ここ）の pull の前の sha と、手順2の merge の前の sha の2つで、どれも `git rev-parse HEAD` で1回だけ控える。pull の前の sha は、pull を実行する直前に（未コミットの変更をコミットした後で）控える。手順2の後に pull するとき（手順4から pull の確認に戻ったとき）は、控えない（控えてあれば、前の値のままにする。その pull で作った取り込みのコミットは、main の取り込みに入る）
- `branch-status.sh` を実行し直すとき（手順4・6）は、控えたものをそのまま渡す（merge の前の sha は `--merged-from`、pull の前の sha は `--pulled-from`。控えていないものは付けない）。push で入るコミットを、main の取り込み・pull の取り込み・自分のコミットに分けるため

片付けない・取り込まないことになって止めたときや、`ask_base`・`recheck` で止めたときは、手順6の「push しなかったとき」のとおり伝える。

取り込み（ここの `git pull --no-rebase` と、手順2の `git merge`）が衝突以外で失敗したら（未追跡のファイルが上書きされるなど。`dirty` は未追跡のファイルを数えない）、直さずに止め、手順6の「push しなかったとき」のとおり、git のメッセージをそのまま伝える。衝突したときは、下の「衝突の直し方の確認」に従う。

### 2. 取り込む

先に、手順1の「控える sha」のとおり merge の前の sha を控えてから、`git merge --no-edit origin/<base_branch>` を実行する（`base` は `branch-status.sh` の出力。`--no-edit` は、エディタを開かず既定のメッセージで merge するため）。rebase と強制 push は使わない。

衝突したら、下の「衝突の直し方の確認」に従って直し、merge を完了する（衝突以外で失敗したときは、手順1の終わりのとおり止める）。

### 3. テストとチェックを通す

取り込んだ結果で、`${CLAUDE_PLUGIN_ROOT}/scripts/checks-commands.sh` を実行し、`--help` の「決め方」（設定 `checks.commands` → リポジトリの手がかりから推測 → ユーザーに聞く）に従って、実行するコマンドを決める。設定の `checks.commands` があれば、関係するものだけに絞らず全部実行し（空の配列は何も実行しない）、出力の `team_commands_changed` が true か null のとき（チームの設定がこのブランチで書き換わった、または比べられない）は、実行する前にコマンドを見せて確認を取り、確認が取れるまで実行しない。ユーザーに聞いたときは、答えを `checks-commands.sh --save --scope <local・team> --command <コマンド>`（実行するものが無いなら `--none`）で設定に保存するかも聞く。出力の `saved.warning` があれば、そのままユーザーに伝える。決めたテストとチェックを実行して、通ることを確かめる。取り込んだ変更と自分の変更が組み合わさって壊れていないかを見るためなので、衝突が無かったときも省かない。

失敗したら、原因が取り込みで入った変更との組み合わせなら直して、コミットする（commit スキル）。直すのに、取り込みで直した衝突の直し方を変える（片側の変更を採り直すなど）なら、直す前に、下の「衝突の直し方の確認」の「直し方を変えるとき」に従う。直せない、または判断できないときは、push せずに止め、手順6の「push しなかったとき」のとおり、失敗の内容を伝える。

### 4. push の前に確認を取る

確認の直前に `branch-status.sh` をもう一度実行して、push で入るコミット（`push_commits`）を取り直す（手順1の値は、手順2・3で取り込んだり、修正をコミットしたりすると古くなる）。控えた sha は、手順1の「控える sha」のとおり渡す（`--merged-from <merge の前の sha>`・`--pulled-from <pull の前の sha>`）。取り直した `unpulled` が 1 以上なら（手順3の間に別の場所から push があったなど）、push は拒否されるので、push の確認はせずに、そのことを伝えて、手順1の「取り込む前の確認」の `unpulled` の確認（pull するか）に戻る。pull したら、手順3から進め直す（手順2の取り込みは済んでいる。この pull の前の sha は控えない。このとき pull で作った取り込みのコミットは、手順2の merge の後にできたので、`push_commits` の `main` に入る。そう伝える）。

AskUserQuestion で、「push する」「push しない」を選んでもらう。確認の内容は、質問の中（質問の文や選択肢の preview）に入れる（設計書 §8。別の端末から使うと、質問の直前の文章が見えないことがある）。

- push で実際に origin に入るコミット（`push_commits.all`）。件数と主な内容を見せ、初回の push（`push_commits.first_push` が true。ブランチが新しく作られる）のときはそう伝える
- そのうち、`push_commits` の `main`（取り込んだ main のコミットと、手順3で直したコミット）・`pull`（pull が作った取り込みのコミット）・`own`（取り込む前から手元にあった自分のコミット）を分けて示す。どれも、origin に既にあるコミットは数えていない。範囲を自分で組み立てて数え直さない。手順1で `push` として進めたとき（`main` などが null）は分けずに、前に取り込んだ merge のコミットを含めて、`all` をまとめて示す
- 衝突を直したか、直し方を変えたなら（手順1で `push` として進めたときに、手順3で前の取り込みの直し方を変えたときも）、そのファイルと直し方。確認を取った方針や前の取り込みの直し方から変えたところ（手順3でテストの失敗を直したときなど）があれば、何をなぜ変えたかを分けて示す
- テストとチェックの結果（実行したものと、通ったか）

選択肢の説明には、選ぶと実際に何が起きるか（「`feat/12-x` を origin に push する。PR #5 に、取り込んだ main のコミット3件が加わり、CI が走り直す」など）を書き、`git push` などの内部の手順は書かない（設計書 §8）。

### 5. push して CI を待つ

「push する」と選ばれたら、`git push origin <ブランチ>`（強制のオプションは付けない）を実行する。拒否されたら（他の場所から push があったなど）、強制せず、手順6の「push しなかったとき」のとおり、メッセージをそのまま伝えて止まる。

push できたら、PR があれば `gh pr checks <PR番号> --watch` で CI が通り直るのを待つ（PR が無ければ、push までで終える）。push の直後はチェックがまだ登録されておらず、`gh pr checks` が `no checks reported` と出してすぐ終わる（`--watch` に入る前にエラーになる）ことがあるので、出力にそれがあれば、数秒待って、チェックが現れるまで数回やり直す。それ以外は、終了コードで判断せず、出力の各チェックの結果（pass・fail・pending）を読む。fail があれば、手順6で失敗したチェックを伝える。pending が残って終わったときは、もう一度 `--watch` で待つ。

### 6. 結果を伝える

push したかどうかで、伝えることを分ける（手順1の `none` で取り込まずに終えたときは、手順1のとおり伝えるので、ここには当たらない）。

**push しなかったとき**は、どこで止めたときも、push・CI・キューへの入れ直しの案内は伝えない（GitHub の PR は変わっていないので）。代わりに、止めた理由と、手元に残ったもの（push していないコミット）を伝える。手元に残ったものは、`branch-status.sh` を実行し直して（控えた sha は、手順1の「控える sha」のとおり、控えたものだけを渡す）、`push_commits` をそのまま見せる（`all` が空なら、無いと伝える）。範囲を自分で組み立てない。手元に何があるか（取り込みのコミットや、未コミットの変更をコミットしたものがあるか）は、この一覧で示し、下の箇条で言い切らない（どこまで進めてから止めたかで変わるため）。止めた場所ごとに、次も添える。

- 取り込む前の確認で止めた（未コミットの変更を片付けない、origin のブランチを取り込まない）・`ask_base`・`recheck` で止めた：止めた理由。origin のブランチを取り込まなかったなら、このままでは push が拒否されること
- 取り込み（pull・merge）が衝突以外で失敗した：git のメッセージ
- 手順3で直せなかった：失敗の内容と、手元のコミットはテストが通っていないこと
- 手順4で「push しない」が選ばれた：次にこのスキルを使うと、手元のコミットの上から進む（push するかは、そのときの状態で決まる）
- 手順5で push が拒否された：拒否のメッセージ。origin のブランチに手元に無いコミットがあるなら、次にこのスキルを使うと、取り込む前の確認でそれを取り込むかを聞くこと
- 衝突の確認で「取り込みをやめる」か「変えずに止める」が選ばれた：下の「衝突の直し方の確認」の「抜けたとき」のことも足す

**push したとき**は、取り込んだコミットの数、衝突の有無、push の結果、CI の結果を伝える（手順1で `push` として進めたときは、取り込んだコミットの数と衝突の有無の代わりに、前に取り込んだ分を push したことと、push したコミットの数を伝える）。CI が失敗したら、失敗したチェックの名前と、ログから分かる原因を伝える（直すかどうかは、ユーザーに聞く）。通ったら、PR をマージできる状態になったことを伝える（マージは人間が行う）。`pr.merge_queue.enabled` が true（キューを使うリポジトリ）なら、PR がキューに入っていない（main と衝突した PR はキューから外れ、push でも外れる）ので、「PR をもう一度キューに入れてください（PR の「Merge when ready」か `gh pr merge <PR番号>`）」と伝える。キューに入れるのは人が行い、このスキルでは行わない。

## 衝突の直し方の確認

このスキルで衝突を直すときは、どの場面でも、直す前に、衝突ごとの直し方の方針を見せて確認を取る。両側の意図を両立できるかは AI の解釈なので、両立できると判断した衝突も含めて、直す前に見せる（push の前の確認では、直したコミットが既にできていて、直し方を選び直せない。設計書 §8）。場面ごとに規則を書かず、どの場面もこの節に従う。

この節に従う場面:

- 取り込む前の確認で、origin のブランチを取り込んだ（`git pull --no-rebase`）ら衝突した
- 手順2で、`origin/<base_branch>` を取り込んだ（`git merge`）ら衝突した
- 手順3で、テストの失敗を直すのに、取り込みで直した衝突の直し方を変える（手順1で `push` として進めたときの、前に取り込んだときに直した分も含む）

**衝突したとき**（pull・merge）は、次の順に進める。

- **読む**：衝突したファイルごとに、両側の変更の意図を読む。`git log` と `git diff` で、取り込む側で何が変わったか、自分のブランチで何をしたかを確かめる。ここではまだファイルを直さない
- **方針を決める**：衝突ごとに、直し方の方針を決める。両側の意図を両立できるなら、そのように直す方針にする（よくある衝突の直し方は、下の例のとおり）。どちらを採るか、AI が判断できない衝突は、直し方の案を2〜3個に絞る
- **判断できない衝突を聞く**：AI が判断できない衝突があれば、先に AskUserQuestion で、その衝突ごとに1問にして、どう直すかを聞く（1回に聞けるのは4問までなので、多ければ分けて聞く）。衝突の内容（ファイルと、両側の変更の要点）は、質問の中にも入れる（設計書 §8）。選択肢は、絞った直し方の案（3つまで）と「取り込みをやめる」にし、説明には、選ぶと実際にどうなるか（「main 側の `foo()` の引数の追加を残し、こちらの呼び出しを合わせる」など）を書く。選ばれた直し方を、その衝突の方針にする。どれかの質問で「取り込みをやめる」が選ばれたら、ほかの答えによらず、方針の確認の「取り込みをやめる」と同じように終える
- **方針の確認**：すべての衝突の方針が決まったら、AskUserQuestion で、方針の確認を取る（1問にまとめ、ほかの質問と混ぜない）。どの衝突も「判断できない衝突を聞く」で、出した案がそのまま選ばれた（AI が決めた方針が1つも無い）ときは、同じことを二度聞かないよう、この確認を省いて直す。「Other」に書かれた答えは、どう直すかを AI が解釈するので、AI が決めた方針として扱い、この確認に入れる。衝突ごとに、ファイル、両側の変更の要点、どう直すか（聞いて決めた直し方を含む）を並べ、質問の中にも入れる（質問の文と、選択肢の preview。設計書 §8）。選択肢は次の3つにし、説明には選ぶと実際に何が起きるかを書く
  - 「この方針で直す」：見せた方針のとおりにファイルを直し、取り込みのコミットを作る（push はまだしない）
  - 「直し方を変える」：どの衝突をどう直すかを聞いて方針を決め直し、「判断できない衝突を聞く」（決め直した方針に、AI が判断できない衝突があれば）と「方針の確認」をもう一度行う
  - 「取り込みをやめる」：取り込みを取り消して（`git merge --abort`）、取り込む前の状態に戻して終える（「抜けたとき」のとおり伝える）。ファイルは何も直さない
- **直す**：確認を取った方針のとおりに直す。直している途中で、方針のとおりには直せないと分かったら（両側の変更が思ったより絡んでいたなど）、その衝突の方針を決め直して、「判断できない衝突を聞く」と「方針の確認」をもう一度行う（どの衝突もユーザーが選んだときも、このときは方針の確認を省かない）。このときは、直し終えたファイルを示し、どの質問の「取り込みをやめる」の説明も「取り込みを取り消して、取り込む前の状態に戻す。直し終えたファイルも元に戻る」にする。直し終えたファイルの直し方を変えるなら、`git checkout -m <ファイル>` でそのファイルを衝突した状態に戻してから直す（`git add` した後でも戻せる。戻せなければ、手で直さずに、取り込みをやめて取り込み直すかをユーザーに聞く）
- **コミットする**：直したら `git add` して、`git commit -m "<件名>" -m "<衝突を直した内容を1〜2行>"` で merge を完了する（件名は、git が用意した既定のメッセージの1行目にそろえる。`head -n 1 "$(git rev-parse --git-path MERGE_MSG)"` で読む（ワークツリーでは `.git` がファイルなので、`.git/MERGE_MSG` を直接は読めない）。手順2の merge なら `Merge remote-tracking branch 'origin/<base_branch>' into <ブランチ>`。エディタが開く `--edit` は使わない）

よくある衝突と直し方の例:

- **表や一覧の、隣り合った行をそれぞれが変えた**（README や設計書の表に、両側が別の行を足した・直したなど）：同じ行を変えたのではないので、行ごとに両側の変更を採る。両側が同じ位置に行を足したなら、両方の行を残し、表の並び（アルファベット順・手順の順など）に合わせて並べる
- **同じ行を、両側が違う目的で変えた**（一方が文言を直し、もう一方が項目を足したなど）：両方の変更を1行に合わせる
- **一方が消した・移した箇所を、もう一方が直した**：消した・移した理由を `git log` で確かめ、移した先があれば、そこに直した内容を移す

**直し方を変えるとき**（手順3）は、直す前に、どの衝突の直し方を、何からどう、なぜ変えるかを見せて、AskUserQuestion で確認を取る（質問の中にも入れる）。選択肢は次の2つにする。

- 「この直し方に変える」：ファイルを直してコミットし（push はまだしない）、手順3のテストとチェックをもう一度実行する（手順4で見せる結果は、変えた後のもの）。何をなぜ変えたかを控えて、手順4でも伝える
- 「変えずに止める」：直さず、push もせずに終える（「抜けたとき」のとおり伝える）。取り込みのコミットは手元に残る

**抜けたとき**（「取り込みをやめる」か「変えずに止める」が選ばれて終えたとき）は、push・CI・キューへの入れ直しの案内は伝えない（push していないので）。手順6の「push しなかったとき」のとおり、止めた理由と手元に残ったものを伝え、それに次を足す。

- 「取り込みをやめる」：取り込む前の状態に戻したこと。取り込む前の確認で origin のブランチを取り込んだ（pull した）後に、手順2の merge をやめたなら、pull で取り込んだ分は手元に残ること（pull が取り込みのコミットを作ったなら、そのコミットは push していない。fast-forward で済んだなら、push していないコミットは増えていない）。pull をやめたなら、origin のブランチの手元に無いコミットはまだ取り込んでおらず、このままでは push が拒否されること。merge をやめたなら、ブランチは `base_branch` と衝突したままで、PR があればこのままではマージできない（キューを使うリポジトリでは、キューにも入れられない）こと。直すには、もう一度このスキルで取り込むこと
- 「変えずに止める」：テストの失敗の内容と、テストの通らない取り込みのコミットが手元にあり、push していないこと（次にこのスキルを使うと、この取り込みのコミットの上から進む。push するか、さらに取り込むかは、そのときの状態で決まる）。取り込みをやり直すなら、手元の取り込みのコミットを取り消す必要があるので、どうするかはユーザーに相談すること
