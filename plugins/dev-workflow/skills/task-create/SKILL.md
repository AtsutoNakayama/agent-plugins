# Issue の起票

依頼の内容から Issue の下書きを作り、ユーザーの確認を取ってから `issue-create.sh` で起票する。判断と文章は AI が担当し、起票・ラベル・Project への追加はスクリプトが行う。

起票は GitHub に残るので、必ず手順3でユーザーの承認を得てから行う。承認なしに `issue-create.sh` を実行しない。

スクリプト（どれも JSON を出力する）:

- `${CLAUDE_PLUGIN_ROOT}/scripts/config.sh`：合わせた設定の出力
- `${CLAUDE_PLUGIN_ROOT}/scripts/adr-list.sh`：ADR の作成を提案するかの設定（`suggest`。`adr.suggest`）
- `${CLAUDE_PLUGIN_ROOT}/scripts/issue-create.sh`：起票・ラベル（type と breaking）・Project への追加・Status と Story Point の設定・依存関係（blocked by）の登録・親の Issue への紐付け（サブ Issue。`--help` で使い方）

## 起票を頼まれていない相談で呼ばれたとき

Issue の分け方・親子の構成の相談（起票はまだ頼まれていない）で呼ばれたときは、先に `config.sh .set_up` を実行する。`false`（dev-workflow を導入していないリポジトリ。リポジトリの外を含む）なら、このスキルを使わずに止め、通常の相談として答える（設定ファイルを自分で探さない。`.set_up` は設定の層では変えられない）。起票を頼まれたときは確かめずに、これまでどおり進める。`true` なら、手順1〜3は起票を頼まれたときと同じに進める（重複と親の候補の検索・分け方の案・確認）。違いは次の2つだけにし、手順の中には書き分けない。

- まだ起票しないので、手順2の重なりの質問と手順3の確認（Story Point が大きいときの分割の提案を含む）の選択肢は、ラベルと説明を「起票する」ではなく「下書きする」と書く。GitHub に書き込むこと（親の Story Point を空欄にするなど）は「起票するときに〜する」と書く（例：「そのまま下書きに進む」「#20 と重ならない部分だけを下書きする」「#30 を親にして、そのサブ Issue として下書きする。起票するときに #30 の Story Point を空欄にする」）。「既にある Issue で進める」は、下書きせずに止める。分割の提案の「このまま設定する」は「この値で下書きする」と書く。手順3の「この内容で起票する」は、選ぶと起票するので、そのまま書く
- 手順3の確認に「起票しない（提案だけにする）」を足し、選ばれたら起票せずに止める。「この内容で起票する」が選ばれたら、起票を頼まれたときと同じく手順4へ進む

## 手順

### 1. 設定を読む

`config.sh` で次を読む。

- `language`：Issue を書く言語
- `labels.types`：付けられる type ラベル
- `sub_issues.max_depth`：親子の Issue の深さの上限（一番上の Issue が1層目。既定 3）
- `detected.issue_templates`：リポジトリの Issue テンプレート（あれば本文の見出しをそれに合わせる）
- `guides.issue`：Issue の書き方のガイド（あれば読んで従う。複数あれば後ろのものを優先する）

### 2. 下書きを作る

#### 重複と親の候補を探す

下書きの前に、開いている Issue を読み（`gh issue list --state open --limit 1000 --json number,title,labels,subIssuesSummary`。`--json` に未知のフィールド（`subIssues`・`subIssuesSummary`・`parent`）のエラーで失敗したら、gh が古い（サブ Issue を `gh issue` で扱えるのは gh 2.94.0 から）ので、続けずに gh の更新を促して止まる。）、次を探す。タイトルだけで判断できないものは、`gh issue view <番号> --json number,title,body,parent` で本文も読む。

- **親の候補**：依頼が、その一部にあたる仕様の Issue。サブ Issue を既に持つ Issue（一覧の `subIssuesSummary.total` が1以上）だけを候補にする。サブ Issue を持たない Issue は、依頼より広い内容でも、着手する作業の Issue のこともあるので、親の候補にせず、次の重なりとして扱う。仕様として親にするかは、下の質問でユーザーが決める（作業の Issue を親にすると、その Issue の Story Point が空欄になり、同じ作業を二重に数えることになるため、自動では親にしない）
- **重複・重なり**：依頼と同じ内容の Issue や、やることの一部が重なる Issue（依頼を含む、サブ Issue を持たない広い Issue も含む）。依頼で指定された親と、上の親の候補は、重なりとして数えない（親のやることには子の作業が含まれるため）

重複・重なりがあれば、下書きの前に AskUserQuestion で、どうするかを聞く。質問の中と各選択肢の preview に、重なる Issue の番号・タイトルと、重なる部分を入れる（質問の中にも入れる。設計書 §8）。選択肢は次の3つ（重なる Issue がサブ Issue を持たず、依頼より広い Issue なら4つ）。選択肢の説明には、選ぶと何が起きるかを書く。

- **既にある Issue で進める**：起票せずに止め、重なる Issue の番号と URL を伝える。既にある Issue の本文は書き換えない（説明の例：「起票せず、#20 で進める」）
- **重ならない部分だけを起票する**：重なる部分を除いて下書きし、重なる Issue を本文の「背景」に `#N` で書く（説明の例：「#20 と重ならない部分だけを Issue にする」）
- **そのまま起票する**：重なりを承知で、依頼のとおりに下書きする
- **既にある Issue を親にする**（重なる Issue がサブ Issue を持たず、依頼より広い Issue のときだけ）：その Issue を仕様とみなして親にし、依頼をそのサブ Issue として下書きする（下の「親の Issue」）。説明には、その Issue に Story Point が入っていれば空欄にすることも書く（説明の例：「#30 を親にして、そのサブ Issue として起票する。#30 の Story Point は空欄にする」）

探した結果（重複・重なりと親の候補。無ければ「無い」）は、手順3の確認で伝える。

#### 下書きの項目

依頼の内容から次を考える。分からないことは推測で埋めず、ユーザーに聞く。ただし、分け方の提案を頼まれたときと、親と子をまとめて起票する依頼か、独立して着手できる作業をいくつも含む依頼で、分け方（何本に分けるか、親子にするか）が決まっていないときは、聞くだけで済ませず、下の基準（親子は2層が目安、Story Point は子にだけ付ける、依存は下の「依存する Issue」の書き方）に沿った分け方の案を下書きし、手順3でユーザーに選んでもらう。1本に収まる普通の依頼は、分け方を聞かずに1つの Issue として下書きする。Story Point が 21 以上になりそうなだけのときは、ここでは分けず、手順3の分割の提案に任せる。

- **タイトル**：何をするかが一目で分かる短い文。type（`feat:` など）は付けない（ラベルで表す）
- **type ラベル**：`labels.types` から1つ選ぶ。`ci` は CI/CD パイプラインの変更、`build` はビルドの設定・依存関係・Dockerfile の変更
- **破壊的変更か**：既存の利用者が設定やコマンドを直さないと動かなくなる変更なら、破壊的変更とする。type とは別に `breaking` ラベルを付ける（PR のタイトルが `<type>!: …` になり、major の version が上がる）
  - 例：設定ファイル（`.claude/dev-workflow/config.json` など）のキーやプレースホルダの名前の変更、スクリプトの引数の変更・削除、スキル名の変更
  - 「version を上げたいから付ける」ものではない。破壊的変更を伴わない節目（1.0.0 など）は、release-please の `release-as` などで上げる
  - 当たるか迷うときは、ユーザーに聞く。破壊的変更なら、本文の「背景」か「やること」に、利用者が何を直す必要があるか（移行のしかた）を書く
- **本文**：Issue テンプレートがあればその見出しに沿う。無ければ「背景」「やること」（チェックリスト）「完了条件」「変更するファイル・領域」「依存」
- **変更するファイル・領域**：触りそうなファイルやディレクトリを、`task-next` が同時に進めてよいかを見るのに使う（`task-start` も、着手する前に着手中の Issue と重なるかを確かめるのに使う）。テンプレートに「変更するファイル・領域」の見出しがあれば、そこに、パスを `- plugins/dev-workflow/scripts/` のように1行ずつ書く（無ければ、見出しを足して書く）。依頼やリポジトリの内容から分かる範囲で書き、推測で埋めず、分からなければ「- 不明」と書く。調査・洗い出し・Issue の整理のように、リポジトリのファイルを変えないタスクなら「- なし」と書く（`task-next` はどれとも重ならないものとして扱い、`task-start` はワークツリーを作らずに着手することを勧める）
- **依存する Issue**：この作業より先に終わらせる必要がある Issue。依頼の内容や、上で読んだ開いている Issue から考える。本文の「依存」に `- #N` の形で1行ずつ書き、無ければ「- なし」と書く（テンプレートに「依存」の見出しが無くても、依存があれば「依存」の見出しを足して書く）。「〜の Issue の後に」のように文章だけで書かず、既にある Issue は必ず番号で書く（まだ起票していない Issue への依存は、下の「親と子をまとめて起票するとき」のとおり、番号が決まるまで仮の名前で書く）
- **親の Issue**：大きな仕様を分けた一部なら、その仕様の Issue を親にする（起票した Issue は親のサブ Issue になる）。依頼で親を指定されたときは、その Issue を親にする。指定が無ければ、上の「重複と親の候補を探す」で見つけた親の候補と、重なりの質問で「既にある Issue を親にする」が選ばれた Issue から考え、候補が1つに決まらないときや、親にするか迷うときはユーザーに聞く。親子は2層（仕様 → 着手できる作業）を目安にする。親に親があるか（`gh issue view <番号> --json parent`）を確かめ、あれば起票する Issue は3層目になるので、手順3の確認でそのことを伝え、2層に収められないか（親を一段上の Issue にするなど）も添える。親子の深さが `sub_issues.max_depth` を超える紐付けはできない
- **ADR の項目**：依頼に、ADR にすべき設計上の判断（他の案と比べて選ぶ・破壊的変更・元に戻しにくい）が含まれるかを判断する。基準と決まりの正本は `${CLAUDE_PLUGIN_ROOT}/skills/adr-create/SKILL.md` の「ADR にすべき判断」と「ADR の作成の提案」の節なので、読んでから判断する。含まれるなら、「やること」の最後に `- [ ] <判断の短い説明>を ADR に残す` を足し（例：`- [ ] 提案する契機の判断を ADR に残す`。`language` の設定にかかわらず「を ADR に残す」で終える。`adr-list.sh` がこの文で ADR の項目を見分けるため）、「変更するファイル・領域」に ADR の置き場所（`adr-list.sh` の `dir`）を足す。足すかは手順3の確認の中で聞く。`adr-list.sh` の `suggest` が false なら、足さず、聞かない。判断を含まない依頼（決まったことの実装・不具合の修正・文言の調整など）には足さない。親と子をまとめて起票するときは、判断をする子にだけ足す
- **Story Point**：1, 2, 3, 5, 8, 13, 21, 34 から、作業の大きさ・不確かさ・リスクで見積もり、理由を1文で添える。Story Point は子の Issue にだけ付け、親になる Issue（サブ Issue を持つ、または持たせる予定の Issue）は空欄にする（親の大きさは子の合計で分かり、親にも付けると二重に数えるため）。既にある Issue を親にするとき、親の Story Point が入っていれば、起票のときに `issue-create.sh` が空欄にする

#### 親と子をまとめて起票するとき

依頼が「親の Issue と、その子の Issue」をまとめて起票するものなら（例：「ログイン機能の親 Issue と、画面・API・テストの子 Issue を作って」）、次の2つの形のどちらかで、全部の Issue を一度に下書きする。

- **新しい親と子**：親になる Issue（仕様）と、その子になる Issue（着手できる作業）を下書きする。親は子の完了条件をまとめた内容にし、子は1つずつ着手できる大きさにする
- **既にある Issue を親にする**：親に指定された Issue（`gh issue view <番号> --json number,title,state,parent`）を読み、足す子だけを下書きする。親が閉じていれば、子を足さずに止めて、ユーザーに聞く（開き直すか、別の親にするか）。親にさらに親があれば（`parent` が null でなければ）、足す子は3層目になるので、下の手順3の確認の前に `sub_issues.max_depth` を超えないかを確かめ、目安の2層より深くなることを確認で伝える。親の本文は書き換えない

どちらも、上の項目（タイトル・type・破壊的変更か・本文・変更するファイル・領域・依存・Story Point）を Issue ごとに考える。**親には Story Point を付けず、子にだけ付ける**。子が先に終わらせる必要がある別の子への依存は、番号が決まる前は「（1つ目の子）」のように仮に書く。

大きな依頼を、詰めたり縦に切ったりして子に分ける手法そのものは、この手順の範囲外とする。分け方はユーザーが決めたものか、依頼に書かれているものを使い、決まっていなければ、上の「下書きの項目」のとおり分け方の案を下書きする。

### 3. 確認を取る

タイトル・type・破壊的変更か・Story Point（と理由）・依存する Issue（番号とタイトル）・親の Issue（番号とタイトル）・変更するファイル・領域・本文と、手順2で探した結果（近い Issue の番号とタイトル。無ければ「重複・親の候補は無かった」）をまとめて見せ、AskUserQuestion で確認を取る。選択肢は「この内容で起票する」「Story Point を変える」「空欄にする」など。選択肢の説明には、選ぶと実際に何が起きるか（作るもの・削除するもの・GitHub に書き込むもの）を書き、`--dry-run` などのフラグやスクリプト名といった内部の手順は書かない（設計書 §8）。例：「この内容で起票する」の説明は「Issue を起票し、fix ラベルと Story Point 3 を付けて Project の Todo に追加する」（破壊的変更なら「feat と breaking のラベルと…」のように、breaking ラベルも書く）。見せた内容は、質問の中にも入れる（設計書 §8。別の端末から使うと、質問の直前の文章が見えないことがある）。各選択肢の preview に、タイトル・ラベル・Story Point・依存・親と本文の全文を入れる。親を指定するなら、「この内容で起票する」の説明に「#12 のサブ Issue にする」のように書き、「#12 に Story Point が入っていれば空欄にする」も書く。ユーザーが直したい点を言えば、下書きを直してもう一度見せる。

下書きに ADR の項目を足したとき（手順2）は、この同じ質問の中で、ADR を残すかを聞く（確認を増やさない）。質問の中に、ADR にすべきと判断した判断と、その理由（「ADR にすべき判断」のどれに当たるか）を入れ、選択肢に「ADR の項目を不要にする」を入れる。説明には、選ぶと何が変わるかを書く（例：「『やること』の『提案する契機の判断を ADR に残す』を取り消し線の項目にして起票する。PR を作るときにも ADR を提案しない」）。選ばれたら、その項目を `- [ ] ~~<判断の短い説明>を ADR に残す~~（不要）` にし、「変更するファイル・領域」に足した ADR の置き場所を外して、もう一度見せる。選択肢が4つを超えるときは、「空欄にする」のような、ほかの選択肢を「その他」で受ける。

親と子をまとめて起票するときは、質問の中と各選択肢の preview に、親子の木と各 Issue の本文の全文を入れる。木は、親（既にある Issue なら番号とタイトル、新しければ「新規」）を一番上にし、子をその下に並べて、各 Issue の type・Story Point（親は「空欄」）・依存を添える。続けて、Issue ごとに、タイトルと本文の全文を並べる。例：

```
#12 ログイン機能（既にある Issue。Story Point が入っていれば空欄にする）
├─ 新規 ログイン画面を作る        feat / SP 3
├─ 新規 認証 API を作る           feat / SP 5 / 依存：（1つ目の Issue）
└─ 新規 ログインのテストを足す    test / SP 2
```

「この内容で起票する」の説明には、起票する Issue の数と、子を親のサブ Issue にすること、親の Story Point を空欄にすること（新しい親は最初から空欄）を書く。例：「親の Issue と子の Issue 3つを起票し、子を親のサブ Issue にして、子にだけ Story Point を付けて Project の Todo に追加する」。

Story Point が 21 か 34 になるとき（見積もりでも、ユーザーの指定でも）は、見積もりの精度が低いので、先に Issue の分割を提案する。どう分けるか（例：調査と実装、機能ごと）の案を添え（元の Issue を親にして、分けた Issue をそのサブ Issue にする案も選べる。その親の Story Point は空欄にする）、「分割する」「このまま設定する」を選んでもらう。分割の案は、各選択肢の preview にも入れる（設計書 §8）。「このまま」なら、その値で起票する。34 より大きくなりそうな作業は、分割してから起票する。

### 4. 起票する

手順3で承認されたら、本文を一時ファイルに書き、`issue-create.sh --title ... --type ... --body-file <ファイル> [--breaking] [--story-point N] [--blocked-by N]... [--parent N]` を実行する。破壊的変更なら `--breaking` を付ける。Story Point が空欄なら `--story-point` を付けない。依存する Issue ごとに `--blocked-by N` を付ける（本文の「依存」と同じ番号にする）。親の Issue があれば `--parent N` を付ける。

1回の依頼で複数の Issue を起票するときは、手順2・3でまとめて下書きと確認をし、依存される側から順に、親と子なら親から先に起票する。親と子をまとめて起票するときは、次の順に進める。

1. 新しい親なら、先に `--parent` と `--story-point` を付けずに起票し、番号を控える（既にある Issue を親にするなら、その番号を使う）
2. 子を、`--parent <親の番号>` を付けて1つずつ起票する。子ごとに `--story-point` を付け、依存する子が先に起票済みなら、その番号を `--blocked-by` と本文の「依存」に使う

途中で失敗したら、そこで止めて、起票済みの Issue の番号と、まだの子を伝える。起票済みの Issue を作り直さず、ユーザーが続けると言えば、先に親のサブ Issue を読み直し（`gh api --paginate repos/{owner}/{repo}/issues/<親の番号>/sub_issues`）、起票済みの子とそのタイトル・番号を確かめてから、まだの子だけを、同じ親の番号で起票する。依存する子の番号も、読み直した番号を `--blocked-by` と本文の「依存」に使う。

まだ起票していない Issue への依存は、下書きでは「（1つ目の Issue）」のように仮に書いておき、先に起票した Issue の番号が分かったら、後の Issue の本文の「依存」と `--blocked-by`（親なら `--parent`）にその番号を使う。

失敗したら、標準エラーの1行のメッセージをそのまま伝える。「breaking ラベルがありません」のときは、`repo-setup`（ラベルの設定）を案内する。「親子の深さが上限の … 層を超えます」のときは、何も起票されていないので、親を一段上の Issue にするかをユーザーに聞く（上限が 3 未満なら、`sub_issues.max_depth` を上げる案も添える）。「Issue #N は作りましたが…」のときは Issue は作られているので、もう一度起票しない。

### 5. 結果を伝える

親と子をまとめて起票したときは、親子の木に番号と URL を添えて伝える。Issue ごとに、次を伝える。

Issue の番号と URL、破壊的変更として起票したか（`breaking`）、Project の列（`project.status`）と Story Point、依存する Issue（`blocked_by`）、親の Issue（`parent.number`）と、空欄にした親の Story Point（`parent.story_point_cleared`）を伝える。`project` が `null` なら、Project が未設定なので `repo-setup` を案内する。

### 6. 着手するかを聞く

依頼で着手まで頼まれていなければ（「起票して着手して」などでなければ）、`task-start` に進まず、結果を伝えた同じ返答の中で、着手するかを AskUserQuestion で聞く。並行して進めている他のタスクや優先順位があるので、着手するかは使う人が決める。選択肢の説明には、選ぶと実際に何が起きるかを書く（質問の中に、起票した Issue の番号とタイトルも入れる）。

- 「着手する」：`task-start` に進む（ブランチとワークツリーを作り、Issue を自分に割り当て、列を In Progress に移す）
- 「今は着手しない」：ブランチもワークツリーも作らず、Issue は Todo に残して終える

「起票して着手して」のように着手まで頼まれたときは、通常は聞かずに `task-start` に進む。起票を頼まれていない相談（上の節）で、起票せずに止まったときは、聞かない。

親と子をまとめて起票したときは、着手する Issue を `task-start` に渡す番号として決める。候補は着手できる子の Issue だけで、新しく起票した親は除く（親を渡すと、`task-start` は子を案内して止まる）。

- 着手まで頼まれていて、依頼で子の Issue が特定されているとき：その番号を渡して、聞かずに進む
- 着手まで頼まれていて、子が特定されていないとき：着手する子を AskUserQuestion で聞き、選ばれた子の番号を渡す
- 着手まで頼まれていないとき：どの子に着手するかを聞く質問にする（「今は着手しない」も選べる）

子を選んだときの親の扱いは `task-start` に任せる。
