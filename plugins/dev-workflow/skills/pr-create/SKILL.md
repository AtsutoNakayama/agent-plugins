# PR の作成

今のブランチの変更から PR の本文を書き、ユーザーの確認を取ってから `pr-create.sh` で push と PR の作成を行う。本文と、Issue のチェックリストのどの項目が済んだかの判断は AI が行い、タイトルの検証・`Closes #N`・ラベルの引き継ぎ・push・PR の作成・列の移動・Issue のチェックの付与はスクリプトが行う。

push と PR の作成は GitHub に残るので、必ず手順5でユーザーの承認を得てから行う（設計書 §8）。承認なしに `--dry-run` を外して実行しない。

スクリプト（どれも JSON を出力する）:

- `${CLAUDE_PLUGIN_ROOT}/scripts/config.sh`：合わせた設定の出力
- `${CLAUDE_PLUGIN_ROOT}/scripts/pr-create.sh`：タイトルと本文の検証、push、PR の作成、列の移動、Issue のチェックの付与（`--help` で使い方）

## 手順

### 1. 設定と Issue を読む

`config.sh` で次を読む。

- `language`：本文を書く言語
- `base_branch`：PR のマージ先
- `pr.template`：PR テンプレートのパス（リポジトリのルートから。`null` なら、プラグインの既定 `${CLAUDE_PLUGIN_ROOT}/templates/pull_request_template.md` の見出しを使う）
- `guides.pr`：PR の書き方のガイド（あれば読んで従う。複数あれば後ろのものを優先する）

紐付ける Issue の番号は、ブランチ名（`branch.pattern` の `{issue_number}`）から読む。分からなければユーザーに聞く。`gh issue view <番号> --json number,title,body,labels` で Issue を読む。

### 2. 変更を確かめる

- `git status` で未コミットの変更が無いか見る。あれば commit スキルでコミットしてから進める（PR に入れない変更なら、ユーザーに確かめる）
- `git log --oneline origin/<base_branch>..HEAD` と `git diff origin/<base_branch>...HEAD` で、PR に入る変更を読む

### 3. 本文を書く

PR テンプレートの見出しに沿って書く。既定のテンプレートなら次のとおり。

- **概要**：何のために何をしたかを1〜3文で
- **変更点**：変更したファイルや機能ごとに箇条書き。レビューする人が差分を読む前に全体を掴めるように、なぜそうしたかも添える
- **確認方法**：実行したテスト・確かめた手順と、その結果（件数など）。実行していないものを書かない
- `BREAKING CHANGE: <移行のしかた>`：Issue に `breaking` ラベルがあるときだけ、本文の最後（`Closes #<番号>` の前）に書く。既存の利用者が何をどう直せばよいか（例：「`.claude/dev-workflow/config.json` の `foo` を `bar` に変えてください」）を書く。スカッシュマージでは PR の本文がコミットの本文になり、release-please などが変更履歴に載せる。書かないとスクリプトが止まる
- `Closes #<番号>`：書かなければスクリプトが末尾に足す。テンプレートの空の `Closes #` は消してよい

タイトルはスクリプトが `<type>: <Issueのタイトル>`（Issue に `breaking` ラベルがあれば `<type>!: <Issueのタイトル>`）で作るので、`--title` は付けない。Issue のタイトルでは内容が伝わらないなど、変えたいときだけ付ける（type は Issue の type ラベルと同じにし、`breaking` ラベルがあれば type の後に `!` を付ける）。

### 4. 済んだ「やること」の項目を選ぶ

本文を一時ファイルに書き、`pr-create.sh --issue <番号> --body-file <ファイル> --dry-run` を実行する。出力の `tasks` は Issue の本文のチェックリストの項目（`checked`・`text`）で、`text` が `--check` に渡す文になる。

Issue の「やること」（Issue テンプレートの、作業の項目を並べた見出し。英語なら Tasks など）の項目のうち、まだチェックが無く（`checked` が false）、手順2で読んだ差分で済んだと判断できる項目を選ぶ。次の項目は選ばない。

- 済んだかはっきりしない項目（一部だけ済んだもの、差分から判断できないもの）
- 取り消し線（`~~…~~`）で取りやめた項目
- 「やること」以外の見出し（「完了条件」など）のチェックリストの項目

選んだ項目ごとに `--check "<text>"`（`tasks` の `text` をそのまま）を付けて、もう一度 dry-run する。項目は番号ではなく文で指すので、確認を待つ間に Issue の項目が増減しても、別の項目にチェックが付くことは無い。選ぶ項目が無ければ `--check` を付けない。

### 5. 予定を見せて確認を取る

手順4の dry-run の出力の `title`・`body`（`Closes #N` を足した後のもの）・`labels`・`actions`（push、PR の作成、列の移動、Issue のチェック）と、チェックを付ける項目（`checked` の文）を見せ、AskUserQuestion で「この内容で PR を作る」「本文を直す」「タイトルを変える」などを選んでもらう。選択肢の説明には、選ぶと実際に何が起きるか（作るもの・削除するもの・GitHub に書き込むもの）を書き、`--dry-run` などのフラグやスクリプト名といった内部の手順は書かない（設計書 §8）。例：「この内容で PR を作る」の説明は「ブランチを push し、#12 を閉じる PR を作り、#12 の『やること』の2項目にチェックを付ける」。チェックする項目は、この同じ質問の中で確かめる（確認を増やさない）。選択肢に「チェックする項目を変える」を入れ、チェックを付けない項目（「やること」のうち選ばなかったもの）も preview に並べる。見せた内容は、質問の中にも入れる（設計書 §8。別の端末から使うと、質問の直前の文章が見えないことがある）。各選択肢の preview に、タイトル・ラベルと本文の全文、チェックを付ける項目と付けない項目を入れる。会話の中のあいまいな返事を承認とみなさない。

直したい点を言われたら、本文や `--check` を直してもう一度 dry-run を見せる。

そのブランチの開いた PR が既にあるとき（`created: false`）は、push と Issue のチェックだけを行い、PR のタイトル・本文・ラベル・列は変えない（出力の `title`・`body`・`labels` は `null`）。前に PR を出した後に済んだ項目にも、ここでチェックを付けられる。確認では「push して既にある PR #N を更新する」ことと、チェックを付ける項目を見せ、書いた本文は反映されないと伝える。本文を変えたいと言われたら、GitHub の画面で直してもらうか、`gh pr edit <番号> --body-file <ファイル>` を実行してよいか別に確認を取る。

dry-run が止まったときは、標準エラーの1行のメッセージに従う。

- 「未コミットの変更があります」：commit スキルでコミットしてからやり直す
- 「タイトルが規約に合いません」「タイトルの type が…違います」「タイトルの type の後に ! を付けてください」：`--title` を直す
- 「本文の最後に「BREAKING CHANGE: <移行のしかた>」を書いてください」：Issue に `breaking` ラベルがある。移行のしかたを本文に書いてやり直す。破壊的変更でないなら、ラベルを外してよいかユーザーに確認を取ってから外す
- 「既にある PR #N のタイトルの type の後に ! がありません」「既にある PR #N の本文に「BREAKING CHANGE: <移行のしかた>」がありません」：PR を出した後に Issue に `breaking` ラベルが付いた。直したタイトル・本文を見せ、`gh pr edit <番号> --title … / --body-file …` で直してよいか確認を取ってから直し、やり直す
- 「type ラベルを1つにしてください」：どのラベルにするかユーザーに聞き、Issue のラベルを直してから進める（ラベルの変更も確認を取ってから行う）
- 「--check の文の項目が Issue #N のチェックリストに1つだけではありません」：出力の `tasks` の `text` をそのまま指定し直す。同じ文の項目が複数あってどれか決まらないときは、その項目は選ばない（チェックを付けないことを確認の中で伝える）

### 6. 実行する

承認されたら、同じ引数で `--dry-run` を外して実行する。失敗したら、標準エラーの1行のメッセージをそのまま伝える。

- 「push できませんでした」：origin のブランチに手元に無いコミットがある。強制 push はせず、ユーザーに取り込み方を相談する
- 「push しましたが、PR を作れませんでした」：もう一度実行すれば、push 済みのブランチから PR を作る
- 「PR #N は作りましたが、Issue #N の列を移せませんでした」：PR はできている。もう一度実行しても列は移さないので、メッセージにある `status-set.sh` のコマンドで移し、結果を伝える（列の移動は戻せるので確認を取らない。設計書 §8）。`--check` を付けていたときは、Issue のチェックもまだ付いていないので、同じ引数でもう一度実行して付ける（既にある PR として、push とチェックだけを行う）
- 「PR #N はできていますが、Issue #N のチェックリストを変えられませんでした」（「Issue #N を読めず、…」も同じ）：承認済みの操作の続きなので、同じ引数でもう一度実行する
- 「Issue #N の本文のチェックリストが途中で変わり、指定した文の項目が1つだけではなくなったので、チェックを付けませんでした」：PR はできている。確認を待つ間に、選んだ項目の文が書き換えられたか消された。Issue を読み直して手順4から選び直し、チェックする項目をもう一度確かめてから実行する

### 7. 結果を伝える

PR の番号と URL（`pr.number`・`pr.url`）を伝える。列を移したとき（`status.skipped` が false）は、移した列（`status.to`）も伝える。Issue にチェックを付けたとき（`checked` が空でない）は、付けた項目と Issue の URL も伝える。マージは人間が行う（`allow_ai_merge` が true でない限り、AI はマージしない）。
