# 作業の開始

Issue の作業を始められる状態にする。ワークツリーを作るかどうかは Issue の本文から AI が判断して提案し、ユーザーが選ぶ。ブランチ名の短い説明は AI が考え、ワークツリーの作成・割り当て・列の移動は `task-start.sh` が行う。

調査・洗い出し・Issue の整理のように、リポジトリのファイルを変えないタスクには、ワークツリーもブランチも要らない。そのときは作らずに、割り当てと列の移動だけを行う（設計書 §4）。type ラベルだけでは分からない（docs でもファイルを変えるし、調査は type に現れない）ので、本文から判断する。

親の Issue（サブ Issue を持つ Issue）には着手しない。親は子をまとめるだけで、親そのものの作業は無く、作業は子の Issue で進める（設計書 §4）。

割り当てと列の移動は戻せるので、ワークツリーを作るかを選んでもらった後は、実行の確認は取らずに進めて結果を伝える（設計書 §8）。ただし、Issue のラベルを直すときは確認を取る。

スクリプト（どれも JSON を出力する）:

- `${CLAUDE_PLUGIN_ROOT}/scripts/task-start.sh`：ワークツリーとブランチの作成・割り当て・列の移動。`--no-worktree` で、ワークツリーとブランチを作らずに割り当てと列の移動だけを行う（`--help` で使い方）
- `${CLAUDE_PLUGIN_ROOT}/scripts/branch-name.sh`：ブランチ名を作る・検証する（task-start.sh が中で使う）

## 手順

### 1. Issue を読む

引数があれば Issue の番号として使う（`12` でも `#12` でもよい）。引数が無ければ、依頼の文章から番号を読む。それでも分からなければユーザーに聞く。`gh issue view <番号> --json number,title,body,labels,state,subIssues,subIssuesSummary` で Issue を読む。閉じていれば止める。親の Issue（`subIssuesSummary.total` が 1 以上）なら、ブランチ・割り当て・列の移動のどれも行わずに止め、手順2のとおり子を案内する。type ラベル（`labels.types` のどれか）が無い、または複数あるときは、どれにするかユーザーに聞いて Issue のラベルを直してから進める（ラベルの変更も確認を取ってから行う。選択肢の説明には「Issue #12 のラベルを fix だけにする」のように、選ぶと何が変わるかを書く）。

### 2. 親の Issue なら、子を案内して止まる

`subIssues.nodes` から開いている子（`state` が `OPEN`）を、番号とタイトルの一覧にして見せ、どの子に着手するかを選んでもらうよう伝える（`subIssues` は先頭の一部だけのことがあるので、`subIssues.totalCount` が見せた数より多ければ `gh api --paginate repos/{owner}/{repo}/issues/<番号>/sub_issues` で全部を読む）。ユーザーが子を選んだら、その子の番号で手順1からやり直す（子がさらに親なら、同じように孫を案内する）。別のリポジトリの子（`url` のリポジトリが違う。GitHub の画面で手で紐付けたときだけできる）は扱わないので、一覧には入れず、そういう子があることだけを伝える（番号だけで手順1に戻ると、今のリポジトリの同じ番号の別の Issue を読んでしまうため）。

開いている子が無い（子がすべて閉じた）ときは、親の作業は終わっているので、親を閉じる（completed）よう伝える。親で別にやる作業が残っていれば、それを子の Issue として起票する（task-create）よう添える。どちらも、このスキルでは行わない。

### 3. ワークツリーを作るかを決める

Issue の本文の「やること」「完了条件」「変更するファイル・領域」から、このタスクがリポジトリのファイルを変えるかを判断する。

- 変える：コード・テスト・ドキュメント・設定のどれかを変える項目がある。「変更するファイル・領域」にファイルが書いてある
- 変えない：調査・洗い出し・Issue の起票や整理・GitHub の設定の変更のように、結果を Issue のコメントや別の Issue に残すだけで、リポジトリのファイルを変える項目が無い。「変更するファイル・領域」が「- なし」なら、変えないタスクとして書かれている

AskUserQuestion で、判断した結果と理由（根拠にした本文の項目）を見せ、「ワークツリーを作って着手する」と「ワークツリーを作らずに着手する」のどちらかを選んでもらう。判断に合う方を先頭に置いて (Recommended) を付ける。判断と理由は、質問の中にも入れる（設計書 §8。別の端末から使うと、質問の直前の文章が見えないことがある）。選択肢の説明には、選ぶと実際に何が起きるかを書き、`--no-worktree` などのフラグやスクリプト名といった内部の手順は書かない（設計書 §8。例：「ブランチ feat/12-add-login とワークツリーを作り、Issue #12 を自分に割り当てて In Progress に移す」「ブランチとワークツリーは作らず、Issue #12 を自分に割り当てて In Progress に移すだけ。後からファイルを変えることになったら、もう一度着手すればワークツリーを作れる」）。

依頼の文章で既に決まっているとき（「ワークツリーを作らずに #12 に着手して」「#12 のワークツリーを作って」など）は、聞かずにそれに従う。

作らずに着手するなら、手順4を飛ばし、手順5で `--slug` の代わりに `--no-worktree` を付ける。本文の「変更するファイル・領域」が「- なし」になっていなければ（空・「不明」・パスが書いてある）、結果を伝えるときに「- なし」に直すよう添える（そのままだと、着手している間、task-next が Todo の全部に「重なるか分からない」と警告する）。

### 4. ブランチ名の短い説明を考える

Issue のタイトルと本文から、何をするかが分かる**英語の**短い説明を考える（2〜5語。例：`add login page`）。日本語は使わない（ブランチ名は `[a-z0-9-/]` だけ）。

### 5. 実行する

`task-start.sh --issue <番号> --slug "<短い説明>"`（ワークツリーを作らないなら `task-start.sh --issue <番号> --no-worktree`）を実行する。手順3の後に、もう一度 AskUserQuestion で確認を取らない。

「短い説明に英数字がありません」で止まったら、手順4に戻って英語の短い説明を考え直し、もう一度実行する。

「Issue #N には既にブランチ … があります」で止まったら（ワークツリーを作らずに着手しようとした）、何も変えていない。その Issue は既にブランチで作業しているので、メッセージのブランチとワークツリーの場所を伝え、そのワークツリーで作業するよう案内する。ワークツリーが無ければ、ワークツリーを作って着手し直す（ブランチの名前が `branch.pattern` の形なら、その短い説明を `--slug` に渡すと、既にあるブランチを使い回す）。そのブランチが前の作業で終わったもの（PR がマージ済み。再び開いた Issue など）なら、先に task-finish でそのブランチを片付けてから、もう一度ワークツリーを作らずに着手する。

ワークツリーを作らずに着手したとき、「Issue #N に関係するかもしれないブランチ（…）があります」の警告（`warn:`）が出たら、名前が似ているブランチか、Issue を閉じる PR のブランチがある。着手は済んでいるので、警告のブランチを伝え、この Issue の作業ならそのブランチ（ワークツリー）で作業するよう案内する（関係の無いブランチのこともあるので、決めつけない）。

「親の Issue …なので、着手しません」で止まったら（手順1で読んだ後に子が足された）、何も作られていない。手順1で読んだ子の一覧は子が足される前のものなので、`gh issue view <番号> --json subIssues,subIssuesSummary` で読み直してから、手順2のとおり子を案内する。

ほかのエラーで失敗したら、標準エラーの1行のメッセージをそのまま伝える。途中で失敗しても、もう一度実行すれば既にあるワークツリー・割り当てを使い回して続きから進む。サブモジュールの初期化に失敗したときは、警告（`warn:`）を出すだけで続ける。その警告もユーザーに伝える。

### 6. 結果を伝える

ブランチ名とワークツリーの場所（`worktree`）、列（`status.to`）を伝える。以後の作業は、そのワークツリーの中で行う（Bash では `cd <worktree>` してから作業する）。

ワークツリーを作らずに着手したとき（`worktree` が `null`）は、割り当てと列だけを伝え、次のことを添える。

- 結果（調査の結論など）は、Issue のコメントや、起票した別の Issue に残す
- 途中でリポジトリのファイルを変えることになったら、もう一度このスキルで着手してワークツリーを作る（割り当てと列はそのまま使い回す）。base_branch の上でファイルを変えない
- 終わったら task-finish で Issue を閉じる（PR が無いので、マージでは閉じない）

実装は、全部を直し終えてから1回でコミットするのではなく、論理的な区切り（1つの変更を仕上げてテストが通ったところ）ごとに commit スキルでコミットしながら進める。区切りの細かさは commit スキルの手順2の基準に従う。
