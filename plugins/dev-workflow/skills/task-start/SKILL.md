# 作業の開始

Issue の作業を始められる状態にする。ブランチ名の短い説明は AI が考え、ワークツリーの作成・割り当て・列の移動は `task-start.sh` が行う。

Issue の割り当てと Project の列の移動は GitHub を変えるので、必ず手順3でユーザーの承認を得てから行う。承認なしに `--dry-run` を外して実行しない。

スクリプト（どれも JSON を出力する）:

- `${CLAUDE_PLUGIN_ROOT}/scripts/task-start.sh`：ワークツリーとブランチの作成・割り当て・列の移動（`--help` で使い方）
- `${CLAUDE_PLUGIN_ROOT}/scripts/branch-name.sh`：ブランチ名を作る・検証する（task-start.sh が中で使う）

## 手順

### 1. Issue を読む

`gh issue view <番号> --json number,title,body,labels,state` で Issue を読む。番号が分からなければユーザーに聞く。閉じていれば止める。type ラベル（`labels.types` のどれか）が無い、または複数あるときは、どれにするかユーザーに聞いて Issue のラベルを直してから進める（ラベルの変更も確認を取ってから行う）。

### 2. ブランチ名の短い説明を考える

Issue のタイトルと本文から、何をするかが分かる**英語の**短い説明を考える（2〜5語。例：`add login page`）。日本語は使わない（ブランチ名は `[a-z0-9-/]` だけ）。

### 3. 予定を見せて確認を取る

`task-start.sh --issue <番号> --slug "<短い説明>" --dry-run` を実行し、ブランチ名・ワークツリーの場所・`actions`（割り当て・列の移動など）を見せる。AskUserQuestion で「この内容で始める」「短い説明を変える」などを選んでもらう。会話の中のあいまいな返事を承認とみなさない。

「短い説明に英数字がありません」で止まったら、手順2に戻って英語の短い説明を考え直し、もう一度 `--dry-run` から実行する。

### 4. 実行する

承認されたら、同じ引数で `--dry-run` を外して実行する。失敗したら、標準エラーの1行のメッセージをそのまま伝える。途中で失敗しても、もう一度実行すれば既にあるワークツリー・割り当てを使い回して続きから進む。サブモジュールの初期化に失敗したときは、警告（`warn:`）を出すだけで続ける。その警告もユーザーに伝える。

### 5. 結果を伝える

ブランチ名とワークツリーの場所（`worktree`）、列（`status.to`）を伝える。以後の作業は、そのワークツリーの中で行う（Bash では `cd <worktree>` してから作業する）。

実装は、全部を直し終えてから1回でコミットするのではなく、論理的な区切り（1つの変更を仕上げてテストが通ったところ）ごとに commit スキルでコミットしながら進める。区切りの細かさは commit スキルの手順2の基準に従う。
