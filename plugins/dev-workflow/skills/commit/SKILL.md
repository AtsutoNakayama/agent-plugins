# コミット

変更を読んでコミットの単位とメッセージを決め、`commit.sh` で規約を検証してからコミットする。コミットは手元だけの操作なので、確認は取らずに進めてよい（設計書 §8）。ただし、どの変更を含めるか迷うときはユーザーに聞く。

スクリプト（どれも JSON を出力する）:

- `${CLAUDE_PLUGIN_ROOT}/scripts/config.sh`：合わせた設定の出力
- `${CLAUDE_PLUGIN_ROOT}/scripts/commit.sh`：メッセージの検証とコミット（`--help` で使い方）

## 手順

### 1. 設定を読む

`config.sh` で次を読む。

- `language`：要約と本文を書く言語
- `commit.types`・`commit.scope_required`：使える type と、スコープが必須か
- `detected.commitlint`：commitlint の設定があれば、その規約にも従う
- `guides.commit`：コミットの書き方のガイド（あれば読んで従う。複数あれば後ろのものを優先する）

### 2. コミットの単位を決める

`git status` と `git diff`（ステージ済みなら `git diff --cached` も）で変更を読む。

1つのコミットは1つの論理的な変更にする。基準は次のとおり（`guides.commit` に細かさの決まりがあれば、そちらを優先する）。

- 要約を「〜と〜」とせずに1行で書ける
- どのコミットの時点でも、ビルドとテストが通る（テストはそれが確かめるコードと同じコミットに入れる）
- 準備のための変更（リファクタリング・名前の変更・整形など）は、それを使う変更とは別のコミットにして先に置く
- 関係の無い変更が混ざっていれば、目的ごとに分けて複数のコミットにする。1つのファイルに複数の目的の変更があるときは、手順4のやり方でファイルの一部だけをステージして分ける
- 秘密の情報（トークン・パスワード・`.env` など）や、生成物・一時ファイルは含めない。見つけたらユーザーに伝える
- どの変更を含めるか判断できないときは、ユーザーに聞く

### 3. メッセージを書く

```
<type>(<scope>): <要約>

<本文（任意）>
```

- **type**：変更の性質で選ぶ（`commit.types` のどれか）。Issue の type ラベルと同じとは限らない（例：機能の Issue でもテストだけのコミットは `test`）
- **scope**：変更した範囲が1つにまとまるなら付ける（小文字の英数字と `-`）。`scope_required` が true なら必ず付ける
- **要約**：何をしたかを1行で。末尾に句点は付けない
- **本文**：なぜそうしたかが要約から分からないときだけ書く。1行目の次は空行にする
- `Refs` は付けない（Issue との紐付けは PR の `Closes #N` で行う）

### 4. コミットする

コミットに含めるファイルを `git add <ファイル>` でステージし、メッセージを一時ファイルに書いて `commit.sh --message-file <ファイル>` を実行する。`git add -A` のようにまとめて足すのは、手順2で全部を含めると決めたときだけにする。

検証で止まったら、標準エラーの1行のメッセージに従ってメッセージを直し、もう一度実行する。「main の上ではコミットしません」のときは、task-start で作業用のブランチを作ってから進める。

### 5. 結果を伝える

コミットの sha（短い形）と1行目を伝える。複数のコミットに分けたときは、それぞれを伝える。
