# ローカルのレビュー

作業中のブランチの変更をレビューし、指摘を1つの一覧にまとめて、ユーザーが選んだものだけを反映する。一般的なバグの検出は組み込みの `/code-review` に任せ、このスキルが呼ぶサブエージェントは独自の観点だけを担当する（設計書 §7）。

レビューと反映は手元だけの操作なので、実行の確認は取らない。ただし、どの指摘を反映するかは必ずユーザーに選んでもらい、選ばれていない指摘は反映しない（設計書 §8）。

スクリプト（JSON を出力する）:

- `${CLAUDE_PLUGIN_ROOT}/scripts/config.sh`：合わせた設定の出力
- `${CLAUDE_PLUGIN_ROOT}/scripts/review-perspectives.sh`：3つの層から観点ファイルを集める（`--help` で観点ファイルの形式）

## 手順

### 1. レビューする変更を決める

- コミットしていない変更があれば、先に commit スキルでコミットする（`/code-review` はコミットした変更だけを見るので、独自の観点と範囲を揃える）
- `config.sh .base_branch` でマージ先のブランチを読み、`git fetch origin <base_branch>` の後に `git merge-base origin/<base_branch> HEAD` を基点にする
- 基点からの差分（`git diff <基点>`）をレビューの対象にする
- 差分が無ければ、レビューするものが無いと伝えて止める
- Issue の番号はブランチ名から読む（`branch.pattern` の `{issue_number}` の位置）。読めなければ Issue は無いものとして進める

### 2. 観点を集める

`review-perspectives.sh` を実行する。

- `perspectives` の各観点を手順3でレビューする。0件なら `/code-review` だけで進める
- `invalid` があれば、ファイルと理由をユーザーに伝える（レビューは続ける）
- `disabled` は、止めている観点としてユーザーに伝える

### 3. 並行してレビューする

次をまとめて並行して実行する。

- **独自の観点**：`perspectives` の観点ごとに、Agent ツールでサブエージェントを1つずつ、同じメッセージの中で起動する。サブエージェントには、観点ファイルのパス（`path`）・基点・Issue の番号を渡し、下の「サブエージェントへの指示」をそのまま含める
- **一般的なバグ**：組み込みの `/code-review`（Skill ツールの `code-review`）を、今のブランチ名を引数にして実行する（基点の sha を渡すと、そのコミット1つだけをレビューしてしまう）。使えない環境では、その旨を最後に伝えて独自の観点だけで進める

サブエージェントへの指示:

```
あなたはコードレビューの担当者で、1つの観点だけを見る。ファイルは編集しない。
1. 観点ファイル <path> を読み、本文の指示に従う（frontmatter の title が観点の要約）。
2. `git diff <基点>` を読んで、この観点に当てはまる問題だけを探す。
   一般的なバグ・スタイルの好みなど、観点の外のことは指摘しない。
3. 結果を次の JSON の配列だけで返す（指摘が無ければ []）。
   [{"file": "リポジトリからの相対パス", "line": 行番号または null,
     "summary": "何が問題か（1文）", "detail": "根拠（どの行がどうなっているか）",
     "suggestion": "どう直すか"}]
```

### 4. 一覧にまとめる

- サブエージェントの結果と `/code-review` の指摘を1つの一覧にし、上から番号を付ける。各指摘には出どころ（観点の名前、または `code-review`）を添える
- 同じ場所の同じ問題を複数が指摘していれば、1つにまとめて出どころを並べる
- 並べ方は、壊れる・誤る問題を先に、書き方の問題を後にする
- 一覧を表で見せる（番号・出どころ・ファイルと行・要約・直し方）
- 指摘が1つも無ければ、その旨と、レビューした観点の一覧を伝えて終わる

### 5. 反映するものを選んでもらう

AskUserQuestion の複数選択（`multiSelect: true`）で、反映する指摘を選んでもらう。

- 1つの質問に選択肢は4つまでなので、4件ずつ質問を分ける（1回で4問・16件まで）。17件以上あるときは、表の番号で答えてもらう（「Other」に番号を書いてもらう）
- 選択肢のラベルは番号と短い要約、説明にはファイルと直し方を書く
- 何も選ばれなければ、何も変えずに終わる

### 6. 反映する

選ばれた指摘だけを直す。選ばれていない指摘に関わる変更はしない。

- 直したら、関係するテストや lint を実行して通ることを確かめる
- 直した内容は、論理的な区切りごとに commit スキルでコミットする
- 直し方が複数ありえて決められないときは、ユーザーに聞く

### 7. 結果を伝える

反映した指摘と、そのコミット（短い sha と1行目）、反映しなかった指摘の番号を伝える。
