# 作業の取りやめ

やらないことにした Issue を、理由のコメントを付けて not planned（予定なし）で閉じる。重複なら duplicate で閉じ、元の Issue に紐付ける。着手していれば、やめた作業（PR・リモートのブランチ・手元のワークツリーとブランチ）も片付ける。理由の文章は AI が書き、GitHub の操作は `issue-cancel.sh`、手元の片付けは `cleanup.sh --abandon` が行う。

閉じる理由のコメントは GitHub に残り、マージしていない作業は消すと戻せないので、必ず手順5でユーザーの承認を得てから行う（設計書 §8）。承認なしに、`--dry-run` を付けずにスクリプトを実行しない。

Project からは外さず、Story Point も変えない。後からボードで経緯を参照できるように、見積もりも記録の一部として残す（設計書 §4）。

親の Issue（サブ Issue を持つ Issue）を取りやめるときは、開いている子孫（子・孫）を一緒に取りやめるか、残すかを、手順5の確認でユーザーに選んでもらう。黙ってどちらかに決めない（設計書 §4）。

スクリプト（どれも JSON を出力する）:

- `${CLAUDE_PLUGIN_ROOT}/scripts/issue-cancel.sh`：理由のコメント、not planned か duplicate で閉じる操作、PR を閉じてリモートのブランチを削除する操作、親を閉じるときに開いている子孫を閉じる（`--sub-issues close`）か残す（`--sub-issues keep`）操作（`--help` で使い方）
- `${CLAUDE_PLUGIN_ROOT}/scripts/issue-branches.sh`：Issue の作業のブランチを、確かなブランチ（`branches`）と候補（`candidates`。名前が似ている・Issue を閉じる PR のブランチ）に分けて探し、Issue を閉じる開いている PR を出す。何も変えない（`--help` で使い方）
- `${CLAUDE_PLUGIN_ROOT}/scripts/cleanup.sh`：`--abandon` で、手元のワークツリーとブランチを削除する。失うものを `lost` に出す（`--help` で使い方）

## 手順

### 1. Issue を読む

引数があれば Issue の番号として使う（`12` でも `#12` でもよい）。引数が無ければ、依頼の文章から番号を読む。それでも分からなければユーザーに聞く。`gh issue view <番号> --json number,title,body,state,stateReason,subIssuesSummary` で Issue を読む。既に閉じていれば止める。ただし、前に取りやめの途中で止まった（Issue は閉じたが、PR やブランチが残った）続きなら、同じ理由で手順4から進める。

親の Issue（`subIssuesSummary.total` が 1 以上）なら、子を `gh api --paginate repos/{owner}/{repo}/issues/<番号>/sub_issues` で読み、孫を持つ子（`sub_issues_summary.total` が 1 以上か、応答に無い）はその下も同じように読んで、開いている子孫（`state` が `open`）を集める。開いている子孫が無ければ、普通の Issue と同じに進める。

開いている子孫に別のリポジトリの Issue（`repository_url` が今のリポジトリでない。GitHub の画面で手で紐付けたときだけできる）があれば、このスキルでは扱わずに止める。その Issue を親から外すか、そのリポジトリで取りやめてから、もう一度実行するよう伝える。`issue-cancel.sh` も、その場合は何もせずに止まる（設計書 §4）。

### 2. やめた作業のブランチを探す

`issue-branches.sh --issue <番号>` で、Issue の作業のブランチを探す。取りやめで片付ける対象は、`branches`（`branch.pattern` に合い番号が一致する、手元と origin の確かなブランチ。先頭に 0 が付いた古い名前も含む）だけにする。名前が似ているだけのブランチと、Issue を閉じる PR のブランチは `candidates`（候補）に分けて出るが、関係の無いブランチ（`backup/2024-01-15` など）や、`Closes #17, #18` の PR の別の Issue のブランチもありうるので、片付けない。`branches` の各ブランチの `local`（手元にあるか）・`remote`（origin にあるか）・`worktree` で、手順4の引数を決める（`remote` が true なら `--branch` を付け、`local` が true か `worktree` があれば `cleanup.sh` を実行する）。止まったら（PR の番号・無い番号・gh が古い・origin や Issue を読めない）、標準エラーの1行のメッセージを伝えて終える。ブランチが無いと決めつけて、Issue だけを閉じない。

- 複数あれば、どれを片付けるかユーザーに聞く（スクリプトは1回に1つのブランチを扱うので、選んだブランチごとに手順4と手順6を行う）
- `candidates`（候補）と、`open_prs`（Issue を閉じる、開いている PR）のうちブランチが `branches` に無いもの（規約に合わない名前のブランチやフォークの PR）は、このスキルでは片付けも閉じもしない。名前・PR の番号と URL を手順5の確認に書き、片付けるならユーザーに片付けてもらう（別の Issue の作業かもしれないため）
- 見つからなければ、着手していないか、ワークツリーを作らずに着手した（task-start の `--no-worktree`）ので、片付ける作業は無い。Issue を閉じるだけにする

親の Issue なら、親のブランチ（親には着手しないので、ふつうは無い）に加えて、開いている子孫ごとにも同じように探す。ブランチのある子孫は着手中なので、一緒に取りやめるときは、手順6でその子孫ごとに PR とブランチも片付ける。

### 3. 理由と参照先を書く

閉じるコメントの文章を、`language` の設定（`${CLAUDE_PLUGIN_ROOT}/scripts/config.sh` で読める）の言語で書く。PR があれば、同じ文章を PR にもコメントする。

- **理由**：なぜやらないのか（誤って起票した、方針が変わった、別の Issue と重複した、など）。依頼の内容から書き、分からなければ推測で埋めずにユーザーに聞く
- **参照先**：代わりに作業する Issue や、判断の根拠になった Issue・PR があれば `#N` で書く。文章だけ（「別の Issue で」）では辿れないので、必ず番号で書く。無ければ書かない
- **親の Issue のとき**：開いている子孫を一緒に取りやめると、同じコメントが子孫にも付く。子孫で読んでも分かるよう、親の番号（「親の #12 をやめるため」など）を入れて書く
- **閉じ方**：同じ内容の Issue が既にある（重複している）ときは duplicate、それ以外は not planned にする。duplicate にするのは、重複を表す言葉（「重複」「同じ内容が #20 に」など）と元の Issue の番号がそろったときだけ。番号が分からなければ聞く。迷うときは not planned にする（duplicate は元の Issue に紐付くので、誤ったときの影響が大きい）。大きすぎて子の Issue に分けたときは、重複ではないので not planned にし、子の Issue を参照先に書く

### 4. 行うことを確かめる

次を `--dry-run` で実行し、行うことと失うものを集める。ここで止まったら（既に閉じている Issue、無い Issue を重複の元に指定した、など）、標準エラーの1行のメッセージを伝えて終える。

- `issue-cancel.sh --issue <番号> --reason "<コメント>" [--duplicate-of <元の番号>] [--branch <ブランチ>] [--sub-issues close] --dry-run`：リモートにブランチがあるときだけ `--branch` を付ける。開いている子孫があるときだけ `--sub-issues close` を付ける（付けないと「開いている子の Issue（…）があります」で止まる）。閉じる PR（`pull_requests`）と、リモートのブランチを削除するか（`remote_branch_deleted`）、閉じる子孫（`sub_issues.open`）が分かる
- 着手中の子孫（手順2でブランチが見つかったもの）ごとに、同じコメントで `issue-cancel.sh --issue <子の番号> --reason "<コメント>" [--branch <子のブランチ>] [--sub-issues close] --dry-run`（その子孫の下にも開いている Issue があるときだけ `--sub-issues close` を付ける）と、手元にブランチかワークツリーがあれば下の `cleanup.sh` を実行し、子孫の PR・ブランチ・失うものを集める
- `cleanup.sh --branch <ブランチ> --abandon --dry-run`：手元にブランチかワークツリーがあるときだけ。メインのワークツリーで実行する（`cd "$(git rev-parse --git-common-dir)/.."`）。消すもの（`actions`）と失うもの（`lost`）が分かる。「未コミットの変更があります」で止まったら、メインのワークツリーでそのブランチを使っていて変更がある。ユーザーにコミットするか片付けてもらってから、もう一度確かめる

### 5. 確認を取る

次をまとめて見せ、AskUserQuestion で確認を取る。

- Issue の番号とタイトル、閉じ方（not planned か、#N の重複か）、コメントの全文
- 閉じる PR（番号とタイトル）と、削除するリモートのブランチ
- 削除する手元のワークツリーとブランチ
- 親の Issue なら、開いている子孫（番号とタイトル）と、着手中の子孫の PR・ブランチ・ワークツリー
- 失うもの（`lost`）：マージされていないコミット（`commits`）、未コミットの変更（`uncommitted`）、git が無視するファイル（`ignored`。`.env` など）、サブモジュールのリモートに無いコミット（`submodules`）。どれも消すと戻せないので、空でないものは省かずに書く

選択肢は「この内容で取りやめる」「Issue だけ閉じる（作業は残す）」「コメントを直す」「やめる」など（ブランチが無ければ「Issue だけ閉じる」は要らない）。親の Issue で開いている子孫があるときは、「この内容で取りやめる」の代わりに「子も一緒に取りやめる」（開いている子孫にも同じコメントを付けて not planned で閉じ、着手中の子孫の PR とブランチも片付ける）と「親だけ取りやめる」（子孫は開いたまま残る。閉じた親の下に残ることも書く）を出す。選択肢の説明には、選ぶと実際に何が起きるか（作るもの・削除するもの・GitHub に書き込むもの）を書き、`--dry-run` などのフラグやスクリプト名といった内部の手順は書かない（設計書 §8）。例：「この内容で取りやめる」の説明は「Issue #12 に下のコメントを付けて予定なし（not planned）で閉じ、PR #15 を閉じ、ブランチ feat/12-add-login をリモートと手元から、ワークツリーと一緒に削除する。未コミットの変更 2 件と .env は失われる。Project と Story Point はそのまま残す」（重複なら「#20 の重複として閉じ」）。見せた内容は、質問の中にも入れる（設計書 §8。別の端末から使うと、質問の直前の文章が見えないことがある）。各選択肢の preview に、上の内容をすべて入れる。ユーザーが直したい点を言えば、直してもう一度見せる。

### 6. 取りやめる

手順5で承認されたら、Issue → PR とリモートのブランチ → 手元の順に行う。「子も一緒に取りやめる」なら、先に着手中の子孫ごとに、手順4と同じ引数で下の1と2を行ってから、親で1と2を行う（親を閉じるときに、残りの開いている子孫を閉じる）。

1. 手順4と同じ引数で、`--dry-run` を付けずに `issue-cancel.sh` を実行する（「Issue だけ閉じる」なら `--branch` を付けない。「親だけ取りやめる」なら、`--sub-issues close` の代わりに `--sub-issues keep` を付ける）
2. 「Issue だけ閉じる」でなく、手元にブランチかワークツリーがあれば、メインのワークツリーで `cleanup.sh --branch <ブランチ> --abandon` を実行する。削除するワークツリーの中にいたままだと、削除した後に今の場所が無くなるので、先に移る

失敗したら、標準エラーの1行のメッセージをそのまま伝える。どのスクリプトも何度実行しても同じ結果になるので、原因を片付けた後に同じ引数でもう一度実行すれば、続きから進む。

- 「コメントしましたが、閉じられませんでした」：Issue にコメントは付いている。もう一度実行すると、コメントを付け直さずに閉じる（最後のコメントが同じ理由かで判断する。同じ理由・同じ閉じ方で既に閉じていれば、Issue には何もしない）
- 「子の Issue #N に…できませんでした」「子の Issue #N を閉じられませんでした」：親にはまだ何もしていない。もう一度実行すると、閉じた子孫を飛ばして続きから進む
- 「Issue #N は閉じましたが、…」：PR かリモートのブランチの操作で止まった。もう一度実行すると、残りの PR とブランチから続ける
- `cleanup.sh` で止まった：Issue・PR・リモートのブランチは片付いている。手元の片付けだけをやり直す

### 7. 結果を伝える

閉じた Issue の番号とタイトル、閉じ方、付けたコメント、閉じた PR、削除したブランチとワークツリーを伝える。親の Issue なら、一緒に閉じた子孫か、残した子孫（`sub_issues.open`）も伝える。Project の自動化（Item closed）が有効なら、閉じた Issue は Done の列に移る。「Issue だけ閉じる」を選んだときは、残したブランチとワークツリーを伝える。
