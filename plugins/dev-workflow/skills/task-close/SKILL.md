# やらない Issue を閉じる

やらないことにした Issue を、理由のコメントを付けて not planned（予定なし）で閉じる。理由の文章は AI が書き、コメントと閉じる操作は `issue-close.sh` が行う。

閉じる理由のコメントは GitHub に残るので、必ず手順3でユーザーの承認を得てから閉じる（設計書 §8）。承認なしに `--dry-run` を付けずに `issue-close.sh` を実行しない。

Project からは外さず、Story Point も変えない。後からボードで経緯を参照できるように、見積もりも記録の一部として残す（設計書 §4）。

スクリプト（JSON を出力する）:

- `${CLAUDE_PLUGIN_ROOT}/scripts/issue-close.sh`：理由のコメントと、not planned で閉じる操作（`--help` で使い方）

## 手順

### 1. Issue を読む

`gh issue view <番号> --json number,title,body,state` で Issue を読む。番号が分からなければユーザーに聞く。既に閉じていれば止める。

### 2. 理由と参照先を書く

閉じるコメントの文章を、`language` の設定（`${CLAUDE_PLUGIN_ROOT}/scripts/config.sh` で読める）の言語で書く。

- **理由**：なぜやらないのか（誤って起票した、方針が変わった、別の Issue と重複した、など）。依頼の内容から書き、分からなければ推測で埋めずにユーザーに聞く
- **参照先**：代わりに作業する Issue や、判断の根拠になった Issue・PR があれば `#N` で書く。文章だけ（「別の Issue で」）では辿れないので、必ず番号で書く。無ければ書かない

### 3. 確認を取る

`issue-close.sh --issue <番号> --reason "<コメント>" --dry-run` で、閉じられることを確かめる（既に閉じている Issue などはここで止まる）。

Issue の番号とタイトル、コメントの全文を見せ、AskUserQuestion で確認を取る。選択肢は「この内容で閉じる」「コメントを直す」「やめる」など。選択肢の説明には、選ぶと実際に何が起きるか（作るもの・削除するもの・GitHub に書き込むもの）を書き、`--dry-run` などのフラグやスクリプト名といった内部の手順は書かない（設計書 §8）。例：「この内容で閉じる」の説明は「Issue #12 に下のコメントを付け、予定なし（not planned）で閉じる。Project と Story Point はそのまま残す」。見せた内容は、質問の中にも入れる（設計書 §8。別の端末から使うと、質問の直前の文章が見えないことがある）。各選択肢の preview に、Issue の番号とタイトル、コメントの全文を入れる。ユーザーが直したい点を言えば、コメントを直してもう一度見せる。

### 4. 閉じる

手順3で承認されたら、同じ引数で `--dry-run` を付けずに `issue-close.sh` を実行する。

失敗したら、標準エラーの1行のメッセージをそのまま伝える。

### 5. 結果を伝える

閉じた Issue の番号とタイトル、付けたコメントを伝える。Project の自動化（Item closed）が有効なら、閉じた Issue は Done の列に移る。

その Issue のブランチやワークツリーが既にあれば（`git worktree list` と `git branch --list '*/<番号>-*'` で探す）、そのことも伝える。マージされていないので `task-finish` では片付けられない。要らなければ、ユーザーに削除してもらう。
