# レビューの観点を足す

観点の内容を聞き取って観点ファイルを書き、`review-perspective-add.sh` で置く。作った観点は、次から review スキルのサブエージェントが使う（設計書 §7）。

作るのは手元のファイルだけなので、作成の確認は取らない（設計書 §8）。ただし、置く層はユーザーに選んでもらい、ほかの層の同じ名前の観点を置き換えるときは確認を取る。

review スキルの手順9（レビューの後にユーザーが出した指摘を観点に残す）からも、この手順で作る。そのときは、観点の内容は指摘で決まっているので、手順1の聞き取りは省く。

スクリプト（JSON を出力する）:

- `${CLAUDE_PLUGIN_ROOT}/scripts/review-perspectives.sh`：今ある観点の一覧（`--help` で観点ファイルの形式）
- `${CLAUDE_PLUGIN_ROOT}/scripts/review-perspective-add.sh`：観点ファイルを作る（`--help` で使い方）

## 手順

### 1. 観点の内容を聞く

何を確かめたいかを依頼から読み取る。依頼から分からなければ、ユーザーに聞く。観点ファイルを書くのに次が分かればよい。聞くのは、依頼から読み取れないことだけにする。

- 差分の何を確かめるか（どんな問題を見つけたいか）
- 当てはまらない差分・指摘しないこと（あれば）
- どんな変更のときに実行するか（実行する条件。手順3）。依頼から読み取れず、内容からも決められなければ聞く。決まらなければ条件を付けず、毎回実行する

### 2. 今ある観点と比べる

`review-perspectives.sh` を実行し、`perspectives`・`disabled`・`invalid` の名前と title を見る。

- 同じことを確かめる観点が既にあれば、その観点（名前・title・パス）を伝え、それでも作るかをユーザーに聞く
- 手順3で決める名前は、ここにある名前と重ならないようにする。既にある観点を自分用に書き換えたいという依頼なら、同じ名前にする（手順5で置き換えの確認を取る）

### 3. 観点ファイルの中身を書く

- **名前**：内容が分かる英語の短い名前（小文字の英数字と `-`。例：`error-messages`）。ファイル名になる
- **title**：一覧に出す1行の説明。「〜か」のように、何を確かめるかが分かる問いの形にする。全体を引用符で囲まない（読むときに外れる）
- **本文**：サブエージェントへのレビューの指示。同梱の観点（`${CLAUDE_PLUGIN_ROOT}/review/*.md`）に倣い、次を書く
  - 何を確かめるか（具体的な確かめ方。どのファイルや情報を読むか）
  - 指摘には何を挙げるか（どのファイルと行か、どう直すべきか）
  - 指摘しないこと（観点の外のこと・好みの問題）と、当てはまらない差分のときは指摘を出さないこと
  - 「〜を指摘しない」ことだけを書いた観点は作らない。観点は別のサブエージェントで動くので、ほかの観点の指摘は止められない。ほかの観点の指摘を止めたいときは、その観点ファイルの「指摘しないこと」に足す（`/code-review` の指摘なら、`code-review` の観点ファイルの「## 指摘しないこと」の節。review スキルの手順9）
  - 結果の形（JSON）は review スキルが指示するので、本文には書かない
- **実行する条件**（任意）：当てはまらない変更ではサブエージェントを起動しないよう、観点が意味を持つ変更を条件で書く。条件を付けなければ毎回実行する。複数付ければ、すべてに当てはまるときだけ実行する（形式は `review-perspectives.sh --help`）
  - type（`--type`）：変更の type（Issue の type ラベル、Issue が無いか1つに決まらなければブランチ名の type）がこのどれかのとき。type が分からなければ外れる。例：不具合の修正だけを見る観点は `fix`
  - パス（`--path`）：差分のファイルがこのパターンに当たるとき。`.gitignore` と同じ書き方で、`*` は `/` をまたがない。`!` で始めると除外。例：シェルスクリプトだけを見る観点は `**/*.sh`、docs の下だけの変更では見ない観点は `!docs/**`
  - Issue（`--issue-required`）：Issue があるときだけ。例：Issue と差分を突き合わせる観点
  - マージ先の進み（`--base-ahead-required`）：ブランチを作った後にマージ先へコミットが入ったときだけ。例：マージ先の変更との食い違いを見る観点
  - 本文の中で「当てはまらなければ指摘を出さない」と判断させるより、条件で外すほうがサブエージェントを起動しないぶん安い。条件で判断できることは条件に書く

### 4. 置く層を選んでもらう

依頼で決まっていなければ、AskUserQuestion で選んでもらう。git のリポジトリの外では、自分の観点だけにして聞かずに進める。

- 選択肢は次の2つ。説明には、作るファイルのパスと、どこで使われるかを書く
  - 自分の観点：`~/.claude/dev-workflow/review/<名前>.md` を作り、全リポジトリのレビューで使う
  - このリポジトリの観点：`<repo>/.claude/dev-workflow/review/<名前>.md` を作る。コミットすると、このリポジトリで作業する全員のレビューで使われる
- 手順3で書いた観点ファイルの中身（名前・title・実行する条件・本文）を、各選択肢の preview にそのまま入れる（設計書 §8。別の端末から使うと、質問の直前の文章が見えないことがある）。確認に必要な内容は、文章で見せるだけでなく質問の中にも入れる
- 中身を直したいと答えられたら、手順3に戻って直し、もう一度聞く

### 5. 作る

本文を標準入力に渡して実行する。実行する条件は、付けるものだけをオプションで渡す（`--type`・`--path` は値ごとに繰り返す）。リポジトリの層に作るときは、今のタスクのワークツリー（task-start の `worktree`）の中で実行する（`cd <worktree> && ...`）。観点の追加・修正は、そのきっかけになったタスクの PR に含めるため（設計書 §7）。今いる場所で実行すると、メインの作業ツリー（main の上など）にでき、タスクの PR に入らない。今のタスクのワークツリーが会話から分からなければ、今いる場所で実行する（手順6で `work_branch` を見て伝える）。

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/review-perspective-add.sh" --name <名前> --layer user|repo --title "<title>" \
  [--type <type>]... [--path '<パターン>']... [--issue-required] [--base-ahead-required] [--builtin code-review] <<'EOF'
<本文>
EOF
```

- `--builtin code-review` は、同梱の観点 `code-review` を上位の層で置き換えるときだけ付ける（本文は「## 指摘しないこと」の節。review スキルの手順9）
- **終了コード 3**（同じ層に同じ名前の観点が既にある）：上書きしない。既にあるファイルのパスを伝え、別の名前で作るか、既にあるファイルを直接直すかをユーザーに聞く
- **終了コード 4**（下位の層に同じ名前の観点がある）：AskUserQuestion で、置き換えるか別の名前にするかを聞く。選択肢の説明には、例えば「同梱の観点 docs-sync の代わりに、~/.claude/dev-workflow/review/docs-sync.md の観点を使う」「別の名前（docs-sync-mine）で新しい観点として足す」のように、選ぶと何が変わるかを書く。置き換えるなら `--override` を付けて実行し直す
- **終了コード 5**（上位の層に同じ名前の観点がある）：作っても、このリポジトリでは上位の層の観点が使われる。AskUserQuestion で、別の名前にするか、それでも作るかを聞く。別の名前を先に置き、説明には、例えば「別の名前（docs-sync-mine）で足し、このリポジトリでも使う」「~/.claude/dev-workflow/review/docs-sync.md を作るが、このリポジトリでは <repo>/.claude/dev-workflow/review/docs-sync.md が使われ、ほかのリポジトリでだけ使われる」のように書く。メッセージに下位の層のファイルもあれば（`--override` でそれも置き換わる）、「ほかのリポジトリでは同梱の観点 docs-sync の代わりに使われる」のように、それも説明に書く。それでも作るなら `--override` を付けて実行し直す
- ほかのエラー（書き込めないときの終了コード 1 など）で失敗したら、標準エラーの1行のメッセージをそのまま伝える

### 6. 結果を伝える

作ったファイルのパス（`path`）と、その中身を伝える。

- `overrides` があれば、そのファイルの観点の代わりに、作った観点が使われることを伝える
- `shadowed_by` があれば、上位の層の同じ名前の観点が優先されるので、作った観点はこのリポジトリでは使われないことを伝える
- リポジトリの層に作ったときは、コミットするまでほかの人には使われないことを伝える。そのうえで、`work_branch` を見て次を伝える
  - `true`：今のタスクのブランチ（`branch`）で commit スキルでコミットし、そのタスクの PR に含めるよう案内する。観点のためだけに別の Issue は立てない
  - `false`：作業用のブランチの上ではない（`branch` が base_branch か、null なら detached HEAD）ので、そのままではコミットできず、タスクの PR にも入らないことを伝える。観点を足すきっかけになったタスクがあれば、そのワークツリーへファイルを移してコミットするよう、無ければ task-start で作業を始めてからコミットするよう案内する
  - `null`：設定を読めず、作業用のブランチの上か分からない。標準エラーの警告（`warn:`）をそのまま伝え、ブランチ（`branch`）を添えて、作業用のブランチなら commit スキルでコミットするよう案内する
- 次の review スキルから使われること、観点を止めたり直したりするには、そのファイルを直接編集すればよいことを伝える
