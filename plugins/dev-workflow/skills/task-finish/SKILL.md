# 作業の後片付け

PR がマージされた作業のワークツリーとローカルのブランチを削除し、マージ先のブランチ（`base_branch`）を最新にする。マージの確認・削除・更新と、PR が閉じる Issue の状態の確認（`issues`）は `cleanup.sh` が行う。

ワークツリーを作らずに着手したタスク（task-start の `--no-worktree`）には、ブランチも PR も無い。片付けるものが無いので止まらずに、PR の代わりに Issue を完了として閉じる（手順4）。閉じると GitHub に残るので、そのときだけ確認を取る（設計書 §4・§8）。ブランチは `issue-branches.sh` で、確かなブランチ（`branch.pattern` に合い番号が一致する）と候補（名前が似ている・Issue を閉じる PR のブランチ）に分けて探す。片付けるのは確かなブランチだけで、見つからなくても、ワークツリーの無いタスクと決めつけない。確かなブランチが無かったことと候補を見せて、閉じるか、別の名前のブランチ（候補）で作業したかをユーザーに選んでもらう（ブランチの見落としは、ここで人が止める）。

「マージしたので片付けて」という依頼で結果が決まり、作業が失われるとき（マージされていない、PR に入っていないコミット・未コミットの変更・サブモジュールの push していないコミット・git が無視するファイルがある）は `cleanup.sh` が何も消さずに止まる。そのため、実行の確認は取らずに `base_branch` の更新まで進め、結果を伝える（設計書 §8）。git が無視するファイルを消してよいかだけは、止まった後に確認を取る（手順2）。

スクリプト（どれも JSON を出力する）:

- `${CLAUDE_PLUGIN_ROOT}/scripts/issue-branches.sh`：Issue の作業のブランチを、確かなブランチ（`branches`）と候補（`candidates`。名前が似ている・Issue を閉じる PR のブランチ）に分けて探し、Issue の状態と、Issue を閉じる開いている PR を出す。何も変えない（`--help` で使い方）
- `${CLAUDE_PLUGIN_ROOT}/scripts/cleanup.sh`：マージの確認、ワークツリーとブランチの削除、`base_branch` の更新、PR が閉じる Issue の状態の確認（`--help` で使い方）

## 手順

### 1. 片付けるブランチを決める

- 引数があれば、まず Issue の番号かを見る。`12` か `#12`（数字だけか、`#` の後が数字だけ）なら Issue の番号として使う。それ以外（`fix-foo` など）はブランチ名として、そのブランチで手順2に進む。依頼の文章でブランチ名を指定されたときも同じ
- 引数が無ければ、依頼の文章から番号を読む
- 番号があれば、`issue-branches.sh --issue <番号>` でブランチを探す。`branches` に、`branch.pattern` に合い番号が一致する、手元と origin の確かなブランチが出る（先頭に 0 が付いた古い名前も含む）。名前が似ているだけのブランチと、Issue を閉じる PR のブランチは、`candidates`（候補）に分けて出る。候補には関係の無いブランチ（`backup/2024-01-15` など）や別の Issue のブランチもありうるので、手順4で見せて聞くだけにし、ここでは片付けない。PR からはブランチを探さない（別の Issue の PR のブランチまで拾うため。PR のブランチは候補にだけ出る）。止まったら（PR の番号・無い番号・gh が古い・origin や Issue を読めない）、標準エラーの1行のメッセージを伝えて終える。ブランチが無いと決めつけて手順4に進まない
  - することは `action` に出る（判断はスクリプトが行う。下の値ごとにすることだけをする）。`cleanup` なら確かなブランチを片付ける。それ以外なら、手順2・3を飛ばして手順4に進む
  - `cleanup` で確かなブランチが1つなら、そのブランチで手順2に進む。手元に無い（`local` が false。別の場所で作業した、既に消した）ブランチでも進めてよい。手元に消すものは無く、マージの確認と base_branch の更新、Issue の状態の確認だけが行われる。PR が開いていれば、`cleanup.sh` が「まだマージされていません」で止まるので、何も消えない
  - 複数あれば、名前・手元にあるか・origin にあるか・ワークツリーを見せて、どれを片付けるかユーザーに聞く
- 番号が分からなくて、今いるのが作業用のブランチ（ワークツリーの中など）なら、そのブランチ

### 2. 実行する

削除するワークツリーの外に出てから（Bash では `cd "$(git rev-parse --git-common-dir)/.."` でメインのワークツリーに移る）、`cleanup.sh --branch <ブランチ>` を実行する。ワークツリーの中にいたままだと、削除した後に今の場所が無くなる。実行の前に AskUserQuestion で確認を取らない。

止まったときは、標準エラーの1行のメッセージをそのまま伝えて終える（git が無視するファイルで止まったときだけは、下のとおり確認を取って続けられる）。それ以外では、削除のために変更を捨てたり、強制したりしない。

- 「まだマージされていません」「マージされた PR がありません」：マージされてから片付ける
- 「PR に入っていないコミットがあります」：push していない作業が無いかユーザーに確かめてもらう
- 「未コミットの変更があります」：コミットするか、要らなければユーザーに片付けてもらう
- 「サブモジュール（…）に、リモートに無いコミットか stash があります」：サブモジュールのリモートに push するか、要らなければユーザーに片付けてもらう。リモートのブランチ・タグに無いコミットを SHA で取ってきただけのときも止まるので、そのコミットが要らないことをユーザーに確かめてもらってから、ユーザーにワークツリーを消してもらう
- 「git が無視するファイル（…）があります」：`.env` やローカルの設定など、git が無視するファイルが残っている。メッセージのファイルの一覧を見せ、AskUserQuestion で「ワークツリーと一緒に削除する」「やめる」を選んでもらう。ファイルの一覧は、質問の中にも入れる（設計書 §8。別の端末から使うと、質問の直前の文章が見えないことがある）。選択肢の説明には、選ぶと実際に何が起きるか（「.env と build/ をワークツリーごと削除し、ブランチを消して main を最新にする」など）を書き、`--remove-ignored` などのフラグやスクリプト名といった内部の手順は書かない（設計書 §8）。削除すると言われたときだけ、同じ引数に `--remove-ignored` を付けて実行する。要るファイルなら、ユーザーに移してもらってから片付ける

ほかのエラーで失敗したら、標準エラーの1行のメッセージをそのまま伝える。途中で失敗しても、もう一度実行すれば既に削除したものを飛ばして続きから進む。

### 3. 結果を伝える

削除したワークツリー（`worktree`）とブランチ、`base_branch` の更新（`base.from` → `base.to` の短い sha）を伝える。以後の作業はメインのワークツリー（`main_root`）で行う。

PR が閉じる Issue（`Closes #N`）は `issues`（`number` と `state`）に出る。Issue の番号（`repo` があれば `owner/repo#番号`）と、閉じたか（`CLOSED`）開いたまま（`OPEN`）かを伝える。開いたままのときは、その旨を伝える。GitHub は、マージの後に Issue を少し遅れて閉じることがあるので、「マージの直後は反映が遅れることがある。少し待って `gh issue view <番号>` で確かめ、それでも開いていれば `gh issue close <番号>` で閉じられる」と伝える。`repo` がある Issue（別のリポジトリの Issue）には、どちらのコマンドにも `--repo <owner/repo>` を付けて案内する（付けないと、今のリポジトリの同じ番号の別の Issue を見たり閉じたりしてしまう）。片付けは済んでいるので、止まらずに結果として伝え、閉じるかはユーザーに任せる（閉じるのは、頼まれたときだけ行う）。`state` が `null` なら、状態を取得できなかったので、`gh issue view <番号>`（`repo` があれば `--repo <owner/repo>` 付き）で確かめるよう伝える。`issues` が空なら、PR が閉じる Issue は無かったと伝える。

### 4. ワークツリーの無いタスクを終える

手順1で、`action` が `cleanup` でなかったときに行う。`action` の値ごとに、次のことをする（どの値になるかは `issue-branches.sh` が決め、組み合わせは bats で確かめている）。

- `cleanup_candidate`：Issue は閉じていて、候補（`candidates`）がある（規約に合わない名前のブランチの PR がマージされて閉じた、など）。候補の名前・手元にあるか・ワークツリー・紐付く PR（`pr`）を見せ、AskUserQuestion で、どの候補で片付けるか（候補ごとの選択肢）か「何もしない」を選んでもらう。選ばれた候補で手順2から片付ける
- `nothing`：Issue は閉じていて、候補も無い。片付けるものも閉じるものも無いと伝えて終える
- `blocked_open_pr`：Issue を閉じる PR（`open_prs`）が開いている（規約に合わない名前のブランチやフォークで作業している）ので、作業はまだ終わっていない。Issue を閉じずに止め、PR の番号・URL・ブランチ（`branch`）を伝える。マージされると GitHub が Issue を閉じること、マージの後の片付けは、そのブランチの名前を指定して task-finish でできることを伝える
- `blocked_sub_issues`：開いている子がある親の Issue なので、閉じずに止める。親は、最後の子を閉じた後に人が閉じる（設計書 §4）ことを伝え、開いている子は `gh api --paginate repos/{owner}/{repo}/issues/<番号>/sub_issues` で読んで、番号とタイトルを見せる
- `ask_close`：ワークツリーを作らずに着手したタスクか、確かなブランチの名前の形でないブランチで作業したタスク。決めつけずに、AskUserQuestion で次から選んでもらう。質問の中に、Issue の番号とタイトル、「`branch.pattern` の形で番号が一致するブランチを、手元と origin で探したが見つからなかった」こと、`candidates` があればその名前（名前が似ている、または Issue に紐付く PR のブランチ）、「結果（調査の結論など）を Issue に残していなければ、閉じる前に残す。やめることにしたタスクなら、閉じずに task-cancel を使う」ことを入れる（設計書 §8。選ぶ前に読めるように）。選択肢の説明には、選ぶと実際に何が起きるかを書き、コマンドやスクリプト名といった内部の手順は書かない
  - 「Issue #12 を完了として閉じる」：ワークツリーを作らずに着手したタスクとして、Issue #12 を完了（completed）で閉じる。Project の自動化が有効なら Done に移る
  - 「別の名前のブランチで作業した」：候補があれば、その中から選ぶか名前を聞いて、そのブランチで手順2から片付ける（Issue は閉じない。PR がマージされていれば GitHub が閉じている）
  - 「やめる」：何も変えない

「Issue #12 を完了として閉じる」が選ばれたら、`gh issue close <番号> --reason completed` を実行し、Issue の URL を添えて伝える。Project の自動化（Item closed）が有効なら、閉じた Issue は Done の列に移る。

### 5. 次のタスクの前に /clear を勧める

全経路の最後に、ここで1回だけ行う。次のタスクに着手する前に `/clear` するよう勧める（前のタスクの経緯が次のタスクに混ざらないようにするため。`/clear` の後も、タスクの進め方は SessionStart のフックが読み込み直す）。`/clear` は組み込みのコマンドで、スキルから実行できないので、勧めるだけにする。

- 勧めるのは、片付けを実際に終えたとき（ワークツリーとブランチを削除した、または手順4で Issue を完了として閉じた）で、かつこの会話で、その Issue の task-start や実装・レビュー・PR の作業をしていたとき。この会話に無い（別のタスクの途中、または新しいセッションで古い PR を片付けただけ）なら勧めない
- それ以外は勧めない。たとえば、手順2で止まったとき、`cleanup.sh` 自身が何も消さずに止めた・断ったとき（push していないコミット、未コミットの変更、`.env` などを消す確認を断ったときを含む）、ブランチ名の確認や Issue を閉じる確認で「やめる」を選んだとき、`blocked_open_pr`・`blocked_sub_issues`・`nothing` のとき（作業が終わっていない）
